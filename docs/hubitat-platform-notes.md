# Hubitat Groovy and platform notes

What Groovy code running on the hub can do and see (the sandbox, `state`, events, scheduling, outbound HTTP, app pages and the platform objects) where Hubitat's documentation leaves it out, contradicts it or gets it wrong. The hub's HTTP surface, as a client off the hub sees it, is in [internal APIs](hubitat-internal-apis.md). Coding conventions are in `ARCHITECTURE.md`.

The official sources are the on-hub API reference (hub UI at `/hub/developerDocumentation`, one JSON page per id at `/developer-docs/{pageId}.json`, cited below as *on-hub `page-id`*) and the [developer documentation](https://docs2.hubitat.com/en/developer/overview). Don't restate them here: link to the documented part and record only what they omit or what differs. When a note contradicts the official docs, it says so and names the test that settled it.

Every fact carries an evidence mark ([EVIDENCE.md](EVIDENCE.md)). A `regression` mark names `apps/tests/test-architecture-claims.sh` or another test that re-checks the note: re-run them after each major firmware update and widen the marks' build ranges to the new build ([EVIDENCE.md](EVIDENCE.md#firmware-builds)).

## Sandbox and Groovy

- **`@CompileStatic` can change behavior without a compile error.** Under static compilation, `Map x = [k: false]` is inferred as `Map<String, Boolean>`, so a later `x.prop = 0.5` stores `true`; and an Elvis result multiplied by a `long` (`(a ?: b) * 1000L`) can throw `ClassCastException` at runtime. Both compiled cleanly *(inferred from a local run under Groovy 2.4.21, the hub's version)*. Static checking also types `Integer.intdiv(...)` as `Number`, so `int h = n.intdiv(60)` fails to compile on the hub while the local parse-check passes it; use `.intValue()` *(probed 2.5.2.134)*. Annotate only methods whose maps and arithmetic are explicitly typed, and run the method's tests after adding it.
- `@TypeChecked` is not in the [allowed imports](https://docs2.hubitat.com/en/developer/allowed-imports); saving code that imports it fails with `Importing [groovy.transform.TypeChecked] is not allowed`. `@CompileStatic` is allowed *(probed 2.5.0.148)*.
- The sandbox treats a fully-qualified class name as an implicit import, so an FQN reference to a class missing from the allowed imports is rejected the same way as an `import`: `new java.io.File(...)` with no import fails the save with `Importing [java.io.File] is not allowed` *(regression 2.5.2.135–2.5.3.102, apps/tests/test-architecture-claims.sh)*.
- `encrypt(String)` / `decrypt(String)` are callable from an app and round-trip; a 60-character `state` string encrypted to 88 characters *(probed 2.5.2.134)*. The on-hub API reference calls it a static-IV helper, so equal inputs encrypt alike *(docs: on-hub shared-utilities)*. The key stays with the hub: Hubitat's [Lock Code Manager docs](https://docs2.hubitat.com/en/apps/lock-code-manager) say encrypted lock codes cannot be read after a migration *(docs: [Lock Code Manager](https://docs2.hubitat.com/en/apps/lock-code-manager))*. Whether lock codes use this exact helper, and how `decrypt()` fails on foreign input, is untested.
- `decrypt()` and `encrypt()` are slow, and every call costs the same: about 350 ms on a C-8 Pro and about 830 ms on a C-7 for a 70-character string *(probed 2.5.2.139 C-7 and C-8 Pro, 2.5.3.103 C-8 Pro, throwaway app)*. Decrypting a stored token for each request adds that to every request and poll. Decrypt once and keep the plaintext in memory: a `@Field static ConcurrentHashMap` keyed by `app.id` (or `device.id`) and the secret's name, holding `[ciphertext, plaintext]` so a replaced token misses the cache. Drop the entry wherever the encrypted value is written or cleared, and in `uninstalled()`. The plaintext never goes into `state` *(inferred: from the per-call cost and the `@Field static` behaviour below)*.
- A `password`-type app input is masked only in the page's rendered input: its value comes back in plain text from `/installedapp/statusJson/{id}` (`appSettings[].value`) and from the configure JSON's `settings` map *(probed 2.5.2.134)*. Keep a password in a setting only as long as the code needs it, then `app.removeSetting()` it.
- **How the save reports a sandbox violation** depends on the expression, not the class: an `import` or a constructor of a refused class gives `Importing [java.io.File] is not allowed` (no line); a static call on one gives `Expression [MethodCallExpression] is not allowed: java.lang.System.currentTimeMillis() at line number 3`; a bare reference (`Runtime.runtime`, `x instanceof File`, `def r = Thread`) gives `Expression [ClassExpression] is not allowed: java.lang.Runtime at line number 3`; a typed local or parameter gives `Expression [DeclarationExpression] ...` or `Expression [VariableExpression] ...`. A cast (`(File) x`) is accepted. Only the first violation in the file is reported. Methods refused by name on any receiver: `getClass`, `print`, `printf`, `println`, `sleep`, `invokeMethod`, `getMetaClass`, `setMetaClass`, `getMethods`, `getFields`, `getDeclaredMethods`, `getDeclaredFields`, `getClassLoader`; `wait`, `evaluate` and `getProperties` are accepted. `execute()` is refused on a string literal (`"ls".execute()` fails with `Expression [MethodCallExpression] is not allowed: ls.execute() at line number 3`) and on a list literal (`["ls"].execute()`), and accepted on a GString (`"ls ${n}".execute()`) and on an untyped variable (`x.execute()`) *(probed 2.5.2.135, throwaway apps)*. Assigning to a metaclass (`String.metaClass.foo = { -> 1 }`) fails the save with an HTTP 500 compiler error. `java.lang.Class`, `java.util.concurrent.atomic.AtomicReference`, `java.util.concurrent.Executors`, `java.util.concurrent.locks.ReentrantLock` and `java.util.Timer` are refused; `AtomicIntegerArray`, `Semaphore`, `TimeUnit`, `MessageDigest`, `SimpleDateFormat`, `RoundingMode` and `ConcurrentLinkedQueue` are accepted *(probed 2.5.2.135, throwaway apps)*.
- `java.lang.Iterable` is refused too: `x instanceof Iterable` fails the save with `Expression [ClassExpression] is not allowed: java.lang.Iterable` *(probed 2.5.2.135, throwaway app)*.
- **Property names refused at run time.** Reading `fields`, `metaClass`, `methods`, `declaredFields`, `declaredMethods`, `declaredConstructors`, `constructors`, `classLoader` or `protectionDomain` as a property throws `java.lang.SecurityException: Subscript property 'fields' is not allowed from app or driver code`, on a Map (`m.fields`, `m['fields']`, `m.classLoader`) as on any object (`"x".classLoader`); read such a map key with `m.get('fields')`. Through a dynamic name (`m."${n}"`) `class` is refused too, while the literal `m.class` and `m.properties` read the map's values. `m[n]` with a variable name is never refused, and `state.fields` and `settings.fields` read null *(probed 2.5.2.135, throwaway app)*.
- **No class is imported for you.** On 2.5.2.135 a type annotation with any of `DataType`, `HubAction`, `HubMultiAction`, `Protocol`, `DeviceWrapper`, `ChildDeviceWrapper`, `Event`, `Hub`, `HexUtils`, `JsonSlurper`, `JsonOutput`, `Field`, `ConcurrentHashMap` and the other hub and JDK helpers fails to compile (`unable to resolve class DataType`) unless imported; only Groovy's own default packages (`groovy.util.XmlSlurper`) resolve. The bare name `DataType` still works without an import, in apps and drivers, because the script has a `DataType` property holding `hubitat.zigbee.zcl.DataType`; bare `HubAction` or `Protocol` reads null *(probed 2.5.2.135, throwaway app and driver)*.

## Object introspection

Ways to look at an object's surface, picked by what you need:

- **Just the runtime class name:** [`getObjectClassName(value)`](https://docs2.hubitat.com/en/developer/common-methods-object). The docs present it as the allowed alternative to `value.getClass()`; they don't say that the hub rejects `getClass()` when the code is saved (see [Sandbox and Groovy](#sandbox-and-groovy)), so a `try`/`catch` can't guard it *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*. Routine pattern in exception handlers: `"${getObjectClassName(e)}: ${e.message}"`.
- **Live bean-property snapshot:** `obj.properties.each { k, v -> ... }`. Returns the Groovy bean-accessor map of every readable getter with its current value. Used by `drivers/tests/DeviceInspector.groovy` to dump the full `DeviceWrapper` surface in one line. Best for objects whose useful state IS bean properties (`device`, `location`, `hub`, parsed Maps); much smaller surface for objects whose API is parameterized methods (e.g. `zigbee.properties` returns only 6 entries *(probed 2.5.2.135, throwaway driver)*).
- **Full API surface with signatures:** not available. The save rejects any call named `getMethods()`, `getFields()`, `getDeclaredMethods()`, `getDeclaredFields()` or `getClassLoader()`, whatever the receiver (`Expression [MethodCallExpression] is not allowed: cls.getMethods() at line number 58`), so a driver built on them no longer saves, and reading them as properties (`cls.methods`) throws at run time (see [Sandbox and Groovy](#sandbox-and-groovy)) *(false 2.5.0.148; probed 2.5.2.135)*. `Runtime.runtime.availableProcessors()` is refused too; use `/hub/cpuInfo` for CPU and core-count data *(probed 2.5.0.148, C-8 Pro)*.

## MarkupBuilder (`mkp`) in the sandbox

- Inside `groovy.xml.MarkupBuilder`, the `mkp` accessor resolves to **null within nested tag closures**: `mkp.yieldUnescaped(...)` / `mkp.yield(...)` throw `NullPointerException` (`Cannot invoke method yieldUnescaped() on null object`) *(regression 2.5.2.135–2.5.3.102, apps/tests/test-architecture-claims.sh, `yieldUnescaped` only)*. `mkp` is a property (getter) access the sandbox returns null for, whereas tag *method* calls (`svg`, `path`, `td`, …) route through the builder's `methodMissing` and work. Emit raw markup (e.g. inline SVG) as nested builder tags, not via `mkp`. Hyphenated attribute names (`stroke-width`, `stroke-linecap`) must be quoted string keys in the attribute map *(probed firmware not recorded, a served report page in a community app)*.

## Execution and concurrency

- **An execution is a unit of work.** Each entry point loads the app or device, runs one method and saves `state` when the method returns; a throw drops the `state` writes, while `atomicState` writes and events already sent are kept *(probed 2.5.2.135, C-8 Pro, throwaway app and driver; inferred: the SmartThings Classic execution model Hubitat was built to run)*. Staff describe attribute values as cached "for performance sake", with `skipCache` bypassing the cache, and `sendEvent` as a request "put in a queue" that "a separate thread picks up and runs" *(staff: [chuck.schwer](https://community.hubitat.com/t/11105/12), [chuck.schwer](https://community.hubitat.com/t/11105/19))*; events are processed from that queue, so other activity delays an attribute update *(staff: [bravenel](https://community.hubitat.com/t/118754/23))*.
- **Events sent by a failed execution are delivered.** A driver command that sent an event and then threw: default and `filterEvents: false` subscribers received the event, `currentValue` read it and the error was logged on the device. An app that sent a location event and then threw: its subscriber received it *(probed 2.5.2.135, C-8 Pro, throwaway app and driver)*.
- **Where code runs, and how much at once.** Page renders, Done saves, button handlers, app endpoints (`mappings`), `/device/runmethod` and Maker API commands run on the HTTP request that triggered them, and the reply waits for the method. LAN messages to port 39501 reach `parse()` the same way. Scheduled handlers run at most 30 at a time and device and location event handlers at most 40 at a time. Async HTTP callbacks run apart from both. A call between a parent and its child runs on the caller's thread, inside the caller's execution *(probed 2.5.2.135, C-8 Pro, throwaway app and driver)*. Long handlers therefore hold a slot that other apps' scheduled jobs or event handlers wait for.

## Platform behavior

- **`sendEvent()` dedup.** Default subscribers get state changes only and `filterEvents: false` subscribers get every call *(docs: on-hub app-subscriptions; regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*. Not documented: `device.lastActivity` updates on every `sendEvent()` call, dedup'd or not: an unchanged value moves `lastActivityTime` in `fullJson` and leaves the attribute's `date` alone *(regression 2.5.2.135–2.5.3.102, apps/tests/test-architecture-claims.sh)*, and with a `filterEvents: false` subscriber every repeat is also stored in the event history *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*. So dedup is a UI/default-subscriber convenience, not a "device didn't communicate" signal. **In drivers, call `sendEvent` on every device report; don't suppress driver-side, and don't override with `isStateChange: true`.** Suppression hides the call from `filterEvents:false` subscribers; forcing `isStateChange:true` removes default subscribers' opt-in to dedup. Apply any value smoothing to the *value* being emitted, not to whether the event fires. Prefer `sendEvent` over `createEvent` *(staff: [mike.maxwell](https://community.hubitat.com/t/not-understanding-sendevent/2326/2))*: returning a `List` of `createEvent` maps from `parse()` leaves the event's **"Produced by" column empty** in device logs, whereas a direct `sendEvent()` attributes the event to the device: the `createEvent` row's `producedBy` in `/device/eventsJson` was empty and the `sendEvent` row's was the device link *(probed 2.5.2.135, throwaway LAN driver)*.
- **`state` vs `atomicState`.** The commit timing is [documented](https://docs2.hubitat.com/en/developer/app/overview). Not documented: mid-method, another request reads the new `atomicState` value and the old `state` value, and a handler that throws keeps its `atomicState` writes and loses its `state` writes *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*.
- **A handler gets exactly what the platform has for it.** A `subscribe` handler gets the event; a `runIn`, `runOnce` or `schedule` handler gets the `data` map (a `groovy.json.internal.LazyMap`, so a JSON round trip of what was passed) or nothing when it was scheduled without data. The call is plain Groovy dispatch: a handler with one parameter and no data gets null, a handler with a default parameter (`def h(evt = null)`) works either way, and a handler with no parameter given an event or data, or one with two parameters given one, fails. The error is logged as `org.codehaus.groovy.runtime.metaclass.MissingMethodExceptionNoStack: No signature of method: java.lang.String.call() is applicable for argument types: (com.hubitat.hub.domain.Event) values: [...]`, for a job `(groovy.json.internal.LazyMap)` or `()`. `subscribe()` accepts a handler name the script lacks; the event then logs `No signature of method: <script class>.noSuchHandler() is applicable for argument types: (com.hubitat.hub.domain.Event) values: [...] (noSuchHandler)` *(probed 2.5.2.135, C-8 Pro, throwaway app)*.
- **Subscribing again.** `subscribe(dev, attr, handler)` repeated with the same device, attribute and handler keeps the first subscription and ignores the rest, options included: `filterEvents: false` after a default one left a repeat of the value undelivered, and a default one after `filterEvents: false` left it delivered. Two handlers on one attribute both run. `subscribe()` with an unset device input, with a multiple input nobody filled in or with `[]` throws nothing and subscribes to nothing *(probed 2.5.2.135, C-8 Pro, throwaway app)*.
- **Deleting a device takes it out of the device inputs of apps.** A single device input reads null once its device is gone. A multiple one reads the devices left, and null once none is left. In `statusJson` the setting's row stays, with `value` null and the deleted id missing from `deviceIdsForDeviceList` *(probed 2.5.2.135, C-8 Pro, throwaway app and virtual devices)*.
- **In-place changes to `state` collections persist; in-place changes to `atomicState` collections never do.** Checked in an app and a driver, from a command or button, a scheduled handler and an async callback. Every `state` shape persisted: nested maps, a local alias of a `state` collection, `List` additions and removals, `sort()`, `clear()`, `putAll()` and a change right after `state.m = [...]` in the same method. Every `atomicState` shape was lost, every time: `atomicState.m.k = v`, `atomicState.l << v`, a local alias of an `atomicState` map, nested writes. `atomicState` hands back a copy, so write the whole value back, or in an app use `atomicState.updateMapValue(key, mapKey, value)`, which works; drivers throw `MissingMethodException` for it *(probed 2.5.2.134, throwaway app and driver)*. In an app, removing through `atomicState.keySet().remove(k)`, `entrySet().removeIf(...)` or `values().remove(v)`, or editing a nested map read from `atomicState`, changes the current execution's view only: the next execution sees the old values. `atomicState.putAll(...)` persists *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway app; docs: on-hub api-com-hubitat-hub-appatomicstate)*. Hubitat staff confirmed the `atomicState` behavior and said plain `state` works *(staff: [bravenel 2020](https://community.hubitat.com/t/dynamic-variable-error/54285/12), [mike.maxwell 2021](https://community.hubitat.com/t/atomicstate-array-operations/62242/2), [bravenel 2024](https://community.hubitat.com/t/atomicstate-doesnt-seem-to-update/132831/3))*.
- **Map keys come back as Strings.** `state.h[555L] = v` saves under `"555"`; on the next run `state.h[555L]` is null and `state.h["555"]` finds it. A map keyed by a numeric device or app id looks like it lost its entries after a reload, so key such maps by `id.toString()` *(probed 2.5.2.134, throwaway app and driver)*.
- **An `atomicState` write costs in proportion to the app's whole state, not the key written.** A small integer key took 0.2 ms per write with no other state, 4 ms with an unrelated 10 KB key present and 175 to 205 ms with 500 KB, about 0.35 ms per KB per write. `atomicState` reads and in-loop `state` writes stayed near 0 ms at every size. Keep large or dead data out of an app that writes `atomicState` often, and never use `atomicState` to pass data between methods of one execution *(probed 2.5.2.134, throwaway app)*.
- `remove(key)` returning the removed value is documented for `atomicState` (on-hub `api-com-hubitat-hub-appatomicstate`); plain `state.remove(key)` does the same, in apps and in drivers, so `String v = state.remove("k")` reads and clears in one step *(probed 2.5.2.129, throwaway app and driver)*.
- Concurrent async callbacks in an app without `singleThreaded` race on read-modify-write: 20 callbacks each adding a key to one shared map kept about 5 of 20 in `state` and about 15 of 20 in `atomicState`. Separate top-level `state` keys kept all 20, and with `singleThreaded: true` every form kept all 20. A `@Field static` `ConcurrentHashMap` keyed by instance, an `AtomicInteger` completion count and one `state` write when the last callback arrives kept 20/20 *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*. `computeIfAbsent` with a closure cast to `java.util.function.Function` runs in the sandbox, in apps and drivers *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh, app side only)*.
- **Separate top-level `state` keys protect apps, mostly, and drivers not at all.** With 20 concurrent callbacks, in an app separate keys kept all 20 in 6 of 7 runs and 18 once, while one shared map kept 14 to 17; with `singleThreaded: true` both kept all 20. In a driver, separate keys lost exactly as many as the shared map, so the whole store behaves as one object written back per execution *(probed 2.5.2.134, throwaway app and driver)*.
- **In a driver, a method that uses `state` overwrites the whole store when it ends.** `state` and `atomicState` are one store in a driver (each sees the other's keys). `atomicState` writes reach the store at once *(docs: on-hub api-com-hubitat-hub-deviceatomicstate)*. `state` writes are deferred: the method's `state` map, loaded at its first `state` access, is saved back whole when the method ends and replaces the store. A method that writes `atomicState.a`, then `state.b`, then `atomicState.c` shows `a` and `c` in `fullJson` `deviceState` while it runs (`b` absent) and ends with `a` and `b`: `c` is overwritten (5 of 5 runs on 2.5.2.134, 10 of 10 on 2.5.2.135 and 2.5.3.102), and so are `atomicState.putAll(...)` and `atomicState.remove(...)` made after the first `state` access. The save also overwrites `atomicState` writes made by other executions while the method ran: a counter that preference renders raised from 8 to 11 during the method was back at 8 afterwards *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver)*. The same sequence in an app keeps all three (5 of 5). In a driver, don't mix the two in one method, and for a flag the driver's other threads must see at once, use a `@Field static` concurrent map keyed by `device.id` *(probed 2.5.2.134–2.5.3.102, throwaway app and driver)*.
- **In an app, `state` and `atomicState` are also one keyspace.** A key written through one is read through the other in the next execution, and `statusJson` `appState[]` lists one row per key with no marker for which store wrote it. Within an execution, an `atomicState` write also updates `state`, but a `state` write stays local until the method ends: `state.k = 1; atomicState.k = 2` reads 2 through both and saves 2, while `atomicState.k = 2; state.k = 1` reads 1 through `state` and 2 through `atomicState`, then saves 1 when `state` commits *(probed 2.5.2.135, throwaway app, one run)*.
- **What `singleThreaded: true` covers** (the [definition docs](https://docs2.hubitat.com/en/developer/app/definition) say "top level" methods). It serializes per instance: two instances of the same type ran in parallel. Within one instance no two executions overlapped, for every pair of entry points: app endpoints (over loopback or the hub's LAN IP), scheduled handlers, async callbacks, device and location events, child device and child app calls into the parent, button handlers, page renders and `updated()`; driver commands from an app or over HTTP, scheduled handlers, callbacks, LAN `parse()` and child calls into the parent. A waiting call started a few milliseconds after the running one ended. Without the flag every pair overlapped *(regression 2.5.1.183, C-7, and 2.5.2.129, C-8 Pro, apps/tests/test-singlethreaded.sh, the child call, endpoint and driver command pairs again on 2.5.2.133)*. A child's `parent.childWork()` call blocked until the running call finished, whether that call held by `pauseExecution`, a busy loop or a blocking HTTP call; this held for child devices and child apps calling an app parent and for a child device calling a driver parent *(regression 2.5.2.133, apps/tests/test-singlethreaded.sh)*. A Hubitat staff forum post says `singleThreaded` on a parent does not serialize simultaneous child-to-parent calls *(staff: [gopher.ny](https://community.hubitat.com/t/166528/7))*. Treat the serialization as observed behaviour, not a documented guarantee. Radio `parse()`, Maker API commands, cloud-relay requests and cron `schedule()` are not measured.
- Concurrent identical GETs to an app endpoint share one execution: a request that arrives while one with the same path and query is running does not run the handler, and gets that run's response. This holds across clients (different source IP or headers) and with or without `singleThreaded`. Requests that don't overlap run separately. Tests that fire concurrent requests need a unique query parameter per call, and logs or counters show fewer executions than requests *(probed 2.5.1.183, C-7, and 2.5.2.129, C-8 Pro)*.
- An app that writes device attributes and also subscribes to them (setpoints it sends to a thermostat) needs `singleThreaded: true`. Without it, the event echoing the app's own write ran in parallel with the handler that sent it, before that handler's `state` commit, so the app took its own write for a change made by someone else, and the two handlers overwrote each other's `state` *(probed 2.5.2.129)*.
- **An event is not readable the moment it is sent.** After `sendEvent(name: "switch", value: "on")` in a driver, `device.currentValue("switch", true)` on the next line still returned the old value, and 1 s later (same execution) the new one; the same held for an app sending an event on its child device. Events go through a queue (see `getPendingEventsCounter()` below), so read back what you sent from your own variable, not from the device. The window is under a millisecond: a read right after the call returned the old value in about 398 of 400 runs from an app and 400 of 400 from inside the driver, and about 1 ms of any work or `pauseExecution(1)` gave the new one. After a driver command called from an app, the app's next line read the new value in 400 of 400 runs. A load of about 40 requests per second stretched the window only slightly *(probed 2.5.2.135, C-8 Pro, throwaway app and driver, 200 to 400 runs per cell, idle and under load)*.
- **`currentValue()` of a `number` attribute** returns a BigDecimal made from the stored text (`"5.50"` gives 5.50, `"1e3"` gives `1E+3`, `"007"` gives 7) and null when the text is not a number (`abc`, `true`). The same device's `currentState(attr).value` stays the String, and its `numberValue` throws `NumberFormatException` for text. A `string` or `enum` attribute reads as the String *(probed 2.5.2.135, C-8 Pro, throwaway app and driver)*.
- **A device wrapper keeps the first value it read of each attribute, in apps and drivers.** `currentValue(attr)`, `currentState(attr)`, `latestValue(attr)` and the `currentAttr` shorthand share one cache per wrapper and attribute. The first read fills it and it holds for the rest of the execution: when the first read came right after a `sendEvent` (so it was old), a plain read 100 ms later was old again through every accessor. `currentValue(attr, true)`, `currentState(attr, true)`, `latestValue(attr, true)` and the `currentStates` list gave the new value. A read made before the event is cached too, and a `skipCache` read refreshes the cache. The cache belongs to the wrapper object, not the device: with the device selected in two inputs, a read through the second input was new while the first still returned the old value (a wrapper from a new `getChildDevice()` does the same). To see what an execution just changed, read with `skipCache` true or in the next execution *(probed 2.5.2.135, C-8 Pro, throwaway app and driver, 91 combinations in three rounds)*.
- **Two events on one attribute less than a millisecond apart can lose the second.** A driver command sent `X` then `Y` (both changes) with no pause: every run delivered both events, in the order sent, but the current value stayed `X` in about 3% of idle runs (6% under load) and the handler ran for `Y` before `X` in 16 to 19%. With a 1 to 2 ms gap the value never stuck on `X`, but the handlers still ran in the other order in 9 to 20% of runs; from 5 ms apart they start in the order sent. When the second value was the value before the first (`BASE`, `X`, `BASE`), the second event was dropped in about a third of runs: the hub compares an event with the state already applied, not the value the caller last read and not a value still waiting. So setting an attribute and setting it back within a millisecond can lose the second event, and a repeat sent while the same value still waits can be stored and delivered twice (`B`, `B` back to back stored `B` twice in 7 of 10 runs). After a value is queued, sending the attribute back to its applied value drops it when it is the command's only event, but keeps it when another event of the device comes first in the same command, and the event history then shows it before that other event, though it was sent after. Sending the command over `/device/runmethod` gave the same pattern *(probed 2.5.2.135, C-8 Pro, throwaway app and driver, 200 runs per cell)*.
- **Handler start and scheduling are a few milliseconds late.** An event reached its subscriber's first line in 7 to 8 ms at the median; `runIn` and `runInMillis` handlers started about 8 ms late at the median and never early, with the occasional stall of over a second. A load of about 40 requests a second left the medians unchanged *(probed 2.5.2.135, C-8 Pro, throwaway app and driver)*.
- Empty event values are documented as ignored (`Event.populateValues`) *(docs: on-hub api-com-hubitat-hub-domain-event)*. That holds for `null` too, and even with `isStateChange: true`, so an attribute cannot be cleared through `sendEvent`. Publish a sentinel value such as `none`, or call `deleteCurrentState(name)` on the device; Maker API then reports the attribute as `null` *(probed 2.5.2.129)*.
- `device.lastActivity` advancing on dedup'd events holds for component children too: a parent calling `child.parse([[name: "switch", value: "on"]])` with an unchanged value advanced the child's `lastActivity` while the `switch` state date stayed put. A state date is never newer than `lastActivity`, so taking `max(currentStates.date, lastActivity)` adds nothing *(probed 2.5.2.135, throwaway parent app and component child)*.
- An app instance that has never been saved with Done (e.g. created over the API) runs button handlers but not scheduled jobs: its `runIn` calls are silently dropped: a `runIn(2, ...)` set in a button handler had not run 8 s later *(regression 2.5.2.135–2.5.3.102, apps/tests/test-architecture-claims.sh)*. Finish setup with a Done POST, or have the page render collect async results.
- **Code push does NOT trigger `updated()`**: pushing new source code takes effect immediately, but does not call `updated()`/`initialize()`. Subscriptions and `state` from the old code persist *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*. Re-save the app's preferences to trigger a clean re-init.
- `@Field static` behaves as [documented](https://docs2.hubitat.com/en/developer/best-practices): shared by every instance of the type and reset by a code push *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*. Key per-instance entries by `app.id`.
- A top-level variable declared without `@Field` (`String X = "top"`) reads as `null` inside methods, with no error *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*.
- A `DeviceWrapper` stored in `state` works within the same call; on the next call it comes back as a plain `java.util.HashMap` of device properties, and methods such as `getLabel()` throw `MissingMethodException` *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*. Store device IDs.
- Bare (undeclared, no `def`) variable assignments inside a command method write to the script binding but do **not** persist across separate command invocations *(probed 2.5.0.143, via `/device/runmethod` and Maker API)*. Each invocation gets a fresh binding: a bare write in call A is gone by call B, and a bare read then falls through to `settings.<name>` (for preference-named vars) or `null` (for non-preference names). So the common driver idiom of assigning per-message values to bare names (e.g. `priority = customPriority` in a notification driver) does **not** leak state between messages on current firmware, but it relies on undocumented instance lifecycle, so prefer `def`-declared locals and explicit `settings.*` reads. Within a single invocation, bare write-then-read works (and shadows `settings`).
- Same-device events fired less than 1 s apart were not lost: a driver sending the same attribute twice, each a change, from two executions 65 ms to 1.05 s apart lost nothing in 1600 runs (both events reached the subscriber and the later value was the current state), so coalescing is not reproduced for `sendEvent` (Maker API commands were not tested) *(probed 2.5.2.135, C-8 Pro, throwaway app and driver)*. Commands sent back to back over Maker API or `/device/runmethod`, each after the previous reply, arrived in order and both events reached a subscriber in 400 of 400 pairs *(probed 2.5.2.135, C-8 Pro, throwaway app, Maker API instance and Virtual Contact Sensor)*. Two events less than 1 ms apart in one driver execution behave differently, as the bullet on events less than a millisecond apart says.
- `runIn` / `schedule` overwrite a same-name job by default, as documented (on-hub `shared-scheduling`) *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*.
- The async HTTP call pool is capped at 8 concurrent calls per app, and the HTTP client allows at most 5 concurrent connections to one destination host and port. With 20 `asynchttpGet` calls spread over four destinations, 8 were in flight at once; aimed at one destination, 5. The rest queued and all 20 completed, none lost *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*. Per-device drilling at scale still serializes behind the pool; batch or rate-limit. The 5 matches the default per-route pool of Apache HttpClient 5, which the hub has used for outbound HTTP since 2.5.1.x, so it is most likely the library default rather than a Hubitat setting *(inferred from the HttpClient 5 default, which Hubitat does not document)*. Firmware before 2.5.1.x ran HttpClient 4.5, whose default was 2 per route; whether older hubs were limited to 2 is unverified. **The `timeout` covers the wait for a connection.** Eight `asynchttpGet` calls with `timeout: 15` to a host that never answers all called back 15.0 to 15.2 s after dispatch: the five that got a connection with "connect timed out", the three still queued with "Timeout deadline: 15000 MILLISECONDS". So a queued call never runs longer than its timeout from dispatch. Keeping 8 calls in flight against the hub's own `/device/fullJson` was no slower than 5 *(probed 2.5.2.134, throwaway app)*.
- `location.hub` and `location.hubs[0]` are `com.hubitat.hub.domain.Hub`, the importable type. `com.hubitat.app.HubWrapper`, `com.hubitat.app.HubInfo` and `com.hubitat.app.LocationWrapper` do not resolve *(probed 2.5.2.129, throwaway app)*.
- `getPendingEventsCounter()` is documented (on-hub `shared-utilities`); the cap is not. At about 512 pending events `sendEvent` throws `com.hubitat.app.exception.LimitExceededException` ("Too many events pending processing"), and pending events carry across executions *(probed 2.5.2.125)*. Each device has its own queue. Up to 2 events sent back to back are applied at once; when more are waiting, 2 more are applied every 100 ms, so 18 queued events took about 0.9 s and a burst of a few hundred stalls that device's events for seconds. An event on another device is applied at once. Repeated values that are not state changes, with no `filterEvents: false` subscriber, are not queued. 600 back-to-back events threw `LimitExceededException` ("Too many events pending processing for device N"). `getPendingEventsCounter()` itself is slow, about 0.1 to 0.2 ms per call *(probed 2.5.2.135, C-8 Pro, throwaway app and driver)*. If the throw happens inside a self-rescheduling `runIn` body, the reschedule never runs and the chain dies silently: the app looks alive but its sweep is dead *(probed firmware not recorded, an app emitting from a 10 s `runIn` loop)*. In periodic sweeps emit only the attribute that changed, cap work per tick, and coalesce repeated same-attribute writes.
- A full queue makes even an unchanged-value `sendEvent` throw "Too many events pending processing" *(probed 2.5.2.139, C-8 Pro, throwaway driver)*. An unchanged `sendEvent` costs about 0.4 ms in the calling driver, and a changed one about the same to enqueue; applying it is billed to the device, not the caller *(probed 2.5.2.139, C-8 Pro, throwaway app and driver)*. A call from an app into one of its child devices costs about 2.5 ms even when the method does nothing *(probed 2.5.2.139, C-8 Pro)*.
- A second `LimitExceededException`, "App N generates excessive hub load" (or "Device N …" for a device), throttles one app or device as a whole. Hubitat added it to keep one app from starving the hub: one app can take 100 % of one core on a 4-core hub, and the radio may start dropping messages at about 200 % load *(staff: [gopher.ny](https://community.hubitat.com/t/135185/13))*.
  - **What trips it:** the app's or device's run time as a share of uptime since boot, the `/logs/json` `pctTotal` figure, passing the hub's threshold. `GET /hub/advanced/getExcessiveLoadThreshold` answers `33`. A throwaway app tripped it when its share reached 33.2 %, after running at 75 % busy for 2 min and then at 90 % busy for 19 min on a hub that had been up 36 min. Executions of up to 12 s every 20 s did not trip it *(probed 2.5.3.103, C-8 Pro)*. It counts "the time spent in calls made by app/driver (possibly including its parent)" *(staff: [gopher.ny](https://community.hubitat.com/t/135185/10))*.
  - **The 15-minute grace:** it is never thrown in the first 15 minutes after boot *(staff: [gopher.ny](https://community.hubitat.com/t/135185/10))*. An app at about 88 % of uptime from the first minute after a reboot tripped it 14 min 59 s after boot *(probed 2.5.2.139, C-8 Pro, throwaway app with a child device)*.
  - **What throws:** platform calls that produce an event, such as `sendEvent` in the app's child devices (the trace names the child's line) and `setGlobalVar` *(probed 2.5.2.139–2.5.3.103, C-8 Pro; staff: [gopher.ny](https://community.hubitat.com/t/135185/15))*. Staff said the hub then refuses to process events for the app *(staff: [gopher.ny](https://community.hubitat.com/t/135185/10); false 2.5.2.139)*. On 2.5.2.139 a tripped app's subscribed event handler, `runIn`, `runEvery1Minute` and `runInMillis` methods, and app buttons all kept running; only the event-producing calls threw *(probed 2.5.2.139, C-8 Pro, throwaway app)*.
  - **How it clears:** staff said only a reboot clears it *(staff: [gopher.ny](https://community.hubitat.com/t/135185/8); false 2.5.2.139)*. It clears by itself once the share falls back to the threshold: an app that stopped burning after its trip kept throwing until its share was about 33.6 %, then its next `sendEvent`, at about 33.4 %, succeeded, 24 min after the trip *(probed 2.5.2.139, C-8 Pro)*. An integration that tripped it after a slow post-update boot recovered on its next poll *(probed 2.5.3.103, C-8 Pro)*.
  - **Apps and their child devices:** a child device's own run time counts against the device, not its parent app. A child that burned about 90 % on its own schedule tripped "Device N generates excessive hub load" at a device share of about 86 % while the parent app was at about 2 %, and `sendEvent` calls the parent made through that child kept succeeding *(probed 2.5.2.139, C-8 Pro, throwaway app with a child device)*.
  - **Changing the threshold:** `GET /hub/advanced/setExcessiveLoadThreshold/{n}` takes 20 to 100 and applies only after a reboot; the value survives reboots. At 100 an app at about 88 % of uptime ran 17 min past boot without a trip *(probed 2.5.2.139, C-8 Pro)*. The endpoint's replies are in the internal API reference.
  - Because the share is cumulative, it catches slow work early in uptime and gets far more lenient as uptime grows: on a hub up for weeks, a runaway app needs far more run time before it trips *(inferred: from the cumulative share)*.
- **Reboot and scheduled jobs** *(regression 2.5.2.128, over two reboots, apps/tests/test-architecture-claims.sh --reboot)*: a far-future `runIn` survives; a repeating `schedule` resumes about a minute into uptime with one catch-up run about 10 s after the first, then keeps its cadence; a one-shot `runIn` that fell due while the hub was down never ran and was gone from the app's job list. `systemStart` reached a subscriber at about 115 s of uptime, after the first cron ticks.
- **Driver switch:** changing a device's driver calls the new driver's `deviceTypeUpdated()`, keeps the device's data values (`updateDataValue`), and **clears its `state`** *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*. It also removes the device's scheduled jobs: a one-shot `runIn` and a cron schedule set by the old driver were gone afterwards (`fullJson` `scheduledJobs` null, the cron never fired in 75 s). Only `deviceTypeUpdated()` runs on the new driver; `installed()`, `updated()`, `configure()` and `initialize()` do not, also when the new driver declares the `Initialize` capability *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway drivers; docs: on-hub driver-definition)*. A code push to the device's own driver is not a driver change: `state` and a pending `runIn` job survive and `deviceTypeUpdated()` does not run *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver; docs: on-hub driver-definition)*. The 2.5.3 on-hub reference documents `deviceTypeUpdated()` *(docs: on-hub driver-definition)*; the 2.5.2.134 reference text had no mention of it *(absent 2.5.2.134, on-hub reference text searched for `deviceTypeUpdated`)*. The [Zigbee driver guide](https://docs2.hubitat.com/en/developer/driver/building-a-zigbee-driver) says "nothing happens on its own as a result of a driver change" *(docs: [Zigbee driver guide](https://docs2.hubitat.com/en/developer/driver/building-a-zigbee-driver))*: that holds for `configure()`, `installed()` and `updated()`, which the hub does not call, but not for `deviceTypeUpdated()` *(regression 2.5.2.135–2.5.3.102, apps/tests/test-architecture-claims.sh)*. The new driver's commands show in `fullJson` at once *(probed 2.5.2.135, throwaway drivers switched A to B to A)*.
- `updated()` runs on Done, as [documented](https://docs2.hubitat.com/en/developer/app/overview). Subscriptions created in it **survive a code push** (a push does not re-run `initialize()`) *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*, and a device input assigned on a **sub-page** saves the setting but does not arm its subscription until a Done runs `initialize()`: a sub-page save without Done stored the device with no subscription and no `updated()` call, and the next Done on the main page armed it *(probed 2.5.2.135, throwaway app)*. So a freshly-pushed or sub-page-configured app whose subscription isn't firing almost always never ran `initialize()` with that setting present; the subscription was not dropped.
- `subscriptionData` (on-hub `app-subscriptions`) also works on location-event subscriptions, and `evt.subscriptionData` and `evt.getSubscriptionData()` both return it *(probed 2.5.2.129, throwaway app)*.
- A firmware update downloads the image into memory before applying, transiently dropping `freeMemory` (into single-digit MB on an otherwise healthy hub). A low `freeMemory` sample taken shortly after a `/hub/eventsJson` `name=update` event is that download, not a leak *(inferred from one 5.89 MB `freeMemory` reading taken minutes after an update to 2.5.0.140 was started)*.

## What a code save runs

- **A save runs the static pages too.** Saving an app runs `definition()`, the `preferences` block and the body of every static page (`page(name: ...) { ... }`), so a static page that throws rejects the save. The reply carries the exception's message and the line of the top-level statement, with the script named `Script1`: `No signature of method: Script1.nosuchMethodProbe() is applicable for argument types: () values: [] on line <span id='errorLine'>2</span>`, where line 2 is the `preferences {` line. Page methods (`dynamicPage`) are not run at save *(probed 2.5.2.135, throwaway apps and drivers)*.
- **What that code sees.** In an app save, `settings` is null (a static page reading `settings.x` fails the save with `Cannot get property 'x' on null object`; use `settings?.x`), while `state` is an empty map and `location`, `app`, `log` and `now()` work (`atomicState` is null). The `app` object is an `InstalledAppWrapper` whose `id`, `label`, `name`, `installed`, `appTypeId` and `parentAppId` read null, `getInstallationState()` gives `INCOMPLETE`, and `getChildApps()` and `getChildDevices()` give `[]`; it reads the same at the first save of an app and at a later save of an existing one. In a driver save, `state` is an empty map, `location` works (`location.temperatureScale` reads the hub's scale), and `device` and `settings` are null *(probed 2.5.2.135, throwaway apps and drivers)*.
- **Driver preferences are evaluated per device.** The `preferences` block runs again for each device, with that device's `state` and `device` bound: a title built from `state.flag` changed after a command set the flag, and an input inside `if (state?.flag)` appeared on that device only. *(probed 2.5.2.135, throwaway driver)*.
- **An app can replace its own code while it runs.** An app that posted its own new source to `/app/ajax/update` over loopback got `success`, and the running invocation went on executing the old code to the end: the old `@Field static final` value, and closures it had not called before the save (400 of them in a 146k-character app) loaded without error, even after a loopback GET of the app's page had already rendered the new version. A `runIn()` scheduled by the old code ran the new code. So the `NoClassDefFoundError` on a closure class some apps hit when updating themselves needs some other condition, not reproduced here *(probed 2.5.2.135, throwaway app)*.

## Errors in app and driver code

What app and driver code sees when it fails; the HTTP side is in [internal APIs](hubitat-internal-apis.md) (App configuration):

- An uncaught exception is logged once at `error` level as `<class>: <message> on line <N> (method <name>)`, N being the line that threw in the app's source. A page method's error names the page method; a static page body's error says `(method run)` *(probed 2.5.2.135, throwaway apps and drivers)*.
- When `installed()` throws on the first Done, the instance is installed anyway. Its `state` writes are dropped and its `atomicState` writes kept, and so are the `subscribe()` and `runIn()` calls it made before the throw. A driver's `installed()` that throws leaves the device created, with the driver's `state` writes dropped *(probed 2.5.2.135, throwaway apps and drivers)*.
- A device property that does not exist reads null: `device.typeId`, `device.room` and `device.nosuchProp` throw nothing. So does `device.currentNosuch` *(probed 2.5.2.135, throwaway apps and drivers)*.

## Rooms, device and app lookups, event history

Read back on a C-8 Pro with a throwaway app and driver; they gave the same results wherever both can call a method:

- **`getRooms()`** works in apps and drivers and takes no argument (`getRooms(1)` throws `MissingMethodException`). It returns an `ArrayList` of `LinkedHashMap` with `id` (Long), `name` (String) and `deviceIds` (`ArrayList` of Long); `[]` when there are no rooms, and "Devices without room" is not an entry. Rooms come sorted by name ignoring case (`aaa` before `Room A`), not by id. `deviceIds` is neither the order the room was saved in nor id order: it follows the iteration order of a Java `HashSet<Long>`, so ids 702 to 705, 711 and 712 come back as 704, 705, 711, 712, 702, 703 whatever order was saved. Sort it when order matters *(probed 2.5.2.135, C-8 Pro, throwaway app and driver; inferred: the order matched HashSet iteration in four trials)*. Child devices are included, and a device is in one room: saving it into a second room takes it out of the first *(probed 2.5.2.135, C-8 Pro, throwaway app and driver; docs: on-hub shared-utilities)*.
- **A device's room.** `getRoomName()` (or `roomName`) is a String or null, `getRoomId()` (or `roomId`) a Long or null, for apps and drivers. With no room, `/device/fullJson/{id}` has `roomId` and `roomName` null and `roomAssigned` false, and `/hub2/devicesList` has `roomId` null and `roomName` `""`. Deleting a room leaves its devices with no room *(probed 2.5.2.135, C-8 Pro, throwaway app and driver)*.
- **`getAppsUsingDevice(id)`** is an app method; a driver gets `MissingMethodException`. It takes a Long or an Integer (a String throws `MissingMethodException`) and returns an `ArrayList` of app objects, `[]` for an unknown id, null or no argument. Each has `id` (Long), `name` (the app type's name), `label`, `trueLabel` (null unless relabelled), `disabled` and `installed` (Boolean), `parentAppId` (Long or null), `appTypeId` and `appType`. The namespace is on `appType.namespace` (`"hubitat"` for a built-in app), not on the app. The list holds child apps, built-in apps, disabled apps (`disabled` true) and Easy Mobile Dashboard apps ("All Devices" always, plus "Devices without room" or the dashboard of the device's room; which of those two appears does not follow a room change at once). It is sorted by `label`, case-sensitive (`B` before `b`); apps with the same label come in no fixed order. `appsUsing` in `/device/fullJson/{id}` leaves the dashboards out and lists newest app id first with `id`, `name`, `label`, `trueLabel` and `disabled` *(probed 2.5.2.135, C-8 Pro, throwaway app and driver)*.
- **Dashboards do not follow a room change at once.** After `POST /room/save` put a virtual device in a new room, the device's `roomId` and `getRoomName()` changed immediately, but `getAppsUsingDevice(id)` kept listing `Devices without room` (and `All Devices`) instead of the room's dashboard in every poll for 12 minutes; the same held for 2 minutes after the device moved to a second room and after that room was deleted *(probed 2.5.2.135, C-8 Pro, throwaway app and virtual device)*. An app that decides from this list which dashboards show a device should not expect the list to change when it moves the device.
- **`getAppByAppId(id)`** is an app method too. It takes a Long or Integer (a String throws `MissingMethodException`) and returns the same app object for a child app, a built-in app, a disabled app, a dashboard and the dashboard parent, or null for an unknown id, null or no argument. The `app` wrapper itself reads `disabled`, `installed`, `appType` and `singleThreaded` as null; `getAppByAppId(app.id)` has them *(probed 2.5.2.135, C-8 Pro, throwaway app)*.
- **`getDevicesByIds(ids)`** is an app method. It takes a List of Long (Integers work) and returns an `ArrayList` of device wrappers in the order of the list, with repeated ids repeated. An empty list, null or no argument gives `[]`. One unknown id, or a null element, throws `IllegalArgumentException` (`missing device parameter`) with no partial result. A list of Strings, a single Long and a Set throw `MissingMethodException` *(probed 2.5.2.135, C-8 Pro, throwaway app)*.
- **`device.eventsSince(Date since[, Map options])`** returns a List of events, newest first, whose `date` is strictly later than `since`: an event dated exactly `since` is left out. Without options it returns at most 10. `[max: n]` returns the newest n; `max: 0` gives 10 like no option. A negative `max` throws `RuntimeException` (an SQL error), a String `max` throws `MissingMethodException`, and a null or empty map or an unknown key act as no options. `eventsSince(null)` and a future date return `[]`, a long throws `IllegalArgumentException` and no argument throws `MethodSelectionException` *(probed 2.5.2.135, C-8 Pro, throwaway app and driver)*.
- **`device.statesSince(String attribute, Date since[, Map options])`** returns states newest first, strictly later than `since`, at most 10 without options. `max` limits the attribute's newest n states first and the date filter applies to those, so `max: 3` can return fewer than 3 while older ones would qualify. An unknown attribute gives `[]`; a null attribute or a null date returns null, not a list; a missing date throws `IllegalArgumentException`; a negative `max` throws `RuntimeException`. A state exists for each stored event of a declared attribute; an attribute not declared in the driver has events and no states *(probed 2.5.2.135, C-8 Pro, throwaway app and driver)*.
- **What is stored.** A repeat of the current value and a null value are not stored (see `sendEvent()` dedup above). Every stored event reads `isStateChange` true, also one sent with `isStateChange: false` and a new value. `value` is always a String (`5` stores `"5"`), made as Java prints the value: a BigDecimal keeps its scale (`5.50`), a Double is `1.0E10` for ten billion, a List is `[1, 2]` and a Map is `{a=1}`, not Groovy's `[a:1]`. An event sent with `isStateChange: true` and the current value is stored and reaches default subscribers, with `isStateChange` true. `unit`, `type` (`"physical"`, `"digital"` or null) and `descriptionText` come back as sent, `source` is `"DEVICE"` and `date` a `Date`. A Map passed as `data` comes back in `data` as Groovy text (`[a:1, b:[1, 2]]`) with `jsonData` null; a String comes back in `data` and `dataString`; with no data `data` is null and `jsonData` an empty HashMap. On an event `numberValue` is a Long, a Double or null for text and `integerValue` is 0 for a fraction or for text; on a state, `numberValue` is a BigDecimal and `numberValue` and `doubleValue` throw `NumberFormatException` for text. The device's event maximum is not enforced at once (20 events stayed stored with a maximum of 11) *(probed 2.5.2.135, C-8 Pro, throwaway app and driver)*.
- **Attribute types and event keys that do nothing.** `attribute "a", "number"`, `"NUMBER"` and `"Number"` all show `dataType` NUMBER in `fullJson`, and `currentValue` returns a BigDecimal (`5.50`); `"json_object"` shows JSON_OBJECT and reads a String. The event-map keys `stateChange`, `isStateChanged`, `display` and `archivable` are ignored: a repeated value sent with each was not stored, and only `isStateChange: true` stored the repeat. `displayed: false` does not stop an event being stored (it is stored with `isStateChange` true). A `createEvent(...)` whose result is discarded sends nothing: no event and no current state *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver)*.

## Time, JSON and hex helpers

Read back with the location in a UTC−5 zone with daylight saving time:

- `timeToday(s)` accepts `"H:mm"`, `"HH:mm"` and a full date-time; for a date-time it takes the wall-clock time as written and ignores the offset (`"2026-03-08T02:30:00.000-0500"` gives today 02:30 local). Seconds are zeroed, and `"08:00:30"` throws `ParseException`. With a `TimeZone` argument the result is that time today in that zone *(probed 2.5.2.135, throwaway app)*.
- `toDateTime(s)` accepts `yyyy-MM-dd'T'HH:mm:ss.SSSZ` (with `-0400`, `+0000` or `Z`), the same with `-04:00`, with or without milliseconds, and a bare `yyyy-MM-dd` (midnight in the location's zone). It throws `ParseException` (`Unparseable date: "..."`) for a date-time without a zone, a missing seconds field, a space instead of `T` and `"14:00"` *(probed 2.5.2.135, throwaway app)*.
- `parseJson(s)` behaves as `groovy.json.JsonSlurperClassic`: a HashMap or ArrayList with Integer, Long and BigDecimal numbers; `JsonException` (`Lexing failed on line: 1, column: 2, ...`) for bad JSON or a `//` comment; `IllegalArgumentException` for null or empty text; `NullPointerException` for a bare scalar such as `"5"` *(probed 2.5.2.135, throwaway app)*. `new groovy.json.JsonSlurper().parseText()` also rejects a `//` comment with a `JsonException`, so a user-edited JSON config file must be plain JSON *(probed 2.5.2.134, Hub Inspector loading a File Manager overrides file with one trailing comment)*.
- `HexUtils.hexStringToByteArray` pads odd-length input with a leading 0 and reads a non-hex digit as -1 instead of throwing. `byteArrayToHexString` and `intArrayToHexString` print upper case. `integerToHexString(v, n)` pads to n bytes but never truncates (`(300, 1)` gives `12C`). `hexStringToInt("FFFFFFFF")` throws `NumberFormatException` *(probed 2.5.2.135, throwaway app)*.
- `DataType` constants are the ZCL type ids as Integers (`UINT8` 32, `ENUM8` 48, `ARRAY` 72), and `DataType.getLength` gives the byte count (`UINT48` 6) or -1 for `STRING_CHAR` and `ARRAY` *(probed 2.5.2.135, throwaway app)*.
- `convertTemperatureIfNeeded(value, scale, precision)` (on-hub `shared-utilities`) returns a String rounded toward positive infinity, trailing zeros kept: on a °C hub, `(21.25, "C", 1)` gives `"21.3"`, `(-3.45, "c", 1)` `"-3.4"` and `(70, "F", 0)` `"22"` (21.1 °C rounded up). An unknown scale or a null value gives null, and a String value throws `MissingMethodException` *(probed 2.5.2.135, throwaway driver)*.

## Scheduling and sun times

- **`schedule()` takes Quartz cron and fails at the call.** A malformed expression throws `java.lang.RuntimeException` ("CronExpression '0 0 12 * * *' is invalid."), including a day of the month and a day of the week both given or both `?`, an hour of 25 and a five-field expression. One that can never fire throws `org.quartz.SchedulerException` ("Based on configured schedule, the given trigger 'app123Recur.handler' will never fire."): a past year, February 31, and a time inside the hour the clocks skip in spring. `L`, `L-3`, `LW`, `15W` (day of the month), `6L`, `L` and `2#1` (day of the week) and a year field are accepted and fire as in Quartz. *(probed 2.5.2.135, throwaway app and driver)*.
- **Jobs do not start early.** A `runIn` job, a `runOnce(Date)` job and a cron job started shortly after their time, never before it *(probed 2.5.2.135, C-8 Pro, throwaway app, one run)*.
- **Daylight saving.** Cron times are wall-clock times in the location's time zone. On the spring change a time inside the skipped hour does not exist: `0 30 2 14 MAR ? 2027` never fires in America/Toronto. On the autumn change a repeated time fires at its second, standard-time pass: `0 30 1 7 NOV ? 2027` is due at 06:30 UTC, not 05:30 *(probed 2.5.2.135, throwaway app)*. How a job that fires every minute behaves through the repeated hour was not tested.
- **`schedule(Date)` is not a one-shot.** It becomes a daily cron at that time of day in the location's zone: a Date three hours ahead showed as `1 21 7 * * ?` in `statusJson`, due at that Date. Use `runOnce(Date)` for one run *(probed 2.5.2.135, throwaway app)*.
- **`runEvery*` picks random offsets** on every call (a random second for one minute, a random start within the period for longer ones), so two runs differ and jobs do not fire on the clock boundary *(probed 2.5.2.135, throwaway app)*.
- **The handle `runIn`, `runInMillis` and `runOnce` return** is `{handler}|app{appId}Once` (`dev{deviceId}` in a driver). With `overwrite: false` a second pending job of the same handler gets a counter in front (`1tick|app123Once`), and `cancelRunIn()` with the first handle cancels only that job *(probed 2.5.2.135, throwaway app and driver)*.
- `statusJson` `scheduledJobs` rows show a cron job with its expression as `schedule` and the last fire as `prevRunTime`. A device's `/device/fullJson` `scheduledJobs` lists only its one-shot jobs (`schedule: "Once"`) and is null when it has none, a pending cron job included *(probed 2.5.2.135, throwaway app and driver)*.
- **`getSunriseAndSunset([date:, sunriseOffset:, sunsetOffset:])`** returns a LinkedHashMap of two Dates on whole minutes, for the location-time-zone date of `date` (today by default). An offset that is a number is minutes (1.5 adds 90 s); a string `[+|-]hh:mm` is hours and minutes (`01:30` adds 90 minutes); any other string (`abc`, `-30`) is ignored. Where the sun does not rise or set that day (Tromsø at either solstice) both are null, and passing an offset then throws `NullPointerException`. `getTodaysSunrise()`, `getTomorrowsSunrise()` and the sunset forms match it for today and tomorrow, and drivers get the same calls *(probed 2.5.2.135, throwaway app and driver at Greenwich, Montreal and Tromsø)*. `getNextSunset(null, offset)` and `getNextSunrise(null, offset)` return the first event whose time plus the offset is still ahead, plus the offset, so for the half hour after sunset `getNextSunset(null, 30)` is earlier than `getNextSunset()` *(probed 2.5.2.135, throwaway app, the hub moved so the event was 8 or 40 minutes away on either side)*.
- **Sunrise and sunset events.** At the sunrise minute the hub sends the location event `sunrise` (value `true`, "It is now sunrise"), then within 100 ms `sunriseTime` with the next sunrise as UTC text (`2026-10-14T11:09:00.000Z`); the same for sunset; both have type `API`. It also sends `sunriseSunsetUpdated` with an empty value at midnight, noon and 23:00 and at startup *(probed 2.5.2.135, the hub's location event history)*.

## Hub variables

- **`setGlobalVar()` validates the value against the variable type** *(false 2.5.2.129; probed 2.5.2.133–2.5.2.135)*. A value that doesn't fit returns `false` and leaves the variable unchanged; it doesn't throw. Number takes integers only (`"3.5"`, `3.14` rejected); Decimal rejects `"1,5"`, `NaN` and infinity; Boolean takes only `true`/`false` and the strings `"true"`/`"TRUE"`; DateTime takes a `Date` or the canonical `yyyy-MM-dd'T'HH:mm:ss.SSSZ` text (`Z` offset too) and rejects `""`, `2026-10-03`, `14:00` and `2026-10-03T14:00:00-04:00` even though `toDateTime()` parses the last two. Values over 1024 characters still throw `IllegalArgumentException`. Before 2.5.2.133 every non-null value was accepted *(probed 2.5.2.129)*.
- **"No value" for a DateTime** is `9999-99-99T99:99:99.999-9999`, the form the Hub Variables page writes for an unset value; `setGlobalVar()` accepts it. Date-only is `yyyy-MM-ddT99:99:99.999-9999` and time-only is `9999-99-99THH:mm:ss.SSSZ`. Writing `""` to clear a DateTime fails silently on 2.5.2.133. A reader must check for these forms before calling `toDateTime()`: it throws `ParseException` on the unset and date-only forms and rolls the time-only form over to year 10007 *(probed 2.5.2.133)*.
- **Connectors and Maker API validate too** *(false 2.5.2.129; probed 2.5.2.133)*. Connector `setVariable`/`setDateTime` ignore a bad value (before: Number/Decimal stored `null`, Boolean the raw string *(probed 2.5.2.129)*). Maker API `GET /hubvariables/{name}/{value}` answers a bad value with HTTP 200 `{"result":"not authorized"}` and leaves the value unchanged; a variable that is missing or not in `pickedHubVariables` gets 404 instead. See [Maker API specifics](hubitat-internal-apis.md#maker-api-specifics) for its status codes.
- **What the read calls return** *(probed 2.5.2.135, throwaway app)*. `getGlobalVar(name)` gives a `com.hubitat.hub.domain.GlobalVariable` copy: `value` a Long, BigDecimal, Boolean or String by type, `valueAsString` the stored text, `deviceId`, `attribute` and the Hub Mesh fields null, `isLinked()` false, `toString()` `name: x, type: integer, value: 9, deviceId: null, attribute: null`, `toMap()` one entry keyed by the name. It is null for a missing name and for null. `getAllGlobalVars()` is a HashMap of name to a LinkedHashMap `type`, `value`, `deviceId`, `attribute`, `source` and `sourceIp` (both `""` for a local variable). `getGlobalVarsByType(type)` lower-cases the type (`INTEGER` works), returns null for an unknown one (`Number`, `decimal`) and throws `NullPointerException` for null.
- **What a write stores** *(probed 2.5.2.135, throwaway app)*. Numbers keep their text (`"1e3"` stays `1e3` and reads back as BigDecimal `1E+3`), a Boolean variable stores `TRUE` as written and reads it as true, a String variable stores Java's `toString` (a map as `{a=1}`), and a `Date` is written in the location's zone to the second (milliseconds read back as `.000`). `addValueToGlobalVar` adds a number or numeric string to an integer or bigdecimal variable, returns false for any other type or value, and throws `NullPointerException` ("Cannot get property 'linked' on null object") for a missing variable.
- **Every accepted change sends a location event** `variable:{name}` with the new text as value, type `HUB_VARIABLE_SET` and "Variable '{name}' set to {value}", also with `sendConnectorEvent: false`, also from a driver's `setGlobalVar`, and when the variable is created or updated on the Hub Variables page. A write of the current value returns true and sends nothing. Writing `""` to a String variable records the event with a null value, and no subscriber receives it *(probed 2.5.2.135, throwaway app and driver)*.
- **In-use lists** *(probed 2.5.2.135, throwaway app)*. `addInUseGlobalVar(name)` returns true for any name, one that does not exist included, and the app then shows in the page's `usedBy` (`/hub2/variables`); the list form returns false for `[]`; `addInUseGlobalVar((String) null)` reaches the list form and throws `NullPointerException`. `removeInUseGlobalVar` returns true for a name in use and for a missing name, false for one not in use and for null. `removeAllInUseGlobalVar()` returns true. Renaming a variable on the page calls `renameVariable(oldName, newName)` on each app in `usedBy`, which stays in use under the new name.
- `setGlobalVar()` works in a driver and sends the event; `getGlobalVar()`, `getAllGlobalVars()` and `addInUseGlobalVar()` do not exist there *(probed 2.5.2.135, throwaway driver)*.
- The native MCP server has no hub variable tool *(absent 2.5.2.134, native MCP gateway 0.1.5 tool list)*.
- **A rejected connector command still sends the device event** *(probed 2.5.2.133 and 2.5.2.134)*. `setLevel(55.7)` on a Dimmer connector leaves the Number variable alone but reports `level` 55.7; `setTemperature("abc")` reports `temperature` `abc` on a NUMBER attribute; a Variable connector logs `{name} variable is abc` for a write it rejected. An app subscribed to the connector device sees a value the variable never held, and the connector stays out of step until the next accepted write. Only accepted writes send the `variable:{name}` location event. Connectors check type, not range: a Dimmer connector stores 150 and -5.
- **`NaN` or `Infinity` through a Number or Decimal connector breaks the device's JSON** *(probed 2.5.2.134)*. The variable is left alone, but the connector's attribute becomes `NaN`, and `GET /device/fullJson/{id}` then returns HTTP 500 until a valid value is written. `/device/eventsJson/{id}`, `/hub2/devicesList` and the native MCP `get_device` still work.
- **A Variable connector fails on an empty string** *(probed 2.5.2.134)*. `setVariable("")` throws `MethodSelectionException` (ambiguous between `setVariable(Object)` and `setVariable(Object, Object)`). A value over 1024 characters throws `IllegalArgumentException` from `setGlobalVar` inside the connector app.
- **A variable already holding an invalid value keeps it until a valid write** *(probed 2.5.2.134)*. A Boolean stored as `abc` before 2.5.2.133 still reads `abc`, and so does its connector. A valid write replaces it, and no path can write the invalid value back.
- **DateTime connector `setTime` takes only a full timestamp** *(probed 2.5.2.134)*. `setTime("2026-10-08T08:15:00.000-0400")` sets the time; `"08:15"`, `"08:15:00"` and `"8:15 AM"` are ignored without a log entry. `setDateTime` rejects anything but the canonical form and logs `Invalid Time String: …`. `setDate("abc")` is ignored without a log entry.
- **DateTime connector `setDate` on an unset or date-only variable gets the date wrong** *(probed 2.5.2.134)*. The 99:99:99 placeholder time is added to the new date: `setDate("2027-03-04")` on an unset variable stores `2027-03-08T04:39:00.000-0500`, four days late. `setDate` on a time-only or complete value works. Use `setDateTime`, or call `setTime` first. `setTime` on an unset variable gives the time-only form `9999-99-99T08:15:00.000-0400`.
- **A DateTime connector's `dateTime` attribute carries the placeholder forms as-is** *(probed 2.5.2.134)*: `9999-99-99T99:99:99.999-9999` for unset, plus the date-only and time-only forms. A consumer that parses the attribute must handle them.
- **Rule Machine converts before it writes** *(probed 2.5.2.133)*. Set Variable from a device attribute truncates 55.7 to 55 for a Number variable and skips a non-numeric value, logging the action as done either way.
- **Hub Mesh: the receiving hub rejects bad values** *(probed 2.5.2.133 receiving from 2.5.2.129)*. A Number variable set to `null` or a DateTime set to `abc` on the source hub keeps its last good value on the receiving hub, so the two hubs then disagree with no sign of it on either.
- Only two rejections write a log entry: a DateTime connector's `setDateTime` (`Invalid Time String`) and the 1024-character limit. The rest are silent, and a Variable connector logs a rejected value as if it were set *(probed 2.5.2.133 and 2.5.2.134)*.

## Location events

- **Location events have their own queue, and it drops the newest when full.** One app sending 700 location events back to back got no exception; a subscribed app received 569 of them, the missing ones all from the 431st on, and not in the order sent *(probed 2.5.2.135, C-8 Pro, throwaway app)*. An older firmware logged "Event queue is full, new event for location 1 is dropped" *(unmarked)*.

- A mode change sends the location event `mode` with "{location name} is now in {mode} mode" and type `LOCATION_MODE_CHANGE` *(probed 2.5.2.135, the hub's location event history)*.

- Any app can call `sendLocationEvent(name:, value:, descriptionText:)` with **reserved platform event names** (`systemStart`, `manualReboot`, `manualShutdown`, `sunrise`, `sunset`, `cloudBackup`, …). The dispatcher does not gate by provenance, and a subscriber handler cannot distinguish an app-originated event from a platform one (`evt.source` carries no such tag). Apps that key trust or lifecycle logic off these names can be misled by any other local app emitting the same name. For a tamper-resistant lifecycle signal, derive it from something only the platform controls, e.g. `location.hubs[0].uptime` crossing a threshold, not from a subscribed event name *(probed firmware not recorded, C-8 Pro, throwaway app)*.

- An app-sent `deviceJoin` reaches subscribers with `evt.deviceId` null, the sender's value and description, `evt.source` `LOCATION` and `evt.type` null, and it is listed in the hub's location event history like any other. Code that falls back to `evt.value` as the joined device's id therefore takes any id another app chooses. Creating a virtual device sends no `deviceJoin` *(probed 2.5.2.139, C-8 Pro, throwaway app)*. A real Zigbee join is recorded as a **hub** event, not a location event: `/hub/eventsJson` lists `deviceJoin` with `source` `HUB`, the new device's id as `value`, `deviceId` null and "New Zigbee device joined", and `/logs/eventsJson` has no row for it. So on a real join too the id is only in `evt.value`. Whether `subscribe(location, 'deviceJoin', …)` receives that hub event is not tested *(probed 2.5.2.129, C-7, hub event history)*.

- **A location subscription can filter by value.** `subscribe(location, 'name.value', handler)` receives only the events of that name with that value, while `subscribe(location, 'name', handler)` receives all of them. An app also receives the location events it sends itself, when it is subscribed to them; two instances of one app type both received the events one of them sent *(probed 2.5.2.139, C-8 Pro, throwaway app)*.

## Controlling one app from another

The sandbox gives no direct route between unrelated apps: no call returns a handle to another app or reads its `state`. Every route goes through an event (location, device, or hub variable) or an HTTP call over loopback. The exception is a [parent/child family](https://docs2.hubitat.com/en/developer/app/parent-child-apps), whose members call each other synchronously. As a result, an unrelated custom app can't get a synchronous answer from another app unless that app serves one over HTTP *(unmarked)*. Platform helper classes are not bound by this: `RMUtils.getRuleList()` reads Rule Machine's rules synchronously, while `RMUtils.sendAction()` goes through a location event *(docs: on-hub api-hubitat-helper-rmutils)*.

Four patterns let one piece of automation command an app. They differ in who can call them, whether access is controlled, and whether the caller can read state back *(inferred from the notes below)*.

| Pattern | Custom apps | Rule Machine | Off-hub | Access control | Read-back |
|---|---|---|---|---|---|
| Groovy helper class (`hubitat.helper.RMUtils`) | yes | no | no | none | only what the class exposes |
| Location event (`sendLocationEvent`) | yes | no | no | none | only if the target publishes status events |
| Maker API | yes, over loopback | yes, HTTP actions | yes | per instance: token, selected devices | yes |
| App `mappings` (OAuth endpoints) | yes, over loopback | yes, HTTP actions | yes | per instance: token, plus whatever the app checks | yes, if the app provides it |

- **Helper class.** `RMUtils` is documented (on-hub `api-hubitat-helper-rmutils`). Not documented: any app can run any rule, nothing scopes it, and rule ids differ per hub, so resolve them by label through `getRuleList()` *(unmarked)*. A helper class is the most reusable form: a wrapper app can expose it through its own `mappings`, with its own access checks.
- **Location event.** A broadcast with no target reference and no acknowledgement. Any app can send any name, including reserved ones (see "Location events" above), so a receiver can't trust the sender. Rule Machine only triggers on a fixed list of location events and has no action to send an arbitrary one, so this pattern reaches custom apps only. HSM is the documented example: `hsmSetArm` in, `hsmStatus` out; Rule Machine reaches HSM through dedicated actions *(unmarked)*.
- **Maker API.** Exposes the devices selected in each instance, plus modes and HSM. It does not run rules or reach app internals; a virtual device that a rule triggers on is the usual bridge. On-hub callers use `http://127.0.0.1:8080` *(unmarked)*.
- **App `mappings`.** Each OAuth app instance gets its own token, the same as a Maker API instance. The cloud relay serves every app endpoint, so an app meant for local use has to check `request.requestSource` itself *(probed 2.5.2.116)*.
- **Built-in apps.** Most built-in apps expose no command interface of their own; Rule Machine's actions are the only way in *(unmarked)*. From a custom app, put the actions in a rule and run it with `RMUtils.sendAction`. Thermostat Scheduler, for example, has no OAuth endpoints, and the `thermSched` location event it subscribes to is undocumented and not visible to user apps while Rule Machine drives it. When several schedulers share a thermostat, the RM action works when it targets the scheduler by app name and silently does nothing when it targets by thermostat *(probed 2.5.2.128)*. Its restriction switch (*Disable when switch is off*) is a separate, device-based control that needs no rule *(probed 2.5.2.128)*.

## Locale-aware date/time formatting

- The `format*` helpers (on-hub `shared-date-time`) need firmware 2.5.0.143 or later; older hubs throw `MissingMethodException` *(staff: [gopher.ny](https://community.hubitat.com/t/163415/6))*. Gate on `location.hub.firmwareVersionString` or document a minimum firmware.
- With the date format set to MDY, DMY or YMD, `formatDate(Date)` returns `7/13/2024`, `13/7/2024` or `2024/7/13` (no padding) and `formatShortDate(Date)` `7/13`, `13/7` or `7/13`. The time helpers follow the 12 or 24-hour clock setting (`formatTimeHourMinute` gives `1:25pm` or `13:25`). `formatActivityDateTime(date)` gives `2024-07-13 1:25:00 pm EDT` and takes a Date or a long; `formatActivityDateTimeShort` gives `7/13 1:25pm`. All use the location's time zone, and a null argument returns `""`. `formatDate(long)`, `formatDate(String)` and `formatDate(Date, String)` throw `MissingMethodException`, and an app that declares its own `formatDate(long)` keeps it beside the platform's `formatDate(Date)` *(probed 2.5.2.135, C-8 Pro, throwaway app and driver; docs: on-hub shared-date-time)*.
- `new Date(ms).format("yyyy-MM-dd HH:mm:ss", location.timeZone)` is Groovy's `Date.format`: a null time zone or a null pattern throws `NullPointerException`, an unknown pattern letter `IllegalArgumentException` (`Illegal pattern character 'q'`), and an empty pattern returns `""`. `location.timeZone` is a `java.util.TimeZone`, and the JVM default zone follows the hub's time zone setting: after the setting changed to Asia/Tokyo, `Date.format(pattern)` without a zone and `Date.toString()` read Tokyo time *(probed 2.5.2.135, C-8 Pro, throwaway app and driver)*.

## App `definition()` flags

- `doNotFocus: true` (firmware 2.5.0.123+, undocumented) stops the main page auto-focusing the first input on open *(staff: [gopher.ny](https://community.hubitat.com/t/163415/1))*. Useful when the first element is a paragraph, status banner, or read-only field (the auto-focus otherwise scrolls past it). Unknown definition keys are ignored on older firmware, so this is safe to set unconditionally *(unmarked)*. The 2.5.3 on-hub reference names the flag `doNotAutoFocus` *(docs: on-hub app-preferences)*.
- `installOnOpen: true` is [documented](https://docs2.hubitat.com/en/developer/app/definition). Without it, an instance left before its first Done stays not installed and drops out of the Apps list *(probed 2.5.2.129, two throwaway apps)*. An instance that was never saved also drops its `runIn` calls: a button handler that started work with `runIn` logged its start and never ran again, and `/installedapp/statusJson` showed `installed: false` and no scheduled job. With `installOnOpen: true` the new instance read `installed: true` from creation, and the same work ran through its `runIn` steps without a Done *(probed 2.5.2.139, throwaway app)*.
- `showAppTitle: false` (firmware 2.4.1.x+, default true, undocumented) hides the app title from the rendered configuration page *(staff: [gopher.ny](https://community.hubitat.com/t/152087/12))*. Safe to set unconditionally on older firmware (unknown keys ignored) *(unmarked)*.
- `importUrl` prefills the URL field of the code editor's **Import** dialog, for apps as well as drivers. The [app definition docs](https://docs2.hubitat.com/en/developer/app/definition) call it "not currently used"; that is out of date: the hub stores it for apps (`/app/list/single/data/{id}`) and the app editor's Import dialog reads it, as the driver editor does *(probed 2.5.2.129, throwaway app; source: vue-hub2-app-code-editor, 2.5.2.129)*. The Import menu item is there with or without `importUrl`. Nothing polls the URL, compares versions or shows an "update available" indicator; an app that wants to signal a newer version must implement its own remote version poll.

## Driver preferences

- `section` works in a driver `preferences {}` block, as the [driver preferences docs](https://docs2.hubitat.com/en/developer/driver/preferences) show: inputs inside a section compile and appear as normal settings, but `/device/fullJson` carries no section title, so the grouping has nothing to render from. `paragraph` and `href` are app-page primitives and fail to compile in a driver (`No signature of method: Script1.paragraph()` / `href()`) *(probed 2.5.2.129, throwaway drivers)*. For in-prefs guidance in a driver, use an `input` instead: `input name: "info", type: "paragraph", element: "paragraph", title: "<b>Heading</b>", description: "<i>text</i>"` renders the HTML title and description, and `input name: "info", type: "hidden", title: "<div>text</div>"` renders the HTML title alone. Both occupy one preferences grid cell, not a full row *(probed 2.5.2.124)*.
- A `capability.*` input compiles in a driver but never yields a device. The hub offers no devices to pick (`options` is empty in `/device/fullJson`), and a value written with `device.updateSetting(name, [type: "capability.thermostat", value: [id]])` reads back as the String `"[18]"`, not a `DeviceWrapper`. A driver can't hold a handle to another device *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*.
- `multiple: true` on an `enum` input is documented for apps only, and staff say drivers do not support it *(staff: [bertabcd1234](https://community.hubitat.com/t/155308/3))*. Saved the way the device page saves it (`/device/preference/save` with `["a", "b"]`), the setting is stored as the text `a,b` and the driver reads that **String**; the 2.5.3 reference says `multiple` "permits multiple selections" *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver; docs: on-hub driver-definition)*; an earlier test also found the page's picker single-select *(probed firmware not recorded, a community driver's setting read from `/device/fullJson`)*. A value written with `device.updateSetting("en", [type: "enum", value: ["a", "b"]])` reads back in the next execution as an `ArrayList` (`[a, b]`), and the `fullJson` settings row shows `multiple: true` and `value: '["a","b"]'` *(probed 2.5.2.135, throwaway driver)*. Code reading a driver enum setting must handle both a String and a List.
- **A driver `enum` can take its options from `state`.** With `options: (state?.tvs ?: ["none found"])` in `preferences {}`, `/device/fullJson` showed `{"none found": "none found"}` on a new device and, after a command set `state.tvs` to a Map, that Map's keys and labels as the options *(probed 2.5.3.102, C-8 Pro, throwaway driver)*.

## What only an app can do

The on-hub API reference (`/developer-docs/index.json`) lists each of these methods under app scopes only *(docs: on-hub index.json)*.

- `subscribe()` does not exist in a driver: `subscribe(location, "mode", …)` throws `MissingMethodException`. A driver can't listen to other devices, location modes, hub variables or `systemStart` *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*.
- `getGlobalVar()` does not exist in a driver (`MissingMethodException`), so a driver can't read hub variables *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*.
- `mappings { }` fails to compile in a driver (`No signature of method: Script1.mappings()`), so a driver has no OAuth HTTP endpoints *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*.
- Device selection: see the `capability.*` input note under *Driver preferences* *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*.

With the preferences limits (no `dynamicPage`, `paragraph` or `href`), a driver can act only on its own device and on what its parent passes it. Logic that watches or commands other devices belongs in an app *(inferred from the limits above)*.

## Capabilities

- Capabilities cannot change at runtime, so a multi-function driver must declare the **union** of every capability it might expose, which forces unused capabilities onto every instance and is hostile to consumers (dashboards, rules, app device-selection filters all key off capabilities). When one upstream system surfaces multiple device types, prefer fanning out into one child driver per type (parent app routes by type) over a single multi-capability driver *(unmarked)*.
- `capability "RTSPStream"` compiles on 2.5.2.129 *(probed 2.5.2.129, throwaway driver)*. It was not found on firmware 2.5.2.121 and earlier, and the 2.5.1.138 release notes already announce RTSP streaming *(staff: [gopher.ny](https://community.hubitat.com/t/165384/1))*. A driver that must compile on older firmware can wrap the declaration in `try { capability "RTSPStream" } catch (Exception e) {}` inside `metadata`. The stream endpoints are in [internal APIs](hubitat-internal-apis.md). Drivers skip streaming when `getNumericHubVersion() < 9` *(unmarked)*; it returns 9 on a C-8 Pro *(probed 2.5.2.135, C-8 Pro, throwaway app)*.
- There is no `capability "FirmwareUpdate"`: declaring it fails the save with `Metadata Error: Capability 'FirmwareUpdate' not found.` *(regression 2.5.2.135–2.5.3.102, apps/tests/test-architecture-claims.sh)*. The convention is a plain `command "updateFirmware"` whose body returns `zigbee.updateFirmware()` *(unmarked)*.

## Thermostat driver modes

- The canonical `thermostatMode` / `thermostatFanMode` values ([capability list](https://docs2.hubitat.com/en/developer/driver/capability-list)) can be **narrowed** but not extended: non-canonical values break dashboard widget rendering and capability adherence. Expose a non-canonical mode (e.g. `dry`, `fan_only`) through a parallel custom attribute + command pair instead of stuffing it into `thermostatMode` *(unmarked)*.
- In a custom (user-namespaced) thermostat driver, set the supported-modes list by `sendEvent` of the `supportedThermostatModes` / `supportedThermostatFanModes` attribute with a list of **pre-quoted** strings (`["\"off\"", "\"heat\"", ...]`) so the platform's stringification yields a valid JSON array. Calling `setSupportedThermostatModes(...)` from such a driver throws `MissingMethodException` *(probed 2.5.2.135, throwaway driver; probed firmware not recorded, a custom thermostat driver)*. On the built-in Virtual Thermostat the command works when an app calls it; see below.
- The built-in **Virtual Thermostat** (type id 580, `virtualThermostat`) sets `thermostatOperatingState` from `setTemperature` with a hysteresis (default 0.5): in heat mode with setpoint 20 it starts heating at 19.4, keeps heating through 20.4, goes idle at 20.6 and stays idle down to 19.6. It drives no outputs *(probed 2.5.2.134, throwaway device)*. The copy in `hubitat/HubitatPublic` (`examples/drivers/virtualThermostat.groovy`) is older than the firmware's: its `manageCycle()` would set idle on every report taken while heating, which the firmware build does not do *(false 2.5.2.129; probed 2.5.2.134)*. Firmware 2.5.2.129 still has that bug: readings below the lower band alternate `heating` and `idle` on every `setTemperature`, so an app that switches heaters from the operating state would toggle them on each sensor report. 2.5.2.129 also has no `setHysteresis` command; 2.5.2.134 does *(probed 2.5.2.129, throwaway device)*.
- On the built-in Virtual Thermostat, `heat` or `setThermostatMode("heat")` while the mode is already `heat` and the state is `heating` usually sets `thermostatOperatingState` to `idle`, until the next `setTemperature`. A changed `setHeatingSetpoint` re-evaluates at once without a new reading; a repeated `setTemperature` with the same value also re-evaluates *(probed 2.5.2.134, test rig device)*. `thermostatOperatingState` follows a changed reading about 1 s later, occasionally 2 to 3 s, so a test that asserts on a device driven by the operating state needs to wait more than 3 s *(probed 2.5.2.134, Switched Heater Thermostat behavior suite)*.
- The built-in **Thermostat Controller 2.0** (child of *Thermostat Controllers*, type id 69; app version 2.0.3): selecting a thermostat creates a child virtual thermostat named `thermController-<thermostat>`. It has no switch or outlet inputs, so it cannot drive heaters directly *(probed 2.5.2.134, throwaway instance)*.
- An app can create a Virtual Thermostat child with `addChildDevice("hubitat", "Virtual Thermostat", dni, [name: ..., label: ..., isComponent: true])`. The result assigns to a `DeviceWrapper` and its `getTypeName()` returns `Virtual Thermostat`. The new child starts in mode `off`, operating state `idle`, with all five modes and three fan modes supported *(probed 2.5.2.134, throwaway app)*.
- `getTypeName()` on a device the user selected with a `capability.thermostat` input returns the driver's name (`Virtual Thermostat` for the built-in), so an app can check the driver of an adopted device by name. `getLastActivity()` returns a date *(probed 2.5.2.134, throwaway app)*.
- `setSupportedThermostatModes(JsonOutput.toJson(["off", "heat"]))` works on the built-in Virtual Thermostat, called from an app on the device: the device logs the change and `supportedThermostatModes` reads back as the JSON string `["off","heat"]` (before: `["auto","cool","emergency heat","heat","off"]`). Calling it again with the same list is accepted *(probed 2.5.2.134, throwaway app)*.
- `hasAttribute("power")` on a selected device returns `false` for the Virtual Thermostat and `true` for a switch driver that declares `PowerMeter`, even when `currentValue("power")` is `0`. It finds metered plugs without reading a value *(probed 2.5.2.134, throwaway app)*.
- The Virtual Thermostat's **Enable demonstration mode** preference (`demoMode`, off by default) makes it simulate a room: after `heat` and `setTemperature`, `temperature` changes on its own every 2 s and `thermostatOperatingState` cycles between `heating` and `idle`. `off` sets `thermostatMode` to `off` and `thermostatOperatingState` to `idle`, and the simulation stops *(probed 2.5.2.135, throwaway device)*. With demonstration mode off, `temperature` only changes by `setTemperature` *(unmarked)*. An app that drives a Virtual Thermostat must tell users to keep demonstration mode off *(inferred: from the simulation above)*.

## Command Retry

- Command Retry is a hub-wide, per-device opt-in and is **protocol-agnostic** (not Zigbee-specific). `/device/fullJson/{id}` reports it as `device.retryEnabled` (the opt-in) and `device.retryAvailable` (whether the device can use it). The top-level `commandRetrySelectionEnabled` equals `retryAvailable`, not the opt-in: across Zigbee, Z-Wave and Matter devices it was true wherever `retryAvailable` was, including devices with retry off. Retry was available on actuators (plugs, dimmers, locks, a Z-Wave sensor with a relay output) and not on buttons, sensors, a range extender, virtual, LAN or Lutron devices *(probed 2.5.2.134)*. An app reads both fields over loopback (`httpGet` of `http://127.0.0.1:8080/device/fullJson/{id}`); no `DeviceWrapper` accessor is known. When enabled and a command fails, the platform retries (up to 5) then emits a warn-level log line (`<label> command "<cmd>()" failed after 5 retries.`). Nothing is persisted: no attribute, counter, or endpoint exposes the retry count. A "failed after N retries" warning is therefore not by itself evidence of a Zigbee mesh problem *(unmarked)*.

## Zigbee parse() delivery

- Since firmware 2.5.0.157 the hub answers Time cluster (0x000A) reads itself *(staff: [gopher.ny](https://community.hubitat.com/t/163415/8))*. Whether the reads now also reach `parse()` has not been re-tested. The rest of this section describes earlier firmware; the responder technique still applies to other frames the platform withholds.
- Before 2.5.0.157, inbound Time cluster (0x000A) Read Attributes commands were **not delivered to a driver's `parse()`**: other frames from the same device arrive normally, only the 0x000A reads are withheld, and declaring 0x000A in the fingerprint `inClusters` did not change the routing. A reactive Read-Attributes-Response from `parse()` was therefore impossible. A responder path works instead: a driver can open `ws://127.0.0.1:8080/zigbeeLogsocket` via `interfaces.webSocket.connect()`, watch for inbound 0x000A frames, and send the Read-Attributes-Response with `he raw` *(probed firmware not recorded, C-8 Pro, an Aqara FP300 and a responder driver)*.
- `he raw` response format: space-separated bytes, `0x`-prefixed, with a `0x`-prefixed DNI. The ZCL sequence byte must be **echoed from the request payload**, not taken from the websocket log-event counter. A malformed `he raw` (missing `0x` prefix or non-space-separated bytes) is silently dropped, so the format is exact *(probed firmware not recorded, C-8 Pro, the same responder driver)*.

## App endpoints and child apps


- A `mappings` handler's reply is what it returns, normally `render(...)`: `def handler() { return render(status: 200, contentType: "application/json", data: json) }`. A returned Map or List goes out as JSON; a `void` handler, or one that returns a String, a number or null, answers an empty 200 (see `render` below) *(probed 2.5.2.135, throwaway app)*.
- `request.JSON` works as the [LAN driver guide](https://docs2.hubitat.com/en/developer/driver/building-a-lan-driver) shows, but only when the caller sends `Content-Type: application/json`; with `text/plain` it is `null` while `request.body` still holds the text, and a form-encoded POST leaves both `null` *(probed 2.5.2.129, throwaway app)*. The form fields of such a POST are in `params` (a cloud-relayed POST too) *(probed 2.5.2.129, Pushover Notification Tester callback endpoint)*. `parseJson(request.body)` covers callers that omit the header. A malformed JSON body sent with `Content-Type: application/json` is answered by the platform with an empty 200 before app code runs, with no app log line, so the app cannot return its own 400 for it *(probed 2.5.2.129)*.
- `render(...)` returns a plain LinkedHashMap of its options plus `renderMethod: true`, and that key is what makes the reply a render. Its `contentType` defaults to `application/json` (also when `null`), `data` goes out as `toString()` (a Map renders as `[a:1, b:x]`, not JSON; no data renders `null`), `status` may be an int or a numeric String, and `headers` are added except `Content-Type`, which is ignored. A handler that returns another Map or a List is answered with it as JSON; a String, a number or null is answered with an empty 200 *(probed 2.5.2.135, throwaway app)*.
- `request` is a LinkedHashMap: `body` (the text, absent for a form-encoded or empty body), `JSON` (a LazyMap or a List, for `application/json` with or without a charset), `requestSource` (`"local"`), `HOST`, `METHOD`, `SCHEME`, and `headers` (name → list of values, names written `User-agent`; the hub adds `X-hubitat-scheme`). Other names such as `request.method` or `request.path` read null, and outside an endpoint call `params` and `request` are both null. `params` holds the query parameters (URL-decoded, the first of a repeated name), then form fields, then path parameters, which win over a query value of the same name and arrive still URL-encoded (`/item/:id` gives `a%20b`) *(probed 2.5.2.135, throwaway app)*.
- Routing: routes are tried in the order `mappings` declares them and the first match wins, so a literal path declared after `/item/:id` is never reached. A trailing slash counts, case counts, double slashes collapse, `*` matches any rest of the path, and a route written without a leading slash still matches. No match is 404 `AppException` "Not Found", a verb the route does not map 405 "Method Not Allowed" (action keys are case-sensitive: `get:` maps nothing); `HEAD` always answers an empty 200 without running the handler, `PATCH` 501. An app id that does not exist answers 404 even without a token; otherwise the token is checked first, so a bad one gets 401 on any path *(probed 2.5.2.135, throwaway app)*.
- One app instance can hold several OAuth tokens: `createAnotherAccessToken()` adds one, `getAccessTokens()` lists them, `revokeSpecificAccessToken(t)` and `resetSpecificAccessToken(t)` act on one. Every live token reaches the same mappings, locally and over the cloud relay, and a revoked one gets 401 on both once the filter's cache expires (next bullet). The handler can tell which token was used: it is in `params.access_token` or the `Authorization: Bearer` header. The tokens carry no scope of their own, so any per-token limit is the app's to enforce. Once a second token exists, `state.accessToken` holds the comma-joined list (`"t1,t2"`, and `"t1,"` after a revoke leaves a trailing comma), so code that builds a URL from `state.accessToken` breaks; take one entry from `getAccessTokens()` instead *(probed 2.5.2.135, throwaway app)*.
- `state.accessToken` is where the endpoint filter looks tokens up: any non-empty comma-separated entry of it is accepted, including a string the app writes there itself, and a token made in a handler that then throws never works because the state write is dropped. The token calls are string edits of it: `revokeSpecificAccessToken("a")` turns `"a,b,c"` into `",b,c"` (and `getAccessTokens()` then lists `["", "b", "c"]`), `resetSpecificAccessToken(t)` replaces `t` in place, `revokeAccessToken()` removes the key. While OAuth is off every one of these calls, `getAccessTokens()` included, throws `RuntimeException: OAuth is not enabled for this App`. The filter caches a token it has accepted for 60 s from that first acceptance, so a revoked token that was in use keeps working for up to a minute; a token never used is refused at once *(probed 2.5.2.135, throwaway app)*.
- `addChildApp` (on-hub `app-children`) runs the child's `installed()` before it returns: right after the call the child reports `installed: true` and `getInstallationState() == "COMPLETE"`, its `initialize()` has created its component devices, subscriptions and scheduled jobs, and it is listed in `/hub2/appsList`. Anything the parent then writes into the child (settings, state) is live at once, so it must already be safe to act on; it is not held until someone presses Done. Whether a job scheduled at that point runs before the child's page is first saved has not been checked *(probed 2.5.2.129)*.
- `deleteChildApp(id)` also deletes the child's component devices *(probed 2.5.2.129)*.
- `addChildApp` initial settings: the nested form `addChildApp(ns, name, label, [settings: [n: [type: "number", value: "5"], em: [type: "enum", value: '["one","two"]', multiple: "true"]]])` saves them before the child's `installed()` runs, and `installed()` reads them typed (`number` Long, `bool` Boolean, a multiple enum ArrayList, `time` a String). A `capability.switch` entry and unknown top-level keys are ignored, and so is the flat form `[t: "hello", n: 5]` *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway app and child; docs: on-hub app-children)*. A second `addChildApp` of a `singleInstance: true` child type returns the existing instance (same id), does not run `installed()` again and keeps the first label *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway app and child; docs: on-hub app-children)*. `addChildApp` of a top-level type (no `parent:` in its definition) succeeds and returns an instance, although the reference says the child's definition must name the caller as parent *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway app and child; docs: on-hub app-children)*.
- Child app details *(probed 2.5.2.135, throwaway parent and child)*: `addChildApp` returns an `InstalledAppWrapper` (id a Long), allows a label already in use, ignores a flat properties map as settings (the nested `settings` form works, see below), and for an unknown type throws `hubitat.exception.NotFoundException: App type not found for namespace: X and name: Y`. Inside the child's `installed()`, `getInstallationState()` reads `COMPLETE` when `addChildApp` ran it and `INCOMPLETE` when a first Done ran it (a top-level app's first Done too). `getChildApps()` returns an ArrayList ordered by label, then id, loaded once per execution: after `deleteChildApp` in the same execution the deleted child is still listed and its wrapper still answers. `getChildAppByLabel` returns the lowest id of that label; unknown ids and labels give null. `deleteChildApp` returns null and runs the child's `uninstalled()`; an id that is not a child does nothing. A Map passed to `child.method(m)` is the same object, so the child's changes show in the caller; an exception thrown in a child method the parent calls does not propagate: the parent gets `null`, as it does for a missing child method, so check the returned value, not only an error flag inside it *(probed 2.5.2.129; probed 2.5.2.135, throwaway parent and child)*. `parent.method()` from a child works the same way. `hasParent()` is true only once `parent` has been read in that execution. A child's own `app.updateLabel` survives the parent's Done. Deleting the parent runs its `uninstalled()` first, while it still sees its children, then each child's `uninstalled()` in label order. `child.getState()` prints as Java's `{k=v}`, keys in a default HashMap's order.
- Calls from a parent into a `singleThreaded` child are serialized with each other and with the child's own scheduled handlers, in both orders: a call or handler that arrives while the other runs waits until it ends *(probed 2.5.2.129; probed 2.5.2.134, scheduled-handler ordering, throwaway parent and child apps)*. Child event handlers were not measured.

## Child devices

- `addChildDevice` from an app (on-hub `app-children`) takes `(namespace, typeName, dni)`, `(…, dni, Map properties)`, `(…, dni, Long hubId)`, `(…, dni, hubId, Map)` and `(namespace, typeName, Map)`. It returns a `com.hubitat.app.ChildDeviceWrapper` whose `id` is a String and whose `installed()` has already run. `properties` keys used: `name` (default: the driver's name), `label` (default: none), `isComponent` (default false), and `data`, a map stored as data values; `controllerType` is the one other key honoured (below) and the rest are dropped. The Map-only form makes a UUID DNI; an empty DNI `""` is accepted as is; a `null` DNI throws `java.lang.RuntimeException` wrapping an SQL "NULL not allowed for column DEVICE_NETWORK_ID" *(probed 2.5.2.135, throwaway parent and child)*. `controllerType: "LAN"` is honoured (`fullJson` `controllerType` shows LAN). A `data` map such as `[a: 1, b: [c: 2], l: [1, 2]]` is stored as JSON (`fullJson` `data` shows the nested values) and `getDataValue` returns Java text for it (`"1"`, `"{c=2}"`, `"[1, 2]"`). The legacy keys `completedSetup`, `componentName` and `componentLabel` are ignored *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway app and child)*.
- From a driver (on-hub `driver-children`), `addChildDevice(typeName, dni, Map)` uses the parent driver's own namespace, so a built-in such as `Virtual Switch` needs the four-argument `(namespace, typeName, dni, Map)` form. A `null` DNI makes a UUID. Every key of the properties map is also stored as a data value, `name`, `label` and `isComponent` included (`[name: "x", data: [k: "v"]]` gives data `{name: "x", data: {k: v}}`), and `name`, `label` and `isComponent` apply as for an app. `getAllChildDevices()` does not exist in a driver (`MissingMethodException`) *(probed 2.5.2.135, throwaway parent and child)*.
- Errors: a DNI any device already has (a child of another parent, or a device that is no child at all) throws `com.hubitat.device.exception.DuplicateDNIException: A device with DNI 'x' already exists`. An unknown driver throws `com.hubitat.app.exception.UnknownDeviceTypeException: Device type 'X' in namespace 'ns' not found`; the namespace must match, so a user driver named under `hubitat` is not found. Built-in drivers (`Virtual Switch`, `Generic Component Switch`) work as children *(probed 2.5.2.135, throwaway parent and child)*.
- `getChildDevices()` returns an ArrayList of `ChildDeviceWrapper`s in creation order, read fresh on each call: a child added earlier in the same execution is listed. `getChildDevice(dni)` returns null for an unknown DNI, `null`, or a device that is not this parent's child. Another parent's DNI is not visible *(probed 2.5.2.135, throwaway parent and child)*.
- `deleteChildDevice(dni)` runs the child's `uninstalled()` and deletes it; an unknown DNI, `null`, or a DNI of a device that is not this parent's child does nothing and throws nothing (that device stays) *(probed 2.5.2.135, throwaway parent and child)*.
- A call through a `ChildDeviceWrapper` (`child.on()`, `child.parse([...])`, `child.anyMethod()`) runs that driver method in the child. For a declared command (a `command` or capability command in the metadata) the caller gets `null` whatever the method returns *(probed 2.5.2.135, throwaway parent and child)*. Any other method returns its value, and so do the platform methods a driver has (`child.getChildDevice(dni)`, `child.getChildDevices()`, `child.now()`), which run in the child's context; a method that throws gives `null` and logs the error on the child; a method the driver lacks gives `null`, with no exception, and logs `MissingMethodExceptionNoStack: No signature of method: <driver script>.name() ... (method name)` on the child *(probed 2.5.2.135, a second throwaway parent app and driver)*. A plain `DeviceWrapper` (a device input) instead runs declared commands only: the call returns the `Long` id of the `command-<name>` history row it writes, and an undeclared method, `parse` included, throws `IllegalArgumentException: Command 'x' is not supported by device '<name>' (<id>).`. The `device` a child passes to its parent (`parent.componentOn(device)`) is such a `DeviceWrapper`: `cd.sendEvent(...)` works on it, but `cd.parse([...])` never reached the child's `parse`. Look the child up with `getChildDevice(cd.deviceNetworkId)` to call `parse` *(probed 2.5.2.135, throwaway parent and child)*.
- **A driver calling its child's command** runs it before the next line: a child command that paused 400 ms held the parent for those 400 ms. The parent gets null whatever the command returns, and the child's event history (`/device/eventsJson`) gets no `command-<name>` row. A child command that throws logs the error on the child and the parent carries on with its next line *(probed 2.5.2.135, C-8 Pro, throwaway parent and child drivers)*.
- In the child driver, `parent` is an `InstalledAppWrapper` (id a Long) when an app made it and a `com.hubitat.app.ParentDeviceWrapper` (id a String) when a driver did; `getParent()` is the same object. `device.parentAppId` and `device.parentDeviceId` are Longs, the other null; `device.isComponent` is a Boolean and `device.displayAsChild` null (the probe never set it). `parent.method()` runs in the parent and returns its value; a throw or a missing method returns `null` to the child. `parent.sendEvent(...)` on a device parent sets that attribute on the parent device; on an app parent it does nothing and returns `null` *(probed 2.5.2.135, throwaway parent and child)*.
- Deleting the parent app runs the parent's `uninstalled()` first (its children are still listed), then each child's `uninstalled()` in creation order, and deletes every child, built-in drivers included. Deleting a parent device does the same. A child can also be deleted on its own from the admin side (`/device/forceDelete/{id}/json`); its `uninstalled()` runs *(probed 2.5.2.135, throwaway parent and child)*.
- Inside one execution a wrapper keeps the attribute values it read first: after a child's command changed `switch`, `child.currentValue("switch")` on the same wrapper still returned the old value, while `currentValue("switch", true)` or a wrapper from a new `getChildDevice()` returned the new one *(probed 2.5.2.135, throwaway parent and child)*.

## Settings written by an app

`app.updateSetting` (on-hub `installed-app`) takes effect at once and outside the state transaction: a setting written by an execution that then throws is kept, while its `state` writes are lost *(probed 2.5.2.135, throwaway app)*.

An app can change a preference of a device it selected through an input: `dev.updateSetting("logEnable", [value: "false", type: "bool"])` on the `DeviceWrapper` returned at once, `dev.getSetting` read the new value in the same execution, the device's `updated()` did **not** run, and the driver's next command already ran with the new value *(probed 2.5.2.135, C-8 Pro, throwaway app and Virtual Switch)*.

- Overloads: Groovy sends an Integer to the `Long` overload (type `number`) and a BigDecimal to the `Double` one (`decimal`); `updateSetting(name, null)` throws `GroovyRuntimeException: Ambiguous method overloading` (List vs Map). A bare `updateSetting(...)` in an app is `MissingMethodException`; use `app.updateSetting` *(probed 2.5.2.135, throwaway app)*.
- Read back in the app: `number` as Long, `decimal` as Double, `bool` as Boolean, a List as ArrayList, a single enum or mode value as String. A `number` written as `2.7` stays the text `"2.7"` and reads as a String. A Date or ISO time written to a `time` setting is stored as `HH:mm` in the hub's zone and reads as today's date at that time (`2026-10-13T07:30:00.000-0400`); a time saved from the page keeps the text saved *(probed 2.5.2.135, throwaway app)*.
- A type other than the stored setting's is ignored without an error (`updateSetting("n", "x")` on a number, `[type: "number"]` on an enum, a Double on a number); a stored `text` setting accepts any type. `[value: x]` without a type changes nothing. A name no input declares is stored *(probed 2.5.2.135, throwaway app)*.
- Enum and mode: a collection is stored as a JSON array; a new setting becomes multiple, an existing one keeps its flag. A device input written with a collection becomes multiple even if declared single, and reads as a `com.hubitat.app.DeviceWrapperList`; an id, its text or a DeviceWrapper are all accepted *(probed 2.5.2.135, throwaway app)*.
- `removeSetting(n)` deletes the row; `clearSetting(n)` keeps it with a null value, and the app no longer finds it in `settings` from the next execution. In the execution that removed or cleared it, `settings.n` still reads the old value while `app.getSetting(n)` reads null; after `updateSetting`, `settings.n` reads the new value at once *(probed 2.5.2.135, throwaway app)*.

## Built-in virtual drivers

The built-in virtual drivers' code is closed, so their commands were measured with valid, repeated, out-of-range and wrong-typed arguments *(probed 2.5.2.135, Virtual Switch, Contact Sensor, Motion Sensor, Temperature Sensor, Humidity Sensor, Battery, Smoke Detector, Omni Sensor, Thermostat)*.

- A new device logs `installed...` at warn, saves its preference defaults (fullJson `settings[].value` shows them), and sends starting events: switch off, contact closed, motion inactive with temperature 70 in the hub's scale, temperature 72 °F, humidity 50, battery 100 %, smoke clear, the Omni's eleven attributes, the Thermostat's ten. Switch, Motion Sensor and Omni Sensor schedule `logsOff` in 1800 s *(probed 2.5.2.135)*.
- No range checks: humidity 150, battery -1, temperature 1000 all go out. Virtual Temperature Sensor, Motion Sensor and Omni Sensor send even the text `abc` as the value; Virtual Humidity Sensor and Virtual Battery truncate to an integer (55.5 gives 55) and throw `NumberFormatException` on text *(probed 2.5.2.135)*.
- Virtual Battery sends every call as a state change, repeats included, with a text that keeps the argument (`battery is 55.5%`) *(probed 2.5.2.135)*.
- Virtual Switch writes "was turned on" for a change and "is on" for a repeat (socket frame only, not stored); `refresh()` repeats the current value. `autoOff` defaults to off *(probed 2.5.2.135)*.
- Virtual Motion Sensor's `active()` schedules `inactive` after `autoInactive` (default 15 s); a manual `inactive()` does not cancel it *(probed 2.5.2.135)*.
- Virtual Temperature Sensor's unit is °F unless its `degreesC` preference is on, whatever the hub's scale; Motion and Omni use the hub's scale *(probed 2.5.2.135)*.
- Virtual Smoke Detector's `test()` sets `tested`, which stays until another command *(probed 2.5.2.135)*.
- Virtual Thermostat: values are rounded to `decimalPlaces` (default 2, half up, trailing zeros dropped); temperature events carry the hub's scale as unit and are always state changes; the cooling setpoint is kept at least 2° above the heating one (a lower `setCoolingSetpoint` is raised to it). A mode change (`setThermostatMode`, `heat()`, `cool()`, `auto()`, `off()`; `emergencyHeat()` sets `heat`) sets the operating state idle and then evaluates heating and cooling: it heats below heating setpoint − hysteresis and keeps heating up to heating setpoint + hysteresis, cooling mirrored. `thermostatSetpoint` follows `lastRunningMode` (in state and a data value), which heating, cooling, or a heat or cool mode sets. In one run of four, the evaluation after a mode change used the operating state from before the idle write (a cooling thermostat switched to auto stayed idle), so a test should not depend on that moment *(probed 2.5.2.135)*.

## HTTP subsystem

- Since 2.4.1.151 the HTTP subsystem reuses connections. Test assertions about latency that depend on cold-handshake behavior may flake on warm pools *(staff: [gopher.ny](https://community.hubitat.com/t/152087/1))*.
- **`contentType` vs `requestContentType`.** The on-hub reference (`http`) is right and the [docs2 common methods page](https://docs2.hubitat.com/en/developer/common-methods-object) is wrong: `contentType` sets the `Accept` header and how the response is parsed, not the request body. An `httpPost` with `contentType: "application/json"` and a Map body sends the body form-encoded (`k=1`, `Content-Type: application/x-www-form-urlencoded`); only `requestContentType: "application/json"` sends JSON. With `requestContentType` alone, `Accept` is `*/*` and a JSON response still parses to a Map, by its response `Content-Type` *(probed 2.5.2.129, throwaway app posting to a LAN echo server)*. `contentType: "text/plain"` leaves the response unparsed (a `TextResponseReader`) *(regression 2.5.2.135–2.5.3.102, apps/tests/test-architecture-claims.sh; probed 2.5.2.129, throwaway app posting to a LAN echo server)*. A form-encoded `contentType` (`application/x-www-form-urlencoded`) on a JSON response makes `resp.data` a `LinkedHashMap` whose single key is the JSON text, so its fields (`resp.data.model`) read `null`, with no error raised *(regression 2.5.2.135–2.5.3.102, apps/tests/test-architecture-claims.sh)*. For a JSON API, set `contentType: "application/json"` or leave it out.
- For deferred retry/backoff, do not use `pauseExecution(ms)` + a recursive call: that blocks the platform thread and eats the method's wall-time budget. Use a `runInMillis(ms, "handler", [data: ...])` continuation instead (which requires the call be async/callback-shaped). Before adding inline retry, note that scheduled callers (cron polls, `runEvery*`) already retry on their next tick *(unmarked)*.
- Always set an explicit `timeout:` (seconds) on `httpGet`/`httpPost`. Without it the client default applies *(docs: on-hub http)*: 10 s, for `httpGet` and `asynchttpGet` alike, which a sync call spends holding the thread *(probed 2.5.2.135, C-8 Pro, throwaway app and driver against a LAN test server)*.
- An app cannot `httpGet`/`httpPost` its **own** hub's external LAN IP: on port 80 the call fails with `HttpHostConnectException ... Connection refused` *(regression 2.5.2.135–2.5.3.102, apps/tests/test-architecture-claims.sh; probed 2.5.2.135, C-8 Pro, throwaway app)*, and an earlier call to an app endpoint on that IP failed as a peer error *(probed firmware not recorded, C-8 Pro, an app calling its own endpoint)*. For same-hub calls (including reaching another app's OAuth `/apps/api/<id>/...` endpoint) address `http://127.0.0.1:8080/...`; port 80 on loopback is refused (`HttpHostConnectException`). On loopback the closure gets a `com.hubitat.hub.executor.helpers.ExecutorHttpResponse` whose `data` is parsed by the reply's content type before the status is checked: JSON with JsonSlurperClassic (a `java.util.HashMap`), so a `render` that left the default `application/json` type on a non-JSON body makes the caller's `httpGet` throw `groovy.json.JsonException`; HTML or XML with XmlSlurper; other types a `TextResponseReader`; an empty body null. A 4xx or 5xx throws `ExecutorHttpResponseException` ("status code: 404, reason phrase: Not Found"). A GET follows redirects; a POST hands a 302 to its closure (status 302, data null) *(probed 2.5.2.135, throwaway app)*. Calls to a **different** hub's LAN IP are normal cross-host HTTP and work fine; this only bites self-referential calls *(inferred from the two results above)*.
- An app can read the hub's logs and any device's driver state over loopback: `httpGet` of `http://127.0.0.1:8080/logs/past/json` returned the whole past-log buffer (a List of 14,251 lines; a second read of 14,373 lines took 1.2 s) and `/device/fullJson/<id>` its JSON, `deviceState` included. An `httpPost` of a partial preference list to `/device/preference/save` (JSON, as the device page sends it) changed another device's preference and ran its `updated()`. Live logs need a driver, because `interfaces` is null in an app (see Driver-only globals); a child device can open `/logsocket` (see `interfaces.webSocket`) *(probed 2.5.2.135, C-8 Pro, throwaway app)*.

- **What `httpGet` and friends hand the closure.** A `com.hubitat.hub.executor.helpers.ExecutorHttpResponse`: `status` (an Integer), `reasonPhrase`, `contentType` (the reply's whole `Content-Type` header, charset included, null without one), `headers`, `data`, and `success`, true for every status below 400. `httpGet` returns the closure's value; `httpPost`, `httpPut`, `httpPatch` and `httpDelete` return null. `httpHead` does not exist (`MissingMethodException`); `asynchttpHead` does *(probed 2.5.2.135, C-8 Pro, throwaway app and driver against a LAN test server)*.
- **How sync `data` is parsed**, by `contentType` when given (`*/*` meaning the reply's type), else by the reply's type: `application/json`, `application/javascript` and `text/javascript` with JsonSlurperClassic (a `HashMap`); `application/xml`, `text/xml` and `application/xhtml+xml` with XmlSlurper; `text/html` with XmlSlurper, or a `TextResponseReader` holding the text when it is not well-formed XML; `text/plain` a `TextResponseReader`, decoded by the reply's charset, UTF-8 without one; `application/x-www-form-urlencoded` a `LinkedHashMap`; any other type, or none (`application/octet-stream`, `text/csv`, `application/vnd.api+json`, `image/png`), a `ByteArrayInputStream`. `textParser: true` gives a `TextResponseReader`. An empty body is null, and a JSON body of `null` throws `groovy.json.JsonException`. The body is parsed before the status is checked, so a malformed JSON body throws its `JsonException` even on a 500; otherwise a status of 400 or more throws `ExecutorHttpResponseException` ("status code: 404, reason phrase: Not Found", with `statusCode`, `response.status` and the parsed `response.data`) *(probed 2.5.2.135, C-8 Pro, throwaway app and driver against a LAN test server)*.
- **A bare JSON scalar.** A sync `httpPost` given only a URI and body throws `groovy.json.JsonException` ("A JSON payload should start with an openning curly brace '{' or an openning square bracket '['. Instead, 'true' was found") when the reply's body is `true`, so the call looks failed though the server acted on it; the map form with `textParser: true` reads it as text. On the same reply, `resp.json` in an `asynchttp*` callback returns `true` *(probed 2.5.2.138, a Samsung TV's REST app-launch and app-close replies)*.
- **Redirects.** A GET follows 301, 302, 303, 307 and 308 unless `followRedirects: false`. A POST follows only a 303 (as a GET), even with `followRedirects: true`; a 301, 302 or 307 reaches its closure with `success` true. Async calls behave the same, so an `asynchttpPost` answered with a 302 calls back with `hasError()` true *(probed 2.5.2.135, C-8 Pro, throwaway app and driver against a LAN test server)*.
- **The request on the wire.** Headers in this order: the caller's `headers`, `Accept`, `Accept-Encoding: gzip, x-gzip, deflate`, `Host`, `Content-Length`, `Content-Type`, `Connection: keep-alive`, `User-Agent: Apache-HttpClient/5.5.1 (Java/11.0.31)`. `Accept` is the caller's own `Accept` header when given, else from `contentType`: `application/json, application/javascript, text/javascript` for a type naming JSON (`application/vnd.x+json` included), `application/xml, text/xml, application/xhtml+xml` for `application/xml` and `text/xml`, `text/html, application/xhtml+xml` for `text/html`, any other type as given (`application/javascript` stays as it is), `*/*` without one. `path` replaces the URI's path (`uri: ".../echo", path: "sub"` requests `/sub`). A query in `uri` is sent verbatim, so the 2.5.1.x bug that dropped it is gone; `query` and `params` maps are appended form-encoded (space as `+`, `+` as `%2B`, `:` as `%3A`, a List value repeating its key, null as an empty value), then `queryString` as given *(probed 2.5.2.135, C-8 Pro, throwaway app and driver against a LAN test server)*.
- **Request bodies.** GET, HEAD and DELETE send none (DELETE also removes `body` from the caller's map). A POST, PUT or PATCH without a body sends `Content-Length: 0` and no `Content-Type`. In a sync call a Map body is form-encoded under the default `requestContentType` (`application/x-www-form-urlencoded`; a List value repeats its key, a nested Map is sent as its `toString`), serialized to JSON under a JSON `requestContentType`, and sent as its `toString` (`[a:1]`) under any other; a String goes as is and a `byte[]` as raw bytes. `asynchttp*` serializes a Map or List body to JSON whatever the `requestContentType`, which still defaults to the form type, so the server gets JSON labelled `application/x-www-form-urlencoded` unless the caller sets `requestContentType`. `httpPostJson` and `httpPutJson` send JSON with JSON `Content-Type` and `Accept`, and add `contentType: "application/json"` to the caller's map *(probed 2.5.2.135, C-8 Pro, throwaway app and driver against a LAN test server)*.
- **`gzipBody: true`** sends base64 of the gzipped body text with `Content-Encoding: gzip`, through `hubitat.helper.NetworkUtils.gzipCompressAndBase64Encode(String)`. A sync call with a Map body throws that method's `MissingMethodException`; `asynchttp*` turns the Map into JSON first, so it works there. A GET ignores it. Gzip and deflate replies are decoded, and lose their `Content-Encoding` and `Content-Length` headers *(probed 2.5.2.135, C-8 Pro, throwaway app and driver against a LAN test server)*.
- **Response headers** are a `com.hubitat.hub.executor.helpers.ResponseHeaders`, a Map keyed by each name's first-seen spelling and looked up in any case. A repeated name maps to its last header, which keeps its own spelling (`Set-Cookie: a=1` then `set-cookie: b=2` gives `headers["Set-Cookie"]` as `set-cookie: b=2`). Each value is a `ResponseHeaders$HeaderEntry` with `name` and `value`, `"Name: value"` as a String. `size()`, `iterator()`, a `for` loop, `*.name`, `each { h -> }` and `find { }` go through every header as received, repeats included, as HeaderEntry objects; `each { k, v -> }` gives the name and the HeaderEntry; `collect` and `any` get Groovy's Map entries (`java.util.AbstractMap$SimpleImmutableEntry`), so `collect { it.name }` throws `MissingPropertyException`. `getFirstHeader(name)` returns HttpClient 5's `org.apache.hc.core5.http.message.BasicHeader` *(probed 2.5.2.135, C-8 Pro, throwaway app and driver against a LAN test server)*.
- **Failures in a sync call.** An unknown host throws `java.net.UnknownHostException` ("nohost.invalid: Name or service not known"); a connect timeout `org.apache.http.conn.ConnectTimeoutException` ("Connect to h:p failed: Connect to http://h:p failed: connect timed out", caused by `org.apache.hc.client5.http.ConnectTimeoutException`); a refused connection `org.apache.http.conn.HttpHostConnectException` ("... Connection refused (Connection refused)", caused by `org.apache.hc.client5.http.HttpHostConnectException`); a read timeout `java.net.SocketTimeoutException` ("Read timed out"); a self-signed certificate `javax.net.ssl.SSLHandshakeException` ("PKIX path building failed: ..."), accepted with `ignoreSSLIssues: true`; no `uri` `IllegalArgumentException` ("uri cannot be null"); a malformed one `java.net.URISyntaxException`. `timeout` covers the connect and each read, accepts a numeric String, and is removed from the caller's map along with `textParser`, `ignoreSSLIssues`, `followRedirects` and `gzipBody` *(probed 2.5.2.135, C-8 Pro, throwaway app and driver against a LAN test server)*.
- **What an `asynchttp*` callback gets.** A `hubitat.scheduling.AsyncResponse`. A status outside 200-299 is an error, a 3xx included (204 is not). A call that got no reply (refused, timed out, unknown host, bad or missing `uri`) calls back with status 408, the exception's message from `getErrorMessage()`, null `headers` and null `getErrorData()`. `getData()` is the body as text for the JSON, XML, HTML, plain-text and form types and base64 for the others (`application/octet-stream`, `text/csv`, `application/vnd.api+json`, no type), null when empty; on an error it throws `java.lang.Exception` "No response data exists for async request". `getErrorData()` and `getErrorMessage()` (the reason phrase) throw `java.lang.Exception` when there is no error. `getJson()` parses `data` with JsonSlurper (a `LazyMap`; an empty body throws "Text must not be null or empty") and `getXml()` with XmlSlurper; on an error both throw `IllegalArgumentException` ("No json  exists for response", with two spaces). `headers` is the same `ResponseHeaders` as above, and `getWarningMessages()` an empty list *(probed 2.5.2.135, C-8 Pro, throwaway app and driver against a LAN test server)*.
- **`getErrorJson()` and `getErrorXml()` never return the error body.** Without an error they throw `IllegalArgumentException` ("No Error JSON exists for response"); with one they throw the `getData()` exception, "No response data exists for async request" *(probed 2.5.2.135, C-8 Pro, throwaway app against a LAN test server)*. The on-hub reference says `getErrorJson()` returns the error data as JSON *(docs: on-hub api-hubitat-scheduling-asyncresponse)*; the probe contradicts it. Parse `getErrorData()` yourself.
- **Async callbacks.** The `data` map reaches the callback as the same object, so a change the caller makes after the call shows there; omitted or null, the callback gets null. A callback name with no method logs `MissingMethodExceptionNoStack: No signature of method: <script>.name() is applicable for argument types: (hubitat.scheduling.AsyncResponse, java.util.LinkedHashMap) ...`; a method taking one argument logs `No signature of method: java.lang.String.call() ...` and does not run; a null name runs no callback. A callback that throws loses its `state` writes like any handler *(probed 2.5.2.135, C-8 Pro, throwaway app and driver against a LAN test server)*.
- **The async limits in detail.** The 8 per app (and per device, measured the same) caps the requests an owner has handed to the connection pool, and the 5 per destination is one pool for the whole hub: two apps sending 12 calls each over three destinations had 14 in flight, 8 of one and 6 of the other, whose queued requests waited behind its own 8. A request waiting for one of its owner's 8 slots is not timed: of 12 calls with `timeout: 3` to a server that answers after 6 s, 8 timed out at 3 s and the other 4 started then and timed out at 6 s *(probed 2.5.2.135, C-8 Pro, throwaway app and driver against a LAN test server)*.

## LAN `HubAction` over UDP

- **A `LAN_TYPE_UDPCLIENT` `HubAction` without `ignoreResponse: true` waits for a reply.** Each device has about 5 in flight at once; each one that gets no reply (a Wake-on-LAN broadcast, say) holds its place for between 8 and 11 s, about the default 10 s wait, and later sends queue behind it, `ignoreResponse` sends included. With 5 or more queued, the device logs `device <id> has N pending hub commands` as a `warn`, and from 13 as an `error` with `, consider disabling app/device`. A burst of 40 left 35 queued, which drained at about 0.4 per second. `timeout: 1` is accepted and drains a burst about five times faster (about 2 per second). With `ignoreResponse: true`, and with the platform form `new HubAction("wake on lan <mac>", Protocol.LAN, null)`, the queue empties as fast as it fills. Each send adds 1 to the device's `hubActionCount` in `/logs/json`, and no `parse()` or callback runs *(probed 2.5.2.135, C-8 Pro, throwaway driver sending to 255.255.255.255:9)*.
- **The JVM's `maximum number of DatagramSockets reached` error was not reproduced.** Six devices sending 40 such packets each at once logged only the pending-command lines, with no socket error *(probed 2.5.2.135, C-8 Pro, throwaway driver)*. So waiting `HubAction`s do not seem to hold one socket each; a hub that logs it has another UDP user holding sockets *(inferred from the result above)*. For fire-and-forget UDP (Wake-on-LAN), set `ignoreResponse: true` or use the `wake on lan` form *(inferred from the queue results above)*.

## `HubAction`, `HubMultiAction` and `Protocol`

- **`hubitat.device.Protocol`** has these constants, in this order: `LAN`, `RAW_LAN`, `ZWAVE`, `ZWAVE_LOW_PRIORITY`, `ZIGBEE`, `TELNET`, `EVENTSTREAM`, `DELAY`, `LIFX`, `BOND`, `WIZ`, `MATTER`, `UNKNOWN`; `HubAction.Type` has two, `LAN_TYPE_UDPCLIENT` and `LAN_TYPE_RAW` *(probed 2.5.2.135, C-8 Pro, throwaway driver)*. `HubAction.Encoding.values()` is `[HEX_STRING]`, its only constant *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN echo server)*.
- **Building one sends nothing.** `new HubAction(String)` and `new HubAction(String, Protocol[, dni | options])` print as their String (`toString()` gives the command text, `action` the String and `protocol` the Protocol). `new HubAction(null, Protocol.ZIGBEE)` is accepted and prints null. A Map with a Protocol, `new HubAction([a: 1], Protocol.ZIGBEE)`, and a HubAction in place of the String are `GroovyRuntimeException: Could not find matching constructor` *(probed 2.5.2.135, C-8 Pro, throwaway driver)*. A HubAction has no `callback` property (`MissingPropertyException`) *(probed 2.5.2.135, C-8 Pro, throwaway driver)*.
- **A Map builds an HTTP request** and prints it: `new HubAction(method: "GET", path: "/x", headers: [HOST: "192.0.2.1:80"])` prints `GET /x HTTP/1.1`, `Accept: */*`, `User-Agent: Linux UPnP/1.0 Hubitat`, then the given headers in order, a blank line, each line ending CRLF. The method defaults to `POST` and the path to `/`; `query: [a: 1, b: "two words"]` adds `?a=1&b=two%20words`; a String `body` adds `Content-Length` after the headers and is printed after the blank line, a Map body is sent as JSON with `Content-Type: application/json` added after the headers; `HubAction(map, dni)` and `HubAction(map, dni, options)` print the same text *(probed 2.5.2.135, C-8 Pro, throwaway driver)*.
- **`HubMultiAction`** keeps its list in `actionList` (`actions` is `MissingPropertyException`) and prints as the default `hubitat.device.HubMultiAction@<hash>`. `new HubMultiAction(List)` and `new HubMultiAction(List, Protocol)` take Strings; with a Protocol the constructor wraps each element in `new HubAction(element, protocol)`, so a list holding a HubAction throws the same `GroovyRuntimeException`; `add(String)` appends *(probed 2.5.2.135, C-8 Pro, throwaway driver)*.

- A device created with `/device/save` has the preference defaults saved when it is created, so a driver reads every preference its `preferences {}` block declares from the first execution on, `installed()` included: a saved value, else the input's `defaultValue` (a `number` as `Long`, a `decimal` as `Double`, a `bool` as `Boolean`, `string` and `enum` as `String`), else null. `settings.keySet()` lists all of them, the ones with no default included, and the device page shows the defaults *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver)*. ## Smaller platform facts for drivers

- **`homekitCompatible: true`** in a driver's `definition()` shows as `homeKitCompatible: true` in the `device` section of `/device/fullJson`; 9 of 11 other user-driver devices on the same hub showed false. Whether the HomeKit integration then offers the device was not tested *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver)*.
- **`delayBetween(List cmds, Long delay = 100)`** returns the commands with a `delay <n>` GString between each pair: `["a", "b"]` gives `a`, `delay 100`, `b`; one command comes back alone; an empty or null list throws `IndexOutOfBoundsException: Index -1 out of bounds for length 0`; a String list, a String delay and a BigDecimal delay are `MissingMethodException` *(probed 2.5.2.135, C-8 Pro, throwaway driver)*.
- **`getDeviceDataByName(name)`** returns the same text as `device.getDataValue(name)`, null for a missing name (a null name too); neither returns the `endpointId` that the device page's Save wrote *(probed 2.5.2.135, C-8 Pro, throwaway driver)*.
- **`hubitat.helper.ColorUtils`.** `hsvToRGB([h, s, v])` takes 0–100 for all three and gives Integer RGB (`[0, 50, 50]` is `[128, 64, 64]`); `hsv360ToRGB` takes hue 0–360. `rgbToHSV` gives Doubles rounded to two places, `rgbToHSV360` a 0–360 hue; `rgbToHEX([r, g, b])` is `#RRGGBB`; `hexToRGB("#FF0000")` needs the `#` and gives `[]` without it or for `#abc`. A list shorter than three gives `[]` or `""`, a null list a `NullPointerException` and a String element a `GroovyCastException`. The XY forms (`rgbToXY`, `hsvToXY`, `hsv360ToXY`) give Floats rounded to four places and a brightness percent Integer (`[255, 0, 0]` is `0.64, 0.33, 100`), and `hsvToXY` and `hsv360ToXY` **divide the caller's list in place** (`[33, 100, 100]` is `[0.33, 1, 1]` afterwards) *(probed 2.5.2.135, C-8 Pro, throwaway driver)*.
- **`Date.toLocaleString()`** in a driver reads `Oct 14, 2025, 9:51:37 AM`, in the hub's time zone, and `toString()` is `Tue Oct 14 09:51:37 EDT 2025` *(probed 2.5.2.135, C-8 Pro, throwaway driver)*.
- **Event order inside one execution is not fixed.** A driver that sent five events from one `parse()` had them stored in different orders on repeated runs of the same report (`temperature, thermostatSetpoint, heatingSetpoint, ...` once, `thermostatSetpoint, temperature, ...` another time), so a test should compare the set of events, not their order *(probed 2.5.2.135, C-8 Pro, throwaway driver)*.
- **An exception thrown often loses its message.** Once a throw site is hot the JVM replaces `NullPointerException`, `ArrayIndexOutOfBoundsException` and similar by a shared instance without message or stack, so code that logs `e.message` can see null for a failure that had a message the first time; Groovy's own `MissingMethodException` and `NullPointerException: Cannot get property ...` are built fresh each time and keep theirs *(probed 2.5.2.135, C-8 Pro, throwaway driver)*.
- **A driver command named `dump` did not run.** `/device/runmethod` answered success for it and the driver's own method left no trace in `state` *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver)*. `Object.dump()` taking the call instead is the likely cause *(inferred: Groovy's `Object.dump()` has that name and signature)*. A command named `dumpRec` ran *(probed 2.5.3.102, C-8 Pro, throwaway driver)*.

## LAN messages, raw sockets and ping

- **A LAN HubAction that built an HTTP request is answered through `parse()`**, or through the `callback` named in its options. `parse()` gets the description `mac:<MAC>, ip:<hex ip, lower case>, port:<hex port, 4 digits>, headers:<base64 of the header block>, body:<base64 of the body>` (`body:` empty without a body), `ip` and `port` being the server's. The header block is the status line and the headers, trimmed, each ending CRLF, in the order the server sent them (`Server: fixture ` came back as `Server: fixture`) *(probed 2.5.2.135, C-8 Pro, throwaway driver against a LAN test server)*. A server's refused port gives no `parse()` and no callback *(probed 2.5.2.135, C-8 Pro, throwaway driver against a LAN test server)*.
- **`parseLanMessage(description)`** splits on `, ` into `mac`, `ip`, `port` (Strings) and, for HTTP, `headers` (a LinkedHashMap with the status or request line as a key whose value is null), `body` (text, null when empty), `header` (the block as sent), `status` (the Integer, **only for a 200**; 404, 500 and 204 have none) and `json` and `data` (the same HashMap) for a JSON body whatever the status. The UDP form `index:00, mac:..., ip:..., port:..., type:LAN_TYPE_UDPCLIENT, payload:<hex>` gives those six Strings. A description with no pair, such as a raw-socket hex string, gives an empty map *(probed 2.5.2.135, C-8 Pro, throwaway driver against a LAN test server)*.
- **A callback** receives a `hubitat.device.HubResponse` for HTTP: `headers` (an `org.apache.commons.collections.map.CaseInsensitiveMap`, keys lower-cased, the status line included as a key with a null value), `status` (Integer, set for every code), `body`, `json` and `data` (HashMap or null), `description` (the description above), and null `xml`, `error` and `hubId`. For UDP the callback gets the description as a GString and `parse()` is not called *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver against a LAN test server)*.
- **UDP.** `new HubAction("hello", Protocol.LAN, [type: HubAction.Type.LAN_TYPE_UDPCLIENT, destinationAddress: "ip:port"])` sends the text as UTF-8 and answers through `parse()` with the UDP description (`port` the server's); `ignoreResponse: true` sends and delivers nothing; `encoding: "hex"` is ignored (the text goes out as written) *(probed 2.5.2.135, C-8 Pro, throwaway driver against a LAN test server)*. `type: "LAN_TYPE_UDPCLIENT"` as a String sends UDP like the enum. With `encoding: HubAction.Encoding.HEX_STRING`, the UDP payload `"48656C6C6F"` goes out as the bytes `Hello` *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN echo server)*.
- **A UDP reply reaches `parse()` as a description String** (`callback` unset): `index:00, mac:<hub MAC>, ip:<sender hex>, port:<hex>, type:LAN_TYPE_UDPCLIENT, payload:<hex>`, and `parseLanMessage(d).payload` is the hex payload. With `callback: "name"` that method gets the same description *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN echo server)*.
- **A UDP send with no reply never reaches `parse()`**, and `parse()` never gets a `LAN_TYPE_UDPCLIENT_ERROR` description for it (`timeout: 2` tried). With `parseWarning: true` the hub logs the warning `Read timed out` for the device; with the default or `ignoreWarning: true` it logs nothing. The on-hub reference says `parseWarning` makes UDP failures return a `LAN_TYPE_UDPCLIENT_ERROR` description *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN echo server)*.
- **`LAN_TYPE_RAW` sends the text over TCP and delivers no answer.** The server's reply reached neither the `callback` nor `parse()`, and the hub logged the warning `Read timed out` about 10 s later, with or without a callback. The on-hub reference says the UDP/raw callback receives one response-description String; for raw TCP nothing arrived. With `encoding: HubAction.Encoding.HEX_STRING` a `LAN_TYPE_RAW` payload `"48656C6C6F"` is sent as the bytes `Hello` *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN echo server)*.
- **`parse()` may return a Map or a List during inbound processing.** A UDP reply handled by a `parse()` that returned `[name: "p1", value: ...]` set the attribute; one that returned a List of that event Map and a `new HubAction("followup", Protocol.LAN, [type: LAN_TYPE_UDPCLIENT, destinationAddress: ...])` set the attribute and sent the HubAction, and the reply to it reached `parse()` in turn. `/device/runmethod` with method `parse` ignores the return value *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN echo server; docs: on-hub driver-events)*.
- **`destinationAddress` decides where an HTTP HubAction goes and leaves the `HOST` header alone.** With `headers: [HOST: "192.0.2.1:80"]` and `destinationAddress: "<server ip>:<port>"`, the request went to the destination address and still carried `HOST: 192.0.2.1:80` *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN echo server)*.
- **`interfaces.rawSocket`** is a `hubitat.helper.interfaces.RawSocket` (`interfaces` is `hubitat.helper.InterfaceHelper`, `interfaces.webSocket` a `hubitat.helper.interfaces.WebSocket`, `interfaces.telnet` a `MissingPropertyException`). `connect(host, port)`, `sendMessage(String)` and `close()` return null; every chunk the server sends reaches `parse()` as an upper-case hex String (`echo:hello` is `6563686F3A68656C6C6F`), a server push after a reply arrives as its own call, and `parseLanMessage` of it is an empty map. `socketStatus` was not called when the server closed the connection, and `sendMessage` after the close neither threw nor sent anything *(probed 2.5.2.135, C-8 Pro, throwaway driver against a LAN test server)*. `connect` to a filtered port threw `SocketTimeoutException: connect timed out` *(probed 2.5.2.135, C-8 Pro, throwaway driver against a LAN test server)*. With `byteInterface: true` the String given to `sendMessage` is read as hex and `bytes` went out as the bytes `0B EF DF`; an earlier probe with the `eol` option saw a two-line message produce one `parse()` call, for the first line, within 3.5 s *(probed 2.5.2.135, C-8 Pro, throwaway driver against a LAN test server)*; the receive options below were measured later.
- **`rawSocket` receive options.** By default each read is delivered as a hex String (`echo:a\nb\n` arrives as `6563686F3A610A620A`); `convertReceivedDataToString: true` delivers text. `eol: "\n"` splits on its first character and each message keeps the terminator (`echo:a\n`, then `b\n`; hex unless `convertReceivedDataToString`). `termChars: [13, 10]` splits on CR LF, removes the terminator and delivers text without the conversion flag (`echo:a`, `b`); data without the terminator stays buffered. With both set, `eol` wins (hex, terminator kept). With `readDelay: 1000`, two replies that arrived close together came in one `parse()` call, at about 1 s intervals; by default each reply came in its own call within about 0.45 s *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN echo server; docs: on-hub api-hubitat-helper-interfaces-rawsocket)*.
- **`rawSocket` `timeout` closed no idle socket.** A connected socket with nothing happening stayed open, with no `socketStatus` call, for 75 s by default and for 20 s with `timeout: 5000`. The on-hub reference describes `timeout` as a connect/read timeout (default 30000); no read timeout closed an idle socket, and the connect timeout was not tested *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN echo server)*.
- **`NetworkUtils.ping(host[, count])`** sends `count` packets (3 by default) and returns a `PingData` with `packetsTransmitted`, `packetsReceived` and `packetLoss` (Integers) and `rttMin`, `rttAvg`, `rttMax` (Doubles in milliseconds, `0.0` when nothing came back). A host that dropped every packet counts them all lost; a name that does not resolve returns null, so the first field read throws `NullPointerException` *(probed 2.5.2.135, C-8 Pro, throwaway driver against a LAN test server)*.
- **`NetworkUtils.getMDNSServiceResults(type, timeoutMs)` browses mDNS from a driver** and returns a List of Maps with `type` (`_hubitat._tcp.local.`), `name`, `qualifiedName`, `server`, `port`, `priority`, `weight`, `ip4Addresses` and `ip6Addresses` (Lists of Strings) and `textRecords` (a Map of TXT keys to Strings); a type with nothing on the LAN returns an empty List. `_hubitat._tcp` found the other hubs on the LAN *(probed 2.5.3.102, C-8 Pro, throwaway driver)*. `_androidtvremote2._tcp` found an Android TV box with `port: 6466`, its IPv4 address and `textRecords: [bt: <MAC>]`, and `_googlecast._tcp` found the same box *(probed 2.5.2.139, C-7, throwaway driver)*.
- **A repeated `getMDNSServiceResults` call returns at once.** The first `_airplay._tcp` search on a hub took the whole timeout (6096 ms for 6000 ms); each later one, with timeouts of 3000 ms, returned in 3–22 ms. Results still followed the LAN: a Samsung TV was missing 5 s after it was powered on and listed at 21 s, and still listed 15 s after it was powered off and gone at 35 s *(probed 2.5.2.139, C-7, throwaway driver)*. The hub seems to keep browsing a type once it has been searched and to return what it holds, so a device can appear or vanish up to about half a minute late *(inferred: from the timings above)*.
- **`registerMDNSListener(type)` then `getMDNSEntries(type)` works in an app and in a driver.** `_androidtvremote2._tcp` returned the Android TV box as a Map with `server`, `port`, `ip4Addresses` and `ip6Addresses` (comma-separated Strings) and the TXT key `bt`, and no service name: in an app 90 s after registering, and in a driver at every check from 0 s to 180 s after registering *(probed 2.5.2.139, C-7, throwaway app and driver)*. The driver run came after the app had registered the same type, so the entries were likely already collected; the docs call it a shared listener *(inferred: entry present at 0 s; docs: on-hub shared-network--registerMDNSListener-String)*. In the same app run `_googlecast._tcp` returned an empty List for a box the hub's mDNS list showed, and a driver's `_hubitat._tcp` was still empty 30 s after registering while `getMDNSServiceResults` found two hubs *(probed 2.5.2.139–2.5.3.102, C-7 and C-8 Pro, throwaway app and driver)*.
- **A service that expired without a goodbye is not found again under the same name.** An `_androidtvremote2._tcp` announcer killed without sending a goodbye dropped out of `getMDNSServiceResults` within 2.5 minutes. When it came back with the same instance name, address, port and TXT record, the search still did not list it 3 s and 40 s later, on two hubs, while another service of the same type stayed listed throughout and two other hosts on the LAN (avahi on a Raspberry Pi, and the announcing computer) listed the returned service. A new instance name was found at once, and an announcer that sent a goodbye and came back under the same name was found again *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a python-zeroconf announcer on the same LAN)*. In an earlier run a name stayed unlisted for over 15 minutes and was found again after a reboot, and `registerMDNSListener` + `getMDNSEntries` did not list it either *(probed 2.5.3.102, C-8 Pro, throwaway driver)*. A device that loses power sends no goodbye, so a driver that finds a device by mDNS may not find it after a power cut until the hub restarts *(inferred: from the probes above, not tested with a real device)*.
- **`rawSocket` over TLS, with a client certificate.** `secureSocket: true, ignoreSSLIssues: true` connects to a server with a self-signed certificate. Adding `certificate` and `privateKey` (PEM text) without `caCertificate` makes `connect` throw `NullPointerException` at once; with any PEM certificate as `caCertificate`, even one unrelated to the server, the hub presents the client certificate and the server verified it. `privateKey` accepted both PKCS#8 (`BEGIN PRIVATE KEY`) and PKCS#1 (`BEGIN RSA PRIVATE KEY`). With no `tlsVersion` the hub negotiated TLS 1.2 against a server that offers 1.3; `tlsVersion: "TLSv1.3"` gave TLS 1.3. With `byteInterface: true` both directions carry raw bytes as hex, as on a plain socket *(probed 2.5.2.135, C-8 Pro, throwaway driver against an openssl and a Python TLS server)*. Against a server offering both versions, `httpGet` and `asynchttpGet` with `ignoreSSLIssues: true` negotiated TLS 1.3 *(probed 2.5.2.135, C-8 Pro, throwaway driver against a Python HTTPS server)*. A TLS server that refuses the client certificate does not fail `connect` at once: `connect` returns, and `socketStatus` then gets `receive error: Connection has closed: javax.net.ssl.SSLHandshakeException: ...` about every 6 ms until the driver calls `close()` *(probed 2.5.2.135, C-8 Pro, throwaway driver)*. When the server process of an established TLS session exits, `socketStatus` is not called and `parse()` just stops, as on a plain socket, so a driver needs its own idle timer to notice *(probed 2.5.2.135, C-8 Pro, prototype driver against a Python TLS server)*. A server that drops the connection during the handshake (an Android TV remote port with an unpaired client) made `connect` throw `java.net.SocketException: Broken pipe (Write failed)` *(probed 2.5.2.138, C-7, throwaway driver)*. One 7-byte message from a TLS server reached `parse()` as three calls, so a framed protocol needs its own reassembly buffer. A mode the command wrote to `state` before `connect` was still the old value in a `parse()` that ran before the command returned (see `state` commit timing above) *(probed 2.5.2.138, C-7, throwaway driver)*.
- **Closing a TLS `rawSocket` logs an error the driver can't catch.** `interfaces.rawSocket.close()` on a TLS socket returns normally, then the hub calls `socketStatus("receive error: Socket closed")` and logs `java.lang.RuntimeException: java.lang.InterruptedException (method socketStatus)` as an error on the device, with no line number. In a `singleThreaded` driver the method body never ran; without `singleThreaded` it ran, returned, and the error followed 3 ms later (once a `java.sql.SQLException` instead). A `try`/`catch` around `close()` or inside `socketStatus` can't catch it. It was logged on every close of an open TLS socket (a pairing session, a remote session closed to start pairing), whether the close came from a scheduled method or from `connect()` replacing the socket, and not on the close of a plain socket. It is harmless: the next `connect()` works *(probed 2.5.2.139, Android TV Remote driver and an instrumented copy)*.
- **RSA keys and X.509 certificates in the sandbox.** `java.security.KeyPairGenerator`, `KeyFactory`, `Signature`, `SecureRandom`, `java.security.cert.CertificateFactory` and `javax.crypto.Cipher` can be imported; `java.security.spec.RSAPublicKeySpec` is refused *(probed 2.5.2.135, C-8 Pro, throwaway drivers)*. At run time `KeyPairGenerator.getInstance("RSA")` with `initialize(2048)` produced a key pair in 3.8 s on a C-8 Pro and 5.3 s on a C-7. The public key's `modulus` and `publicExponent` read as `BigInteger`s and `private.encoded` is PKCS#8. A self-signed certificate DER-encoded by hand and signed with `Signature.getInstance("SHA256withRSA")` parsed with `CertificateFactory.getInstance("X.509").generateCertificate(...)`, passed `cert.verify(publicKey)`, and worked as the `certificate` of a TLS `rawSocket`. `generateCertificate` also parsed a PEM and a DER certificate from elsewhere, and their `publicKey.modulus` was readable *(probed 2.5.2.135, C-8 Pro, and 2.5.2.138, C-7, throwaway drivers)*.

## `interfaces.eventStream`, `interfaces.mqtt` and telnet

- **`eventStream` status.** `connect(url, Map)` reports through `eventStreamStatus(String)`: `START: EventStream Started` right after connect, `STOP: EventStream Stopped` when the server ends the stream or after an error, and `ERROR: Exception during EventStream Request: java.net.SocketTimeoutException: timeout` followed by STOP for a silent stream. No reconnect followed. SSE comment lines (`: heartbeat`) never produced a status call, though the on-hub reference lists heartbeat among the status types *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN test server; docs: on-hub api-hubitat-helper-interfaces-eventstream)*.
- **`eventStream` delivery.** By default `parse()` gets only the data of events that have an `event:` line, with a trailing newline (`event: greet` and `data: hello` give `"hello\n"`). An event made only of `data:` lines, a bare line without a field and comments are not delivered. `rawData: true` also delivers every non-empty raw line as its own `parse()` call (`data: hello`, `: heartbeat comment`, `id: 7`), in addition to the parsed data. `rawStream: true` delivers each event block whole with its blank-line terminator (`"event: greet\ndata: hello\n\n"`), comments included, and no parsed data *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN test server)*.
- **`eventStream` `readTimeout`.** A server that sent headers and then nothing gave the ERROR status 60 s after connect by default and 10 s with `readTimeout: 10` *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN test server; docs: on-hub api-hubitat-helper-interfaces-eventstream)*. `logMessages: true` wrote no hub log line for the device, though the reference says it logs received stream messages *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN test server)*.
- **`mqttClientStatus` strings** are `Status: Connection succeeded` after connect and `Error: Connection lost: Connection lost` when the broker drops the connection; `isConnected()` is true after connect and the client connects with keepalive 60 s. `subscribe(topic)` and `publish(topic, payload)` use QoS 1 by default *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a minimal MQTT 3.1.1 broker; docs: on-hub api-hubitat-helper-interfaces-mqtt)*.
- **An MQTT publication reaches `parse()`** as `topic: <base64>, payload: <base64>` (a space after each comma and colon), and `interfaces.mqtt.parseMessage(d)` returns `[topic: "zz/t", payload: "hello"]`. A binary payload decodes to unusable text; with `byteInterface: true` on connect the decoded payload is hex text (`68656C6C6F`, `0102FF`) *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a minimal MQTT 3.1.1 broker; docs: on-hub api-hubitat-helper-interfaces-mqtt)*.
- **`parseMessage` on bad input.** null and `"abc"` return an empty Map; `"a,b"` and a field without a colon throw `ArrayIndexOutOfBoundsException`; an invalid base64 value throws `RuntimeException: bad character in base64 value`; an extra field `x:y` is kept as `x: "y"` *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a minimal MQTT 3.1.1 broker)*.
- **Telnet receive.** After `telnetConnect(ip, port, user, pass)`, `parse()` gets each complete line without its CRLF (`welcome`, `echo:hi`), and a line the server sent in two parts 1 s apart arrives once, joined. `sendHubCommand(new HubAction(msg, Protocol.TELNET))` sends the message followed by CRLF (`hi` arrives as `hi\r\n`) *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN test server)*.
- **Telnet close.** When the server closes, `telnetStatus` gets `receive error: Stream is closed` and the hub logs the warning `telnet input stream closed` *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN test server)*.

## `interfaces.webSocket`

Driver code, read back against a test server on the LAN and the hub's own sockets:

- **`connect`** takes `connect(String url)` or the named-argument form `connect(uri, pingInterval: 30)`, which Groovy passes as `connect(Map, String)`; `connect(url, someMap)` throws `MissingMethodException`. It returns null at once; the outcome comes to `webSocketStatus(String)`, and each text message to `parse(String)`. A URL with no scheme makes `connect` throw `IllegalArgumentException` (`Expected URL scheme 'http' or 'https' but no scheme was found for ...`); `http://` and `https://` work as `ws://` and `wss://`, and a 302 on the handshake is followed *(probed 2.5.2.135, C-8 Pro, throwaway driver)*. An `http://` URL was accepted and connected on 2.5.3.102 too, although the on-hub reference says the URL begins with `ws://` or `wss://` *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN echo server)*.
- **Status strings** are `status: open`, `status: closing` and `failure: <text>`. `closing` arrives after the driver's own `close()` and after a server close frame of any code (1000, 1001, 1011 were tried); `status: closed` never arrived. A failure ends the connection and nothing follows it. Failure texts: `Failed to connect to /127.0.0.1:18799` for a refused port; `connect timed out` after 10 s for a host that does not answer; `Expected HTTP 101 response but was '403 Forbidden'` for a refused handshake; `null` (the string `failure: null`) when the server drops the TCP connection without a close frame; `Unknown opcode: 3` for a reserved opcode, sent after `status: open`; `Read timed out` after 10 s for `wss://` to a plain server; `sent ping but didn't receive pong within 30000ms (after 0 successful ping/pongs)` when pings go unanswered *(probed 2.5.2.135, C-8 Pro, throwaway driver)*.
- **Pings.** The hub pings every 30 s by default; the `pingInterval` option is in seconds. The first ping goes out one interval after `open`, and an unanswered ping fails the connection at the next one, 60 s after `open` by default and 4 s with `pingInterval: 2`. Pings from the server are answered. A `pingInterval` that is not a number is ignored without an error, and so are unknown options and `subprotocol`; `headers: [Name: "value"]` is sent with the handshake *(probed 2.5.2.135, C-8 Pro, throwaway driver and server log)*.
- **`sendMessage(String)`** returns null. It throws `MissingMethodException` for a `byte[]` or a Map and `NullPointerException` for null. With no connection, or after the server closed, `sendMessage` and `close()` return null and throw nothing, and `close()` twice is harmless. `close()` sends close code 1000 with the reason `Disconnect` *(probed 2.5.2.135, C-8 Pro, throwaway driver and server log)*. With `byteInterface: true` on `connect`, `sendMessage("0102")` sends a binary frame of the bytes 01 02, and a non-hex String such as `hello` gives `webSocketStatus` the text `send error: Unexpected hex string: hello` (and a debug log line); without it the same String goes as a text frame. `perMessageDeflate: false` is ignored: the handshake still offers permessage-deflate, and the on-hub reference says unrecognized keys, `perMessageDeflate` among them, are not read *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver and a LAN echo server; docs: on-hub api-hubitat-helper-interfaces-websocket)*.
- **Messages.** A text frame reaches `parse(String)` whole: fragmented frames are joined and a 2,000,000-byte frame arrives in one call. A binary frame reaches `parse(String)` as hex text (the bytes 1 and 2 arrive as `"0102"`); `byteInterface: true` changed nothing for received frames. `parse` runs after `status: open`, in the order the frames arrived. A second `connect` while one is open closes the first (`status: closing`) and opens the new one *(probed 2.5.2.135, C-8 Pro, throwaway driver and server log)*.
- **The hub's own `/logsocket`** is reached at `ws://127.0.0.1:8080/logsocket`. Port 80, on `127.0.0.1` or the hub's LAN address, fails with `Failed to connect to /127.0.0.1:80`. Each log line is one message, `{"name": <device or app name>, "msg": <text>, "id": <id>, "time": "yyyy-MM-dd HH:mm:ss.SSS", "type": "dev" or "app", "level": "info", "warn", "debug", "error" or "trace"}`, with no replay of earlier lines. A driver that logs from inside its own `parse()` is fed that log line back and loops without end until it closes the socket, so skip its own lines *(probed 2.5.2.135, C-8 Pro, throwaway driver)*.

## Admin UI icon fonts

- The hub admin UI and **app configuration pages** (`/installedapp/configure/{id}`) load **Font Awesome 6 Pro** and **PrimeIcons** site-wide, so an app `dynamicPage` can use the hub's own `fa-*` / `pi-*` glyph classes and they match the admin UI in shape and size. Standalone HTML served from an app endpoint (`render` / OAuth report pages) or File Manager loads **neither** font: there, inline an SVG instead of relying on icon-font classes (cloud-served variants also can't reach `/ui2/...` asset paths). FA/PrimeIcons version specifics may age across firmware; verify by inspecting the loaded CSS *(probed 2.5.0.159)*.

## App page rendering (`dynamicPage`)

The firmware version that introduced each option is unknown *(source: `/ui2/js/appUI.js`, 2.5.2.124)*.

- `paragraph` HTML is [documented](https://docs2.hubitat.com/en/developer/app/preferences); not documented: the text is emitted **unescaped** whether or not `rawHtml` is set, so `<style>`, `onclick`, and `<a target='_blank'>` work either way. Escape any user, device, or network text before putting it in a paragraph *(source: `/ui2/js/appUI.js`, 2.5.2.124)*.
- `paragraph rawHtml: true, html` only drops the wrapper `<div style="white-space:pre-wrap; text-align:left">`. Use it for multi-line `"""` HTML, whose newlines and indentation otherwise render as visible whitespace (and stack with any `<br>`), and for flex or centered layouts. Keep plain paragraphs that rely on `\n` line breaks without it *(source: `/ui2/js/appUI.js`, 2.5.2.124)*.
- **A link that behaves like a button is a paragraph, not an input.** The platform's `buttonLink(btnName, linkText, ...)` helper (docs: on-hub app-preferences) and hand-written HTML make a paragraph with a hidden `<name>.type=button` field, an element with `onclick='buttonClick(this)'` and a hidden `settings[<name>]` field. `configure/json` lists it as a body element `{element: "paragraph", type: "paragraph", title: "", description: <the HTML as written>, required: false, multiple: false, appId}`, not among the page's inputs, and the page HTML the hub serves does not contain it. A click posts `POST /installedapp/btn` with `id`, `name` (the button name without `.type`), `settings[<name>]=clicked` and `<name>.type=button`, and `appButtonHandler` receives the name (colons in it are fine). The click stores no setting; a Done that carries the hidden fields stores one named after the button with type `button` and value `""`, whereas a native `input ... "button"` leaves no setting *(probed 2.5.2.135, throwaway app; source: `/ui2/js/appUI.js` buttonClick, 2.5.2.135)*.
- `section(sectionClass: "x")` sets the class on the wrapper that holds the section title and its body grid, so CSS on `.x > *` reaches the title and the grid, and the inputs inside the grid are out of its reach. It scopes per-section styling and cannot build a multi-column input layout; inputs go side by side through their own `width:` values on the native grid *(probed 2.5.2.129)*.
- On `input`, `styleClass:` lands on the cell div and `inputClass:` on the control itself. For buttons, `inputClass: "p-button"`, `"p-button p-button-outlined"`, or `"p-button bg-hubitat-primary-green text-white"` gives the native PrimeVue look. Buttons also accept `disabled:` *(source: `/ui2/js/appUI.js`, 2.5.2.124)*.
- App pages load PrimeFlex and PrimeVue CSS alongside the icon fonts (see above), so utility classes work in paragraph HTML: layout (`flex align-items-center gap-3`, `border-1 border-round p-3`), color (`bg-green-50`, `text-red-700`, `text-color-secondary`), and native message boxes (`p-message p-message-warn`) *(source: `/ui2/js/appUI.js`, 2.5.2.124)*.
- `window.alertHubitat(html)` is a firmware UI global that opens the native modal dialog. Call it from an `onclick` in paragraph HTML; JSON-encode the HTML, then entity-escape `& ' < >` for a single-quoted attribute. It is alert-only (no confirm result) *(source: `/ui2/js/appUI.js`, 2.5.2.124)*.
- The Done button can be hidden on a confirmation page so the only exits are explicit Cancel and Confirm: `#formApp:has(.my-confirm-section) #fieldsetAppButtons button[value='Done'] { display:none !important; }`. Pair it with a single-use token in the confirm `href` `params` so a refresh or stale link can't repeat the action *(source: `/ui2/js/appUI.js`, 2.5.2.124)*.
- `dynamicPage(refreshInterval: n)` is [documented](https://docs2.hubitat.com/en/developer/app/preferences); set it only while async work is running (`busy ? 2 : 0`). An app not yet saved with Done drops its `runIn` calls (see [Platform behavior](#platform-behavior)), so have the page render itself collect the result, and tag each run with a nonce in `state` so callbacks from an abandoned run are ignored *(unmarked)*.
- **`href` params stick.** After a link with `params` (e.g. `[undo: true]`), the hub passes the same params to every page the app renders next, including plain URL loads of other pages, until another link sets new ones. A page method declared without a parameter then fails with `No signature of method: java.lang.String.call() ... (java.util.HashMap)`. Declare every page as `Map pageName(Map params = null)`, and don't let a param pick an action; use a separate page instead *(probed 2.5.2.129)*.
- `/logs?tab=past&appId=${app.id}` deep-links to the app's past logs *(source: `/ui2/js/appUI.js`, 2.5.2.124)*.
- Selectors such as `#formApp`, `#fieldsetAppButtons`, `button.hrefElem[name^='_action_href_<name>']`, `.state-incomplete-text`, `.mdl-grid`, and `div.panel-body` style native elements but are internal markup, not API. Prefer PrimeFlex color tokens (`text-color`, `text-color-secondary`) over hard-coded hex so pages follow the theme *(source: `/ui2/js/appUI.js`, 2.5.2.124)*.
- An app input's `defaultValue` is display-only: `settings.x` for an input with `defaultValue: 5` reads null before the first Done, after an HTTP Done that leaves it out, and for an input added by a later code push (which is also absent from `settings`) *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway app; docs: on-hub app-preferences)*. A browser Done posts the displayed value and so saves it *(inferred: the page posts what it displays)*.
- `required: true` is not enforced by the hub: an HTTP Done with a required text input and a required `capability.switch` input both empty installed the app, and `installed()` saw null for both *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway app)*.
- A `mode` input lists the mode names as its options in `configure/json` (a separate `modeMap` maps id to name), and a save that posts names stores names: a single input reads as a String (`"Away"`) and a multiple one as an ArrayList (`["Away", "Day"]`) *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway app)*. A browser save stores names too *(inferred: the page's option helper posts the option strings)*. Instances saved on earlier firmware have held mode ids (`"33"`) *(probed firmware not recorded, older instances)*, so code that compares a mode setting with `location.currentMode` can test the name and the id.
- A `dynamicPage` closure runs on every render, and `state` and `atomicState` written in it persist: three `configure/json` reads raised a counter written in the page method from 1 to 4, in each store *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway app)*. A driver's `preferences` closure also runs on every render, the device page and each `/device/fullJson` read included, but only `atomicState` written in it persists; a `state` write there is never saved *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver)*. A driver that caches data for its preference options (a device list fetched from a cloud API) keeps it in `atomicState`, and guards the code with `device != null`, because saving the driver runs the closure with no device and `atomicState` null *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver)*.

## App label round-trip

- HTML embedded in an app label via `updateLabel()` (e.g. a badge `<span>`) renders in the Apps list but does not always round-trip verbatim: saving the app's config page (the name/label input on Done) can return the label with its **HTML tags stripped**, leaving bare text. A "strip-then-reapply badge" routine anchored to the exact `<span>…</span>` element then fails to match the bare-text remnant and appends a fresh badge on each refresh: it self-stacks (stabilizing at a doubled badge). Strip a label badge by its **text content with optional/repeating markup**, never by exact HTML element *(inferred from a self-stacking badge in Hub Inspector, firmware not recorded)*. Over HTTP the HTML survives: a Done POST that sent the label back with its `<span>` kept it *(probed 2.5.2.135, throwaway app)*, so the stripping, if it happens, is in the browser's handling of the label field; a search of `/ui2/js/appUI.js` found no label-stripping code *(source: appUI.js, 2.5.2.135)*.

## File Manager API

The file methods, the file-name rule and their signatures are documented (on-hub `shared-files`). There is no append and no rename, so adding a line means downloading the whole file and uploading it again: `appendHubFile`, `appendToHubFile` and a three-argument `uploadHubFile` throw `MissingMethodException` *(probed 2.5.3.102, C-8 Pro, throwaway driver)*. For a missing file, `downloadHubFile` threw `java.nio.file.NoSuchFileException` on a C-7 and on a C-8 Pro, although the docs said it returns null *(probed 2.5.2.129–2.5.2.135; false 2.5.3.102)*. From 2.5.3 it returns null, as the docs say *(probed 2.5.3.102, C-8 Pro, throwaway app and driver; docs: on-hub shared-files)*. Code that runs on both treats a null return and `NoSuchFileException` the same way.

The name rule and what each call does with a bad name differ *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway app and driver)*:

| Call | Missing file | Bad name (`a b.txt`, `x/y`, `é`) | `.hidden` | `""` | null |
|---|---|---|---|---|---|
| `uploadHubFile` | creates it | ignored, nothing written | `IllegalArgumentException` | `FileSystemException` | `NullPointerException` |
| `downloadHubFile` | `NoSuchFileException` (the name as message) up to 2.5.2; null from 2.5.3 | `IllegalArgumentException` | not tested | `FileSystemException` | returns null |
| `deleteHubFile` | nothing | `IllegalArgumentException` (`é` tested) | not tested | not tested | nothing |

The `IllegalArgumentException` message is "Invalid file name {name} valid characters are: a-z, A-Z, 0-9, - and _"; dots inside a name (`zz..txt`) are accepted. `getHubFiles()` returns an ArrayList of `com.hubitat.hub.service.fileManager.FileManagerEntry` whose `name`, `type` (`file`), `size`, `date` (epoch milliseconds) and `id` are all Strings, readable by property or subscript (`entry["name"]`); `toMap()` has the keys `id`, `type`, `name`, `size`, `date`. A folder that does not exist lists nothing. An empty byte array writes an empty file, and null bytes do not throw *(probed 2.5.2.135, throwaway app)*.

Append cost grows with file size: a one-row append took about 11 to 17 ms at 1 KB and 200 to 390 ms at 8 MB in an app on a C-8 Pro or a C-7, and copying the byte arrays directly was faster than the usual logger pattern (`new String(bytes) + row`, `getBytes()`) at larger sizes. Rule Machine's "Append to local file" (`actSubType` `getAppendLocalFile`) also slows with file size, so it rewrites the whole file as apps must. It appends the text with no newline *(probed 2.5.2.129, throwaway app)*.

Two writers appending to the same file at once lose rows with no exception: both download the same content and the last upload wins (C-8 Pro, 1 KB to 4 MB, every burst lost all rows but one) *(probed 2.5.2.129)*. `singleThreaded: true` prevents this inside one app only; nothing in the sandbox locks a file across apps *(inferred from the File Manager API, which has no lock or append)*.

Appends from several apps to their own files slow each other down, and past a few MB in flight the time per append jumps to about 2 s (C-8 Pro) or 3 s (C-7), up to 8.6 s and 7.1 s at 4 MB with 8 files at once. The upload step grows with the number of concurrent uploads even at 1 KB, so File Manager writes appear to be serialized hub-wide. The cause (garbage collection, a write lock) is not verified *(probed 2.5.2.129, throwaway app)*.

## Built-in app names

- Match built-in apps by app-type id, not by name: names change, and community apps can share them. Firmware 2.4.2.128 swapped the HomeKit app names and 2.4.2.129 reverted the swap *(staff: [gopher.ny 2.4.2.128](https://community.hubitat.com/t/154531/4), [gopher.ny 2.4.2.129](https://community.hubitat.com/t/154531/5))*. On 2.5.2.129 "HomeKit Bridge" exposes hub devices to Apple Home and "HomeKit Controller Integration" controls HomeKit accessories from the hub *(probed 2.5.2.129, `/hub2/appsList`)*. Shelly, UniFi Network (2.4.3.122) and MQTT (2.4.4.151) became built-in apps that can coexist with community apps of the same name *(staff: [gopher.ny 2.4.3.122](https://community.hubitat.com/t/157204/1), [gopher.ny 2.4.4.151](https://community.hubitat.com/t/161597/8))*.
- HomeKit Controller Integration runs only on a C-8 Pro. It arrived in 2.4.2.119 marked "requires C8 pro hub" *(staff: [gopher.ny 2.4.2.119](https://community.hubitat.com/t/154531/1))*. Installing it on a C-7 shows "Incompatible: This integration works only with hub revisions C8 Pro and newer." *(probed 2.5.2.139, C-7)*
- `hubitat.helper.NetworkUtils.startReolinkDiscovery()` and `getReolinkDiscoveryStatus(scanId)` (on-hub `api-hubitat-helper-networkutils`): the status goes `running`, then `complete`, and an unknown scan id reports `expired` *(probed 2.5.2.129, throwaway app)*. Gate on firmware 2.5.2.122 or later and also catch `MissingMethodException` *(unmarked)*.
