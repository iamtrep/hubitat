# Hubitat internal hub APIs

The hub as a client off the hub sees it: the admin HTTP endpoints, the websockets and the Diagnostic Tool on port 8081, with their payloads, authentication and status codes, and hub behavior that shows only through them. What Groovy code running on the hub can do is in [platform notes](hubitat-platform-notes.md); when an app calls one of these endpoints over loopback, the endpoint is described here and the in-app behavior there.

Hubitat documents only Maker API. The other endpoints drive the hub's admin UI, are unsupported and can change between firmware versions. Every fact carries an evidence mark ([EVIDENCE.md](EVIDENCE.md)).

`{hub_ip}` below is a placeholder for the hub's LAN address.

## Read-only inventory endpoints

- `GET /hub2/hubData` — hub metadata: `name`, `model`, `version` (firmware), `ipAddress` — no auth required *(probed 2.5.2.135)*. Carries no hub-security setting: `baseModel.userLoggedIn` is **session state** ("this request is authenticated"), not "security is enabled" — it reads `false` on a hub with security off *(probed firmware not recorded, hub security off; community: [thebearmay's Hub Information driver](https://github.com/thebearmay/hubitat/blob/main/hubInfoV3.groovy))*. To read the setting, use the `/logout` probe under [App configuration](#app-configuration-addremove-devices-change-settings) *(inferred: the `/logout` bullet)*.
- `GET /hub2/userDeviceTypes` — list user drivers (includes `usedBy` with device IDs/names) *(probed 2.5.2.135)*
- `GET /hub2/userAppTypes` — list user app types *(probed 2.5.2.135)*
- `GET /hub2/appsList` → `systemAppTypes[]` lists the built-in app types (`id`, `name`, `description`, `category`, `menu` = `Apps` / `Automations` / `Integrations`, `deprecated`, `allowNewInstances`); the Add Built-In dialogs show the ones not `Hidden` or deprecated. `userAppTypes[]` has the same shape for user code, and `apps[]` is the installed-app tree *(probed 2.5.2.129)*.
- `GET /hub2/devicesList` — list all devices *(probed 2.5.2.135)*. Each entry's `data` carries `dni`, `type` (the driver name) and `currentStates` as a list of `{key, value}` *(probed 2.5.2.139, C-7)*.
- `GET /driver/ajax/code?id={ID}` — get driver source + version: keys `id`, `source`, `status`, `version` *(probed 2.5.2.135)*
- `POST /driver/ajax/update` — push driver code (id, version, source form-encoded) *(unmarked)*
- Same pattern for apps: `/app/ajax/code`, `/app/ajax/update` *(probed 2.5.2.135)*
- `GET /hub/mdnsDevices` (firmware 2.5.0.126+) — services the hub has discovered via mDNS/Bonjour on the LAN (pre-commissioning visibility — HomeKit accessories, ESPHome devices, printers, AirPlay receivers, integration bridges). Response shape not yet HAR-verified; capture before parsing *(staff: [gopher.ny](https://community.hubitat.com/t/release-2-5-0-available/163415/3))*.
  - mDNS is **always on** — the hub is a permanent mDNS/Bonjour responder (HomeKit and Hub Mesh depend on it); there is no disable *(unmarked)*. The only toggle is **`restartBonjourOnSchedule`** (bool) on `GET /hub2/networkConfiguration` (firmware 2.3.9.184) — "periodically restart Bonjour," recommended OFF (periodic restarts trigger a LAN multicast storm). Neither `/hub2/hubData` nor `/hub/details/json` carries the flag *(probed 2.5.1.129)*.
  - `GET /hub/details/json` carries **`mdnsName`** — the advertised `.local` name (e.g. `hub-<name>`). Only mDNS field there; not an enable/disable flag *(probed 2.5.2.135)*.
- **Wi-Fi: no channel or signal is exposed** *(absent 2.5.2.134, C-8 Pro on Ethernet: admin bundles, Groovy API reference, native MCP, thebearmay's endpoint list, the forum's endpoint wiki and search, guessed paths)*. `GET /hub2/networkConfiguration` gives `hasWiFi`, `wifiDriversInstalled`, `wifiMessage`, `wlanAddr` and `wifiNetwork` (both `null` when not on Wi-Fi). `hasWiFi` is `false` on a C-8 Pro that has the radio but uses Ethernet, so it is not a capability flag, although thebearmay's Hub Information driver reads it as one. `GET /hub2/availableWiFiNetworks?reload=true|false` runs the Wi-Fi setup scan (~2.5 s) and returns a **plain list of SSID strings**: no channel, band, RSSI or BSSID. `GET /hub/advanced/getWiFiNetworkInfoAsyncStatus` only reports the progress of a join. `/hub/advanced/setWiFiNetworkInfo[Async]?ssid=&psk=`, `deleteWiFiNetworkInfo` and `disconnectWiFi` change the connection. Guessed read-only paths (`/hub/advanced/getWiFiNetworkInfo`, `wifiStatus`, `/hub2/wifiInfo`) are 404 *(probed 2.5.2.134, C-8 Pro and C-7)*.
- **IP settings: no endpoint exposes the DHCP lease's netmask** *(absent 2.5.2.134, C-8 Pro on DHCP: `networkConfiguration`, `ipSettings`, the admin network drawer)*. In `GET /hub2/networkConfiguration`, `staticGateway`/`staticSubnetMask`/`staticNameServers` are the saved static-IP form values, not the live config: on a DHCP hub `staticGateway` can name a different host than the real gateway. `dnsServers` (= `dhcpNameServers` under DHCP) is live. `GET /hub/advanced/ipSettings` returns the applied static settings on a static hub *(staff: [gopher.ny](https://community.hubitat.com/t/84194/15))* but only `{"status":"dhcp"}` under DHCP. `GET /hub/networkTest/ping/gateway` pings the **live** gateway (plain-text ping output, first line `PING <gateway-ip> …`, ~2 s), the only source found for it; it follows the real default route, not an `x.x.x.1` guess or the `static*` fields *(probed 2.5.2.134, C-8 Pro on DHCP)*.
- `GET /hub/zigbee/getChildAndRouteInfoJson` — the coordinator's own Zigbee tables. Response `{status, devices, children, neighbors, routes}`: `neighbors` is the coordinator's neighbor table (`{id, lqi, age, inCost, outCost}`), `routes` its routing table (`{id, nextHopId, used, status, age, routeRecordState, concentratorType}`), `children` its directly-parented end devices. This is the **coordinator's view only** — asymmetric; to learn how another router sees the coordinator you must still ZDO-probe that router *(probed firmware not recorded)*. The response also carries `topologyRefreshing` (boolean) and `topologyLastUpdated` (epoch ms). The first read of a session returned empty `neighbors` and `routes` with `topologyRefreshing: true` and `topologyLastUpdated: 0`, and a read 4 s later had 16 neighbours and 16 routes. Later reads showed `topologyRefreshing: true` next to full tables, so the flag alone does not mean the tables are empty. On a mesh of about 112 devices the rebuild took more than 15 s, and in one run the tables were still empty after 15 s; a read about 2 minutes later returned 16 neighbours. An unused `routes[]` slot is `{used: false, status: "Unused"}` *(probed 2.5.2.139, C-7)*.
- `GET /hub/zigbeeDetails/json` returns top-level `channel`, `panId`, `extendedPanId`, `powerLevel`, `networkState` and more, and `devices[]` entries `{id, name, type (driver name), lastMessage, ping, messageCount, shortZigbeeId, zigbeeId, lastActivity, active}` *(probed 2.5.2.139, C-7)*. The top-level keys are `channel`, `panId`, `extendedPanId`, `weakChannel`, `enabled`, `networkState`, `inJoinMode`, `firmwareUpdateInProgress`, `firmwareUpdateAvailable`, `channels`, `healthy`, `devices`, `showPowerSelection`, `powerLevel`, `powerLevels`, `showReboot`, `showRebuild`, `showRebuildNetworkOnReboot`, `rebuildNetworkOnReboot`, `showInactiveDevicePing` and `inactiveDevicePingEnabled`. None holds the hub's own IEEE; an app reads it from `location.hub.zigbeeEui` (see platform notes) *(probed 2.5.2.139, C-7)*. `lastMessage` has the form `yyyy-MM-dd'T'HH:mm:ssZ` with a `+0000` offset (no colon), and is null for some devices whose `lastActivity` is set (4 of 54 on one hub). A device entry has no power-source field, and `ping` was true for all 54 devices, mains and battery alike *(probed 2.5.2.139, C-7)*.
- `GET /hub2/chart/data?deviceId={id}&attribute={name}` (firmware 2.5.0.135+) — historical attribute trace from a **separate** store than the main events DB; retention 31 days OR 1000 values, whichever caps first. Independent of events-DB churn — useful when the events store has been compacted but a long-window trace is still wanted. Response shape not yet HAR-verified *(staff: [gopher.ny](https://community.hubitat.com/t/release-2-5-0-available/163415/4))*.
- `GET /hub/zigbee/healthStatus` and `GET /hub/zwave/healthStatus` (firmware 2.4.1.154+) — dedicated per-radio health probes *(staff: [gopher.ny](https://community.hubitat.com/t/release-2-4-1-available/152087/5))*. **Response is a plain text body of `true` or `false`**. Content-Type is `text/html;charset=utf-8` — misleading, the body is the literal text `true`/`false`, NOT JSON *(probed 2.5.0.143)*. Use for cheap up/down badges; use `/hub/zigbeeDetails/json` / `/hub/zwaveDetails/json` when per-device mesh info is needed.

- **Small read endpoints** *(probed 2.5.2.135, C-8 Pro)*, with the format each answers:
  - `GET /modes/json` → `{modes: [{id, name, icon, conditions: []}], currentModeId, selectedModeManager: "builtIn", modeManagerAppId, legacyModeManagerAppId, easyModeManagerAppId}` *(probed 2.5.2.135, C-8 Pro)*.
  - `GET /hub/messages` → `{messages: [String], mode: {locationId, id, icon, name}, hsm: null, hsmAlert: null}` *(probed 2.5.2.135, C-8 Pro)*.
  - `GET /hub/cloud/checkForUpdate` → `{"status":"NO_UPDATE_AVAILABLE"}` on the newest build, otherwise `{version, upgrade, releaseNotesUrl, hubCount, accountEmails: [String], status, beta}` *(probed 2.5.2.135, C-8 Pro)*.
  - `GET /hub/cpuInfo` → `text/plain`, `Processors 4` and `Load Average 0.27` on two lines, a trailing newline, the load unrounded (`0.6399999999999999`). *(probed 2.5.2.135, C-8 Pro, a blank hub and a hub in daily use)*
  - `GET /hub/advanced/*` answers plain text, not JSON: `stateCompressionStatus` `disabled`, `databaseSize` `2` (unit not found), `internalTempCelsius` `35.0`, `event/limit` `Maximum event count: [11]`, `maxEventAgeDays` `31`, `maxDeviceStateAgeDays` `7`, `ntpServer` `No value set`, `getExcessiveLoadThreshold` `33`, `zipgatewayVersion` `7.18.3`, `getLimitedAccessAddresses` `<html><body>no limit set</body></html>`, `getDNSFallback` `true`, and `freeOSMemoryLast` and `freeOSMemoryHistory` as CSV (`Date/time,Free OS,5m CPU avg,Total Java,Free Java,Direct Java`, then `MM-dd HH:mm:ss,<KB>,<load>,<KB>,<KB>,<KB>` rows, one row for `Last`). `GET /hub/allowSubnets` answers `Not set` or a comma-separated list of subnets. *(probed 2.5.2.135, C-8 Pro, a blank hub and a hub in daily use)*
  - `getExcessiveLoadThreshold` is the "App N generates excessive hub load" limit, in percent of uptime since boot, and answered `33` on C-7 and C-8 Pro hubs *(probed 2.5.2.129–2.5.3.103, five hubs)*. What the limit does to app code is in the platform notes, under the pending-events bullet.
  - `GET /hub/advanced/setExcessiveLoadThreshold/{n}` stores a new threshold and answers `done, reboot the hub to apply`; the getter keeps answering the old value until the reboot, and the new value survives later reboots. Outside 20 to 100 it answers `Excessive load threshold must be between 20 and 100` *(probed 2.5.2.139, C-8 Pro)*.
  - `GET /hub2/networkConfiguration` also carries `lanAutoneg`, `hubVersion`, `wifiDriversInstalled`, `hasEthernet`, `hasWiFi` and `restartBonjourOnSchedule`; `GET /hub2/hubMeshJson` has `hubList`, `modeHubId`, `sharedDevices`, `hubMeshToken`, `fullRefreshInterval`, `hubMeshEnabled`, `privateDevices`, `availableLinkedDevices`, `localLinkedDevices`, `migrationSourceHubs`, `migrationDestinationHubs` and four hub-variable lists. *(probed 2.5.2.135, C-8 Pro, a blank hub and a hub in daily use)*
  - `GET /hub2/cloudBackups` → `{backups: [{type: "cloud", hubUID, hubVersion, platformVersion, createTime, createTimeSort, createTimeOrig, fileSize, path, thisHub, canDelete, ...}], message, zigbeeDisabled, zwaveDisabled, zwaveJsEnabled, fullLocalBackupSupported, hasCloudBackupEntitlements, ...}`; `GET /hub2/userBundles` and `/hub2/userLibraries` → `[]` with none installed, else lists of `{id, name, namespace, ...}`; `GET /hub/matterDetails/json` → `{enabledByPreference, installed, enabled, installFailed, installInProgress, rebootRequired, threadReadyForPairing, networkState, ipAddresses: [{interface, address}], fabricId, devices: []}`. *(probed 2.5.2.135, C-8 Pro, a blank hub and a hub in daily use)*
  - `GET /hubMesh/localLinkedDevice/{id}` → a JSON object (`deviceId`, `hubName`, `deviceDisplayName`, `deviceType`, `deviceAttributeStates`, `deviceCommands`, ...) for a device, `{}` for an unknown id *(probed 2.5.2.135, C-8 Pro)*.

## LAN messages to a driver (port 39501)

- The hub listens for HTTP on TCP port 39501 (`location.hub.localSrvPortTCP`, a String). A request from an address whose upper-case hex is a device's network id (`192.0.2.10` is `C000020A`) is handed to that device's driver `parse()` as a description; the sender gets `200` with the single header `Connection: Close` and an empty body *(probed 2.5.2.135, C-8 Pro, throwaway driver, requests sent from a machine on the LAN)*.
- The description is `mac:<sender MAC>, ip:<hex ip, lower case>, port:<sender's port in hex>, headers:<base64>, body:<base64>` (`body:` empty without a body). The header block starts with the request line cut at the first `?` (the query string does not arrive) and lists the headers in the iteration order of a Java `HashMap` keyed by name (`User-Agent`, `Connection`, `Host`, `Accept-Encoding`, ... for Python's urllib), not the order sent *(probed 2.5.2.135, C-8 Pro, throwaway driver)*. `parseLanMessage` in the driver decodes it, see [platform notes](hubitat-platform-notes.md#lan-messages-raw-sockets-and-ping) *(probed 2.5.2.135, C-8 Pro, throwaway driver)*.
- A request from the hub itself reaches a driver too. An app's `asynchttpPost` to `http://<the hub's LAN address>:39501/` is handed to the device whose network id is that address in upper-case hex, and one to `http://127.0.0.1:39501/` to the device with id `7F000001`. The description then starts `mac:null` (the text `null`, so `parseLanMessage` gives `mac` as `"null"`), followed by `ip:` as lower-case hex of the sender address and the sender's port in hex; an empty body leaves `body:` empty and `parseLanMessage(...).body` null. With no device of that id nothing is delivered and the sender still gets 200. The caller's callback gets status 200 with a null body *(probed 2.5.2.135, C-8 Pro, throwaway app and driver)*.

## Radio health and topology

- The radio **detail** endpoints (`/hub/zigbeeDetails/json`, `/hub/zwaveDetails/json`, `/hub/zigbee/getChildAndRouteInfoJson`, the `healthStatus` probes above) read **cached** state — they do NOT poke the radio chip, so calling them is cheap and safe *(unmarked)*. `getChildAndRouteInfoJson` is the exception: it can return empty tables while the hub rebuilds them (see its bullet above) *(probed 2.5.2.139, C-7)*.
- **Radio reboots logged in `/hub/eventsJson` indicate hub-wide overload, not a radio fault** — an overloaded hub can't service the Zigbee NCP heartbeat in time, the NCP times out, and the firmware reboots the radio to recover. Investigate broad resource use (blocking sync HTTP on the app thread, multi-MB file I/O, heavy JSON parse), not the radio or specific endpoints *(unmarked)*.
- **A radio that goes offline and stays offline is a different failure.** On a C-7 (2.5.2.134), the Zigbee radio went offline with CPU, memory and temperature at their normal levels, and it stayed offline until a hub reboot. The hub logged one hub event (`zigbeeStatus` = `offline`) and one location event (`zigbeeOff`, "Zigbee radio is offline"). No `zigbeeOn` followed, not even after the reboot brought the radio back, so read the radio state after `systemStart`; there is no event to wait for. While the radio was down, the nightly local backup and the weekly cloud backup did not run, and after about 14 h Zigbee device commands began throwing `java.lang.IllegalStateException: Queue full` *(probed 2.5.2.134, C-7, hub and location event logs)*.
- **`GET /hub/rebootZigbeeRadio` restarts only the Zigbee radio.** It is the Zigbee settings page's "Reboot radio" button, which the page shows only when `/hub/zigbeeDetails/json` has `showReboot: true` *(source: vue-hub2-zigbee-info.min.js, 2.5.2.135)*. Hubitat's [Zigbee Details docs](https://docs2.hubitat.com/en/user-interface/settings/zigbee-details) say Reboot radio and Rebuild network are not available on the C-7 and earlier. `showReboot` and `showRebuild` are true on a C-8 Pro with the radio up, false on a C-8 Pro with Zigbee disabled, and false on C-7s. The call blocks for about 7 s and returns the text `done`, with the radio already back `ONLINE`. It logs **no** hub event and **no** location event (`zigbeeOff`/`zigbeeOn`), so detect recovery by polling `networkState` or `/hub/zigbee/healthStatus`. Not tested on a C-7 or with a dead radio *(probed 2.5.2.129 and 2.5.2.135, C-8 Pro and C-7; docs: [Zigbee Details](https://docs2.hubitat.com/en/user-interface/settings/zigbee-details))*. The same page also calls `/hub/zigbee/enable/{true|false}`, `/hub/rebuildZigbeeNetwork` and `/hub/zigbee/reset` *(source: vue-hub2-zigbee-info.min.js, 2.5.2.135)*; **reset erases the Zigbee network** *(unmarked)*.
- **`GET /hub/advanced/dumpThreadsToLog`** returns `done` and writes a JVM thread dump to the engineering logs that Hubitat staff read. Nothing appears in the user-visible logs (`/logs/past/json`) *(probed 2.5.2.135)*.
- **`GET /hub/zigbeeChannelScanJson` includes the hub's own network.** It runs a live active scan (~15–30 s) and returns a JSON list with one entry per (channel, PAN): `{channel, panId, extendedPanId, lastHopRssi, lastHopLqi, …}`, and empty entries for channels where nothing answered. The hub's own PAN shows up on its own channel, answered by its own routers, so filter it out by matching `panId`/`extendedPanId` from `/hub/zigbeeDetails/json` before counting neighbour networks *(probed 2.5.2.134)*. The scan's `extendedPanId` is byte-reversed relative to `/hub/zigbeeDetails/json` (`0011223344556677` there, `7766554433221100` in the scan); `panId` is in the same form in both *(probed firmware not recorded, C-7, cached scan compared on 2.5.2.139)*.
- **Z-Wave controller is node 01** (hex `01`) — the coordinator, not a paired device. It is **absent** from `/hub/zwaveDetails/json` (`zwDevices` / `nodes` list paired devices only; on a hub with no nodes they are `{}` and `[]`) but **present** in `/hub/zwaveTopology`, an HTML table, as its first row and column (the only ones on a hub with no nodes) *(probed 2.5.2.135, C-8 Pro with no Z-Wave nodes)*. Treat `01` as "Hub"; don't expect it in device lists or synthesize a Hubitat `deviceId` for it.
- **`/hub/zwaveTopology` is one row per node, and each row is that node's own neighbour list.** The page is an HTML table: a header row of hex node ids, then per node a row of `bgcolor` cells, `blue` = neighbour, `red` = not, `white` = the node itself; body rows have no `</tr>`. The same markup comes back on the Z/IP and Z-Wave JS stacks *(probed 2.5.2.139, two Z/IP hubs and one Z-Wave JS hub)*. The matrix is not always symmetric: on one 11-node Z/IP mesh, two pairs were listed by one side only. On Z/IP, the count of blue cells in a row equals that node's `zwaveDetails.nodes[].neighbors`, including the two nodes whose column count differs, so the row, not the column, is the node's list *(probed 2.5.2.139, two Z/IP hubs, 15 nodes)*. On Z-Wave JS, `nodes[].neighbors` is not a neighbour count: a 4-node mesh reported 11, 10 and 10 where the matrix rows hold 3, 2 and 2 *(probed 2.5.2.139, Z-Wave JS)*; count the matrix row instead. What the JS value means is unknown.
- **`/hub/zwaveDetails/json` has two node lists that can disagree.** `nodes[]` is the radio's view (`nodeId`, `deviceId`, `route`, `nodeState`, `lwrRssi`, `per`, `neighbors`); `zwDevices` is the Hubitat device database, keyed by decimal node id, each value a device record whose `id` is the device id (`name`, `label`, `deviceNetworkId`, `deviceTypeId`) — it has no route or state fields *(probed 2.5.2.129, Z/IP stack)*. **Z-Wave Long Range nodes are absent from `nodes[]`** on the Z/IP stack: a USLR hub on Z/IP Gateway 7.18.3 listed two working LR devices (node ids 270, 271; DNIs `010E`, `010F` — 4 hex digits, vs 2 for mesh nodes) in `zwDevices` only, so the hub reports no RSSI/PER for them *(reported: a user's export, hub firmware not reported)*. So a device with no `nodes[]` row is not a ghost; a ghost is a `nodes[]` row with no `deviceId` *(inferred: the two lists above)*. Whether the Z-Wave JS stack also omits LR nodes is unverified (no LR hardware to test). On Z/IP, `lwrRssi` is a positive string like `"31dB"` — not dBm *(probed 2.5.2.129, Z/IP stack)*.
- **`/hub/zwaveDetails/json` names the Z-Wave stack in four top-level keys:** `zwaveJS` (true on Z-Wave JS), `zwaveJSVersion` (null on Z/IP), `zwaveJSReady` and `zwaveJSInstallationValid`. Two Z/IP hubs return `zwaveJS: false`, `zwaveJSInstallationValid: false`, `zwaveJSReady: true`, `zwaveJSVersion: null` *(probed 2.5.2.139, two C-7)*. A `zwaveJSAvailable` key was returned *(probed 2.5.2.135, C-8 Pro)* and is gone *(false 2.5.2.139, 2.5.3.105)*; code that reads it gets null.
- **`nodes[].listening` differs by stack.** On Z/IP, sleeping battery sensors have no `listening` key at all, while mains devices and FLiRS door locks report `true` *(probed 2.5.2.129, C-7, Z/IP stack)*. On Z-Wave JS, mains devices report `true`, FLiRS door locks report `false`, and each node also carries `batteryPercent` (`null` on a node that doesn't report one) *(probed 2.5.2.139, C-7, Z-Wave JS)*. So `listening != true` marks a battery node on both stacks; Z/IP FLiRS locks are the miss *(inferred: the two probes above)*. This matters where the driver has no Battery capability, such as the built-in **Aeon Minimote** driver, which declares only Actuator, Configuration, PushableButton and HoldableButton, so its devices never get a `battery` value *(probed 2.5.2.139)*.
- `GET /hub/zwave2/getControllerState` (Z-Wave JS stack only) returns the controller identity + live statistics as JSON: `firmwareVersion`, `sdkVersion`, `homeId`, `ownNodeId`, `isPrimary`/`isSUC`/`isSISPresent`, `rfRegion`, `supportsLongRange`, and a `statistics` map (`messagesRX`/`TX`, `messagesDroppedRX`/`TX`, `CAN`, `NAK`, `timeoutACK`/`Callback`/`Response`, `backgroundRSSI`). It is the **only** source of these — `/hub/zwaveDetails/json` carries nodes/region/`firmwareVersion`/`zwaveJSVersion` but no controller identity or stats. Gate on the stack probe `GET /hub/zwave2/status` → body `true` (legacy Z/IP hubs return `false`); `sdkVersion` and `firmwareVersion` here describe the **radio chip** (Silicon Labs SDK / module firmware), distinct from the node-zwave-js library version in `zwaveDetails.zwaveJSVersion` *(probed firmware not recorded, C-8 Pro on Z-Wave JS)*.
- **`getControllerState` quirk — bare `null` body on some hubs:** at least one C-8 Pro (firmware 2.5.1.134, ZWave-JS 15.25.3) with a healthy 57-node mesh returns the literal body `null`, reproduced hitting the URL **directly in a browser** — so it is endpoint-intrinsic, not app concurrency or SPA load (the same call returns the full object under rapid/concurrent requests on a 0-node C-8 Pro) *(reported: a user's C-8 Pro on 2.5.1.134, reproduced in a browser; probed firmware not recorded, 0-node C-8 Pro)*. `null` is valid JSON but a scalar, so `httpGet` with `contentType:"application/json"` throws `groovy.json.JsonException` (`payload should start with { or [`) on parse — handle it as **no data available**, not a fault. `zwaveDetails/json` and `zwave2/status` still return normally on the same hub, so node/mesh/version data is unaffected. Cause is a platform/hub-side quirk, unrecoverable from an app *(inferred: the endpoint answers `null` outside any app)*.
- The `null` body also occurs on a **C-7** (2.5.2.134, ZWave-JS 15.29.0, 3 nodes) right after a migration from Z/IP to JS, so it is not specific to the C-8 Pro or to large meshes *(probed 2.5.2.134, C-7, ZWave-JS 15.29.0)*.
- **The `null` goes with an empty hub-side controller cache** *(probed 2.5.2.134, C-7 and C-8 Pro, ZWave-JS 15.29.0)*. On the C-7 returning `null`, `zwaveDetails/json` also has `firmwareVersion: null` and `longRangeChannel: null`, and `GET /hub/zwaveVersion` is 404. A C-8 Pro returning the full object has `firmwareVersion: "7.23.4"`, `longRangeChannel: 255` and `/hub/zwaveVersion` → `7.23`. **A plain reboot restores it** *(probed 2.5.2.134, C-7)*: the C-7's only boot since the Z/IP → JS switch had been the switch's own reboot; after a separate reboot, once `zwaveJSReady` (~2.5 min), `getControllerState` returned the object (`firmwareVersion: "7.18"`, `rfRegion: 9`), `/hub/zwaveVersion` → `7.18`, and `zwaveDetails` had `firmwareVersion: "7.18.1"`, `longRangeChannel: 1` (the settings page shows "Channel B" and the "Firmware version:" line again). So the cache is filled at Z-Wave JS startup and was left empty by the migration boot. The radio itself is fine: `GET /hub/zwave2/getNodeState?node=1` (the controller node) returns `firmwareVersion`/`sdkVersion` (`7.18.1` there), `ready: true`, `interviewStage: "Complete"` and a `statistics` map (`commandsRX`/`TX`, `commandsDroppedRX`/`TX`, `timeoutResponse`) on both hubs *(probed 2.5.2.134, C-7 and C-8 Pro)*. Users can see the cache state: the Settings → Z-Wave page prints a "Firmware version:" line only when `zwaveDetails.firmwareVersion` is set (`vue-hub2-zwave-info.min.js`), so on the two JS hubs tested, a page with only "ZWave-JS version:" matched the `null` hub *(source: vue-hub2-zwave-info.min.js, 2.5.2.134)*. The admin UI never calls `getControllerState` *(absent 2.5.2.135, the 17 admin bundles fetched, `vue-hub2.min.js` and the device, Zigbee and Z-Wave chunks)*, and Hubitat does not document it *(unmarked)*.
- **Not the cause: migration alone, a 7.18 radio, or an unfinished node interview** *(probed 2.5.2.129 and 2.5.2.134, ZWave-JS 15.29.0)*. A C-8 Pro on 2.5.2.129 with a 7.18 radio and no nodes, switched from Z/IP to JS (`GET /hub/zwave2/enable`, which reboots the hub), returned the full object with `firmwareVersion: "7.18"`; `zwaveDetails.firmwareVersion` became `"7.18.1"` about 2.5 min after the switch. On the affected C-7 every node reports `ready: true`, `interviewStage: "Complete"`. Still untested: a non-empty network at migration time *(probed 2.5.2.129, C-8 Pro; probed 2.5.2.134, C-7)*. A user-reported affected hub (2026-10-09) is a C-8 Pro on 2.5.2.134 with a 7.23 radio, US-LR and a 56-node mesh, switched from legacy, where `/hub/zwaveVersion` also fails (Hub Inspector's Radio Firmware tile reads N/A), so neither C-7 hardware, a region the chip can't use, nor the .134 build explains it; every hub seen returning the object had no Z-Wave nodes *(reported: a Hub Inspector user's C-8 Pro, 2.5.2.134)*. The affected C-7 reports region `USLR` while the Z/IP C-7s report `US`; setting it to `US` (UI, then `zwaveDetails/update?…&region=US` → `{"success":true}`) did not stick: it still read `USLR`, with `getControllerState` still `null`, 90 s later. After the reboot that restored the cache it still reads `USLR`, now with a Long Range channel, so the region was not the cause. Untested: whether every migration of a hub with nodes leaves the cache empty until the next reboot (the empty C-8 Pro's migration boot filled it) *(probed 2.5.2.134, C-7)*.
- **`zwaveDetails.firmwareVersion` is a JS-only field** *(probed 2.5.2.129 and 2.5.2.134)*: it is `null` on every Z/IP hub, whatever the radio. Under Z/IP, `GET /hub/zwaveVersion` answers with a non-JSON `VersionReport(zWaveLibraryType:7, zWaveProtocolVersion:7, zWaveProtocolSubVersion:18, firmware0Version:7, firmware0SubVersion:18, …)` string, or `No Z-Wave controller instance is available` when Z-Wave is disabled. Under JS it returns `7.23`-style text, or 404 on the affected hub. The radio on/off switch behind the Z-Wave settings page is `GET /hub/zwaveDetails/update?enabled=true&region=<region>&secureJoin=<n>` (plus `longRangeChannel` when shown) → `{"success":true}` *(probed 2.5.2.134, C-7)*; the page switches back to Z/IP with `GET /hub/zwave2/disable` (the hub reboots immediately, then `/hub/rebooting`) and calls `/hub/zwave2/enable` the same way *(source: vue-hub2-zwave-info.min.js, 2.5.2.135)*.
- **`zwaveDetails.nodes[]` field shapes differ by stack** *(probed 2.5.2.134, C-7, ZWave-JS 15.29.0)*. Under JS: `averageRtt` is a **decimal string** (`"41.7"`, ms), not an integer; `msgCount` is **not a radio message count** (it restarts at 0 on boot and moved on only some nodes; what it counts is unknown); `routeChanges` is the string `"N/A"`; `lwrRssi` is a **negative dBm string** (`"-86db"`), unlike Z/IP's positive `"31dB"`; JS rows add `interviewStage`, `interviewComplete`, `lastSeen`, `deviceName`, `zwaveManufacturer`. `GET /hub/zwaveVersion` returns **404** on JS (Z/IP returns a `VersionReport(...)` text) *(probed 2.5.2.134, C-7; probed 2.5.2.129, Z/IP)*.
- `GET /hub/zwave2/getNodeState?node=<decimal id>` (JS stack; not tried on Z/IP) returns the node-zwave-js node: `nodeState`, `status` (int), `interviewStage`, `ready`, `rssi` (`"-87db"`), `rtt` (decimal **string**), `per`, `route`, `lastSeenLocal`, `securityClass`, `keepAwake`, `isControllerNode`, a full `values[]` list, and `statistics` (`commandsTX`/`RX`, `commandsDroppedTX`/`RX`, `timeoutResponse`, numeric `rssi`/`rtt`, `lwr` route with `repeaters`/`protocolDataRate`). **`isFrequentListening` is a string** (`"1000ms"` on a FLiRS lock), not a boolean. Its `statistics` counters reset without a hub reboot: all three nodes went from 66–79 RX to 0 RX / 1 TX at about 03:03, with no `systemStart` event and nothing logged (one observation, 2026-10-09; cause unknown). It is the only per-node source of radio message counts on JS found so far: one call per node, about 20–28 KB (mostly `values[]`) and 0.5–0.8 s each on a C-7 *(probed 2.5.2.134, C-7)*. The admin Z-Wave Details page's "Msgs" column reads `zwaveDetails.nodes[].msgCount` on both stacks, so on JS it shows that count, not radio traffic; its "Refresh Z-Wave statistics" button calls `GET /hub/zwaveNodeDetailGet`, which did not change `msgCount` on JS (2026-10-08). Other read-only endpoints in the 2.5.2.134 admin bundles (`/hub/zwave/getChildAndRouteInfoJson`: nodes + route connectors; `/hub/zwave2/nodeDetails?node=`: command-class catalog) carry no counts, and `/logs/json` `deviceStats` counts driver executions, which stay 0 for system-driver locks on JS *(source: admin bundles, 2.5.2.134; probed 2.5.2.134, C-7)*.

## Platform versions and the Diagnostic Tool (port 8081)

The Diagnostic Tool is a separate Jetty process at `http://{hub_ip}:8081` (plain HTTP only, not relayed by `cloud.hubitat.com`). It keeps running when the main platform is down. Its UI asks for the hub's MAC address and stores the returned token in the browser's `localStorage` under `hubitat-diagnostic-tool-token`; the MAC is in `GET /hub/details/json` → `macAddress`, which needs an admin session when hub security is on. The two reads below answer **without** that login, on hubs with and without hub security. Both return `application/json`. CORS allows only `https://findmyhub.hubitat.com`, so a browser page served from the hub can't read them; call them server-side (an app's `httpPost` to `http://127.0.0.1:8081` works, sync and async) *(probed 2.5.1.183 and 2.5.2.124; docs: [Hubitat Diagnostic Tool](https://docs2.hubitat.com/en/user-interface/advanced-features/hubitat-diagnostic-tool))*.

- `POST :8081/api/versions`: platform versions stored on the hub and restorable from the tool, `{"success":true, "hubList":["hub-2.5.2.120", …], "currentVersionExecuting":"hub-2.5.2.124"}`. Strip the `hub-` prefix. `GET` returns 404 *(probed 2.5.1.183 and 2.5.2.124)*.
- `POST :8081/api/hubInfo`: `{hubId, uv, hasServices, hubAvailable, pv, ip, hubTime, hv, stableVersion}`. `pv` is the running platform (`hub-` prefixed), `hv` the hardware model, `uv` the tool's own version, `stableVersion` the fallback release the tool's "switch to stable" installs. `hubId` carries a trailing `\n` *(probed 2.5.1.183 and 2.5.2.124)*.

The tool's page (`/js/vue-updateTool.min.js`) makes these calls for its buttons *(source: vue-updateTool.min.js, tool 1.1.136, 2.5.3.103)*:

- `POST /newLogin`, body the MAC upper case without colons, `Content-Type: application/x-www-form-urlencoded`: `{"inProgress":false, "success":true, "message":"<token>"}` and a `UTSESSION` cookie. A wrong MAC answers HTTP 200 with `"success":false`. The page sends the token as `Authorization: Basic <token>` only to `GET /checkLogin`, which answers 200 with any token or none *(probed 2.5.3.103, C-8 Pro)*.
- Download Latest Version: `POST /api/updateTime` with the UTC time as text (`2026-10-17 21:5:9`, unpadded), then `POST /api/getLatest`, which answers `{"getLatest":"success"}` without a login. Progress is in `GET /setupStatus`, `{inProgress, success, message}`. When the latest public release is already stored it reports `"success":false` with the message `Latest version 2.5.2.139 is already installed`, the only place the tool names that version. It fetches the latest public release on a beta-enrolled hub too *(probed 2.5.3.103, C-8 Pro)*.
- Restore Previous Version: `POST /api/versions`, then `GET /api/switchVersion/hub-<version>`, which answers `{success, …}` and reboots the hub. The page then polls `GET /hubStartStatus`, `{inProgress, success, message}` *(source: vue-updateTool.min.js, tool 1.1.136, 2.5.3.103)*.
- `GET /api/switchToStable` installs `stableVersion` from `/api/hubInfo`, an older fallback build, not the latest release: 2.5.1.182 on a hub running 2.5.3.103 *(probed 2.5.3.103, C-8 Pro; source: vue-updateTool.min.js, tool 1.1.136)*.
- Other calls on the page: `/api/rebootHub`, `/api/shutdownHub`, `/api/safeMode`, `/api/softResetHub`, `/api/factoryResetHub`, `/api/resetZigbee`, `/api/resetZwave`, `/api/backups`, `/api/downloadBackup/`, `/api/downloadLatestBackup`, `/api/latestBackupFileInProgress`, `/api/currentTime` *(source: vue-updateTool.min.js, tool 1.1.136, 2.5.3.103)*.

Downloading a release so it becomes restorable is a main-platform endpoint:

- `GET /hub/advanced/downloadPlatform/{line}`: downloads the latest stable release of a version line and adds it to the `/api/versions` list. `{line}` is the line's digits without dots: `250` for 2.5.0.x, `234` for 2.3.4.x. The request blocks until the download completes (about 97 s on a C-8 Pro), then answers plain text `success`. An unknown line answers `incorrect version` immediately. Both are HTTP 200 with `text/html`, so check the body. The download drops free OS memory sharply (about 900 MB to 370 MB on a C-8 Pro). It is a GET that changes hub storage: call it from a button, never from a link that prefetching could follow *(probed firmware not recorded, C-8 Pro)*.

## Code push details

- POST body: `id={ID}&version={VERSION}&source={URL_ENCODED_SOURCE}` *(probed 2.5.2.135)*
- Use `--data-urlencode "source@{FILEPATH}"` to auto-encode file contents *(spec: curl manual, `--data-urlencode`)*
- Response: `{"id":..., "version":..., "status":"success"}` on success *(probed 2.5.2.135)*
- `POST /app/ajax/update` recompiles and re-reads `definition()`: on firmware 2.5.2.128 a push changed `category`, `description`, `menu`, `singleInstance` and `importUrl` with no Save in the editor. Read them back from `GET /app/list/single/data/{id}`. `oauth: true` in `definition()` does not enable OAuth on push or install; that takes the editor's OAuth button (`oauthClientId` stays null, `/hub2/userAppTypes` `oauth` stays empty). For apps, `singleThreaded` was not found on any endpoint on 2.5.2.128, so whether a push applies it is untested *(probed 2.5.2.128, throwaway app types)*. For devices, `/device/fullJson/{id}` exposes `device.deviceTypeSingleThreaded` and a driver push applies it at once (below) *(probed 2.5.2.139, C-7)*. A driver push likewise picks up new commands, capabilities and preference inputs on a device-page reload *(unmarked)*.
- A driver push whose `definition()` drops `singleThreaded: true` applies to the existing device at once: `/device/fullJson/{id}` showed `device.deviceTypeSingleThreaded` false right after the push, with no re-save *(probed 2.5.2.139, C-7)*.
- **`lastModified` moves on every successful code save, and only then.** In `/hub2/userAppTypes`, `/hub2/userDeviceTypes` and `/hub2/userLibraries` (`lastModified` and `updateTime`), it changed on `POST /{app|driver}/ajax/update` and on `POST /{app|driver|library}/saveOrUpdateJson` with an `id`, including a save of an identical source; it did not change on a save rejected for a compile error. A library save leaves its consumers' `lastModified` unchanged. The value is printed to the second (`2026-10-18T22:05:53+0000`), so two saves landing in the same second would carry the same value: code that keys a cached fact to `lastModified` should re-read an item whose fact was read within a second or two of it *(probed 2.5.3.103, throwaway app, driver and library types)*. Re-importing a bundle from its zip URL (`GET /bundle2/uploadZipFromUrl`) updates its members in place, keeping their ids, and moves `lastModified` on every member, including one whose source is unchanged *(probed 2.5.3.103, throwaway bundle of a library, a driver and an app)*. The importer can fetch a zip from the hub's own File Manager at `http://127.0.0.1:8080/local/<name>`; the same file by the hub's LAN address answered `Cannot retrieve zip file` *(probed 2.5.3.103)*. The code editor's Save button posts JSON to `/{app|driver|library}/saveOrUpdateJson` *(source 2.5.3.103, `/ui2/js/vue-hub2-{app|driver|library}-code-editor.min.js`)*.
- **`GET /hub2/userLibraries` is slow and carries no source.** Each entry has a `source` key that is `null`; the whole response for 26 libraries was 18 KB yet took 11–20 s, against under 1 s for the app and driver lists on the same hub *(probed 2.5.3.103)*.
- **An app type's OAuth can be turned on but not off.** `GET /app/updateOAuth?id=<type>&oauthEnabled=true` (what the code editor's OAuth dialog sends) and a `POST /app/edit/update` with `oauthEnabled=true` turn it on. `GET /app/updateOAuth` with `oauthEnabled=false` answers `{"success":true}` and leaves it on, a `POST /app/edit/update` without `oauthEnabled` leaves it on, and the editor offers no way to turn it off. `/hub2/userAppTypes` `oauth` is empty until it is turned on. An app that wants its endpoints closed revokes its token instead: once the filter's cache of a used token runs out, every request is refused *(probed 2.5.2.139, throwaway app type)*.

## Live logs and events

- `ws://{hub_ip}/logsocket` — WebSocket for real-time hub log stream (each frame's `msg` is HTML-escaped: `&amp; &lt; &gt; &quot; &apos;`; `/logs/past/json` keeps the text raw) *(probed 2.5.2.135)*
- `ws://{hub_ip}:80/eventsocket` — WebSocket for real-time device-state events (used by the admin UI). One text frame per event, a flat JSON object with this fixed key order *(probed 2.5.2.135)*:

  `{ "source":"DEVICE","name":"switch","displayName" : "Kitchen", "value" : "on", "type" : "null", "unit":"null","deviceId":795,"hubId":0,"installedAppId":0,"descriptionText" : "null"}` *(probed 2.5.2.135)*

  - **Every field except `deviceId`, `hubId` and `installedAppId` is a string.** A null `type`, `unit` or `descriptionText` arrives as the string `"null"`, and numbers as numeric strings (`"21.5"`). `hubId` and `installedAppId` were `0` on every frame, including a location event sent by an app and device events caused by a Maker API command; `deviceId` is `0` for a location event *(probed 2.5.2.135)*.
  - `source` is `DEVICE` or `LOCATION`. A location event (`sendLocationEvent(name:"probeEvt", value:"x")` from an app) carries the hub name in `displayName` *(probed 2.5.2.135)*.
  - The JSON is hand-formatted: `{ ` opening, spaces around some colons, non-ASCII in `displayName` and `descriptionText` escaped as `é` (upper-case hex), and `/` in values escaped as `\/`. `unit` was sent unescaped (`"°C"`). Parse with a JSON parser, never by string match *(probed 2.5.2.135)*.
  - **No `isStateChange`, timestamp, event id, or `physical`/`digital` flag.** `type` carries the `sendEvent` `type:` (`"physical"`, `"digital"`) or `"null"` *(probed 2.5.2.135)*.
  - **The socket sends every `sendEvent`, change or not.** A repeat of the current value is a normal frame, with or without `isStateChange: true`. The event history (`/device/eventsJson`) drops the repeat unless an app subscribes with `filterEvents: false`, in which case it is stored with `isStateChange: false`. Switching a subscriber between the two modes did not change the socket output. An attribute not declared in the driver's metadata is sent and stored as an event, but never appears in `currentStates` *(probed 2.5.2.135)*.
  - **No coalescing on the socket:** two events 0, 50 and 500 ms apart each arrived as two frames, in send order, a few ms after each `sendEvent`. Events get lost in the hub's own processing instead: two same-attribute `sendEvent`s, each a change, sent 0–1 ms apart in one execution left `currentStates` at the earlier value in 4 of 5 runs. When the second value equalled the value at the start of the execution, it was also missing from the event history (`off` then `on`, sent from `on`, left the device `off` with no `on` event). The socket showed both events every time. With a 20 ms pause between them the result was correct *(probed 2.5.2.135)*. A repeat with 200 runs per cell did not reproduce the 4 of 5: two changes sent with no pause left the earlier value in 5 and 7 of 200 runs, and in 0 of 400 with a pause of 1 ms or more; when the second value equalled the value before the first, the attribute stayed at the first value in 65 and 63 of 200 runs and the subscriber never saw the second event. The platform notes ("Two events on one attribute less than a millisecond apart can lose the second") give the rest *(probed 2.5.2.135, C-8 Pro, throwaway app and driver)*. In the repeat the socket carried both events, in the order sent, in 100 of 100 runs at 0 ms and in 100 of 100 at 1 ms, including the runs where the current value stayed at the first one *(probed 2.5.2.135, C-8 Pro, throwaway app and driver)*.
  - The socket is hub-wide (every device, no filter parameter) and sends nothing on connect: no snapshot, no hello frame *(probed 2.5.2.135)*.
- **All of these log/event/radio websockets accept the WS upgrade with NO auth** — `/logsocket`, `/eventsocket`, `/zigbeeLogsocket`, `/zwaveLogsocket` upgrade with no cookie or login handshake even on hub-security-enabled hubs (cookie auth only gates the plain HTTP `/` paths). External (Python/Node) tooling against a secured hub can use the socket path with no login code *(unmarked)*.
- `ws://{hub_ip}/zigbeeLogsocket` / `ws://{hub_ip}/zwaveLogsocket` — WebSocket streams of raw received radio frames (the hub's Zigbee/Z-Wave "logging" pages consume these). The Zigbee socket emits one JSON object per received frame: *(probed 2.5.0.146, C-7)*

  `{name, id (DNI as 16-bit int), profileId, clusterId, sourceEndpoint, destinationEndpoint, groupId, sequence, lastHopLqi, lastHopRssi, time ("YYYY-MM-DD HH:MM:SS.mmm"), type: "zigbeeRx", deviceId, payload: [hex-string bytes]}` *(probed 2.5.0.146, C-7)*

  - **Carries `sourceEndpoint` / `destinationEndpoint`** (2-hex strings, e.g. `"01"`, `"19"`, `"00"`). Without them, multi-endpoint devices (dual-relay plugs, multi-endpoint thermostats) are indistinguishable on the wire *(probed 2.5.0.146, C-7)*.
  - **`sourceEndpoint == "00"` marks a ZDO frame.** ZDO and ZCL cluster IDs overlap, so route endpoint-0 frames to a ZDO parser by endpoint, not by cluster ID *(probed 2.5.0.146, C-7; spec: Zigbee specification, ZDO cluster IDs)*. ZDO decoding, including routers that reply NOT_SUPPORTED to `Mgmt_Rtg_req`, is in [`hubitat-zigbee-helper.md`](hubitat-zigbee-helper.md) → ZDO responses.
  - **It can stop for every client while the radio keeps working.** On one C-7 the socket accepted connections but sent no frames to either of two clients for at least 17 minutes, while `/hub/zigbeeDetails/json` showed `lastMessage` moving on many devices, `networkState` `ONLINE` and `healthy` true, and `/logsocket` worked. Nothing was logged at error level. A hub reboot restored it; the cause was not found *(probed 2.5.2.139, C-7)*.
  - **All frames are `type: "zigbeeRx"`** — received by the hub (device→hub). The envelope carries endpoints but no src/dst node addresses, so direction is inferred from the ZCL frame-control direction bit, not the envelope *(probed 2.5.0.146, C-7)*.
  - **`zwaveLogsocket`** is the Z-Wave sibling socket. On the Z-Wave JS stack each frame is `{sourceLabel: "DRIVER"|"SERIAL"|"CNTRLR", plainTextMessage, deviceId, time}`, where `plainTextMessage` is zwave-js's rendered log text, wrapped at ~80 columns with continuation lines indented (wraps can split mid-word or mid-hex). `deviceId` is `-999` even for node traffic; the node shows only as a `[Node NNN]` tag (decimal, zero-padded) in the text. **The stream is lossy at the hub:** two clients connected at the same time receive byte-identical streams with the same lines missing (a 30 s `GetBackgroundRSSI` poll should log 8 lines; 4 to 7 arrive). Don't assume a request has its response, or a serial frame its ACK *(probed 2.5.2.134, C-8 Pro)*.

- `GET /hub/matterLogs/json` → `{"text": "<ANSI-colored CHIP/Matter SDK dump>"}` — **polling only, no socket** (the native page polls ~every 2 s). Each response is the **full rolling buffer** (no `offset`/`since`/`Range` params), so a live tail must dedup against the previous poll — anchor on a block of trailing lines (lines repeat verbatim), not single lines. CHIP line format (ANSI-stripped): `[<epoch>.<ms>] [<pid>:<tid>] [<COMPONENT>] <message>`, with indented multi-line continuations *(probed firmware not recorded, C-8 Pro)*.

### Logs page endpoints

The Logs page (`/logs`, tabs `?tab=past` etc.) is a Vue chunk (`/ui2/js/vue-hub2-logs.min.js`) that reads these:

- `GET /logs/json`: runtime stats since boot. Top-level `uptime`, `appStats[]`, `deviceStats[]`, `jobs[]`, `runningJobs[]`, `hubCommands`, `totalAppsRuntime`, `totalDevicesRuntime`, `appsUptime`, `devicesUptime`, `appPct`, `devicePct`, `maxEvents`, `maxStates`. Each stats entry: `id`, `name`, `total`, `count`, `average`, `pct`, `pctTotal`, `grandTotal`, `stateSize`, `largeState`, `hubActionCount`, `cloudCallCount`, `pendingEventsCount`, `customAttributes`. Each `jobs[]` entry: `id` (`app{id}Once.{method}`, `dev{id}Recur.{method}`), `name`, `link`, `recurring`, `methodName`, `nextRun`, `nextRunDt`. Slow on a loaded hub (15 s or more) *(probed 2.5.2.129)*.
- `GET /logs/past/json`: the hub's past-log buffer as a JSON array of strings, one per line: `"{yyyy-MM-dd HH:mm:ss.SSS}\t{LEVEL} \t{type}|{id}|{name}|{message}"`, where `type` is `app`, `dev` or `sys`. Covers several hours; read it instead of a live capture to answer "what logged in the last N minutes" *(probed 2.5.2.129)*. A message with line breaks takes one string per line, and the lines after the first are bare text with no time, level or source (a callback error ending in Groovy's `Possible solutions: ...` line) *(probed 2.5.2.135, throwaway app)*.
- `GET /logs/eventsJson` and `GET /hub/eventsJson`: event lists for the page's events views *(probed 2.5.2.129)*.
- `GET /logs/cloudCalls/json` (new in 2.5.2.129, 404 before): inbound cloud-relay requests per app, in hourly buckets. Backs the "Cloud calls" tab *(probed 2.5.2.129)*.

  `{apps: [{id, name, installed, total, currentHour}], hours: [{appId, hourStart, count}], startedAt, generatedAt, timeZone}` *(probed 2.5.2.129)*

  Times are epoch ms; `hourStart` is the bucket start. Counts start at `startedAt`, which looked like hub boot in one sample. Requests to an app ID that no longer exists still count: that app is listed with `installed: false` and `name: "Deleted app ({id})"`. The hub also logs each one as a `sys` WARN, `Received cloud request for App {id} that does not exist, path: {path} from {ip}`, where `{ip}` is the caller's public address. The caller can be the hub itself, for example a driver whose cloud-check URL still names the deleted app. A LAN DNS log for `cloud.hubitat.com` lookups on the same cadence identifies the device *(probed 2.5.2.129)*.

## App configuration (add/remove devices, change settings)

- `GET /installedapp/configure/json/{installedAppId}` — get full app config as JSON (inputs, settings, etc.) *(probed 2.5.2.135)*
- `POST /installedapp/update/json` — save app configuration. Content-Type must be **`application/x-www-form-urlencoded`** despite the `json` suffix; the `json` refers to the response format. Sending `application/json` returns HTTP 500 with no useful diagnostic *(probed 2.5.2.135)*.
- **Session cookie:** the hub sets a `HUBSESSION` cookie on its HTML pages, and on a hub without security POSTs work with no cookie *(probed 2.5.2.135, hub security off)*. With hub security on, log in and send the cookie with every request (`curl -c cookiejar -b cookiejar`) *(unmarked)*
- **Loopback bypasses hub security:** `http://127.0.0.1:8080` (same-hub app→app calls and `/installedapp/`, `/hub2/`, `/device/`, `/hub/*` from on-hub code) is NOT gated by hub security — only off-hub LAN-IP access is. An on-hub integration hitting loopback needs no credential handling *(unmarked)*.
- **Detecting whether hub security is enabled — no credentials needed:** on-hub, `GET http://127.0.0.1:8080/logout` with redirects disabled. `Location: http://127.0.0.1:8080/login` means security is ON; any other target means OFF. The OFF case answers 302 to `/` *(probed 2.5.2.113)*; the ON case is taken from thebearmay's Hub Information Driver v3, which ships this probe as its `securityInUse` attribute (`hubInfoV3.groovy`, `checkSecurity()`/`getSecurity()`, added v3.1.7) — not independently re-verified here *(community: [hubInfoV3.groovy](https://github.com/thebearmay/hubitat/blob/main/hubInfoV3.groovy))*. Only discriminates from on-hub — off-hub against a secured hub every path redirects to `/login`. An app config page therefore never needs to ask the user whether hub security is on, and — given the loopback bullet above — an app whose HTTP calls all target loopback needs neither the flag nor the credentials *(inferred: the `/login` redirect and the loopback bullet)*.
- `settings[{deviceInput}]` = comma-separated device IDs is the definitive device list *(probed 2.5.2.135)*
- A bare `{name}=value` (no brackets) returns `{"status":"success"}` but **persists nothing** — only the `settings[{name}]` bracket form sticks (keep the `.type` metadata bare alongside it) *(probed firmware not recorded, C-8 Pro)*.
- **Press an app's button input:** `POST /installedapp/btn`, form-encoded: `id` (installed app id), `name` (the button input's name), `settings[<name>]=clicked`, `<name>.type=button`. It calls the app's `appButtonHandler(name)`, so tests can drive in-hub apps without the UI *(probed 2.5.2.135)*.
- **Buttons inside paragraph HTML** (grids of `app-button-link` divs, as built-in apps draw them) may carry a `data-stateAttribute`; the page then adds `stateAttribute=<that value>` to the `/installedapp/btn` POST, and the app uses it to tell apart buttons that share a name (Thermostat Scheduler's heating and cooling cells are both named `Wake.1`, with `tsH` and `tsC`). A button without the attribute sends no `stateAttribute`; adding one anyway made toggle buttons do nothing. After the click, a button with class `submitOnChange` is followed by a form save without Done (next bullet) *(source: /ui2/js/appUI.js, 2.5.2.129; probed 2.5.2.129)*.
- **Save-on-change** (an input with `submitOnChange`, or the save that follows such a button): the page POSTs the whole form to `/installedapp/update/json` exactly as for Done but **without `_action_update=Done`**, so `updated()` does not run. Use this form to drive an app's in-page editors. A Done save while a built-in app had an editor open left that app's page throwing on every render. Some inputs appear only after an earlier value is saved (a sunrise offset after choosing *Sunrise*), so set them in a second POST *(probed 2.5.2.129)*.
- The first Done (`_action_update=Done`) installs the instance and runs `installed()` even when the POST carries no setting at all: a bare Done, a label alone, an empty device input, and a Done on a page whose only input is a button each installed, with or without a `configure/json` read first *(probed 2.5.2.135, throwaway apps)*.
- A setting or the label left out of an `update/json` POST is **kept**, not removed, so a POST may carry only the settings it changes *(probed 2.5.2.135, throwaway app)*.
- The save does **not** check a device against the input's capability: a Virtual Contact Sensor POSTed into a `capability.switch` input was stored, the app subscribed to `switch` on it, and its page rendered without error. Validate before writing *(probed 2.5.2.129)*.
- A **disabled** app renders no inputs, but a save to it still applies: the setting changes. Its `updated()` does not run, so its subscriptions stay on the old devices, and enabling the app again does not run `updated()` either; only a Done save does *(probed 2.5.2.129, a Notifier)*.
- Not every built-in picks devices with a `capability.*` input. Groups and Scenes (Group-2.1) uses `enum` inputs (`bulbs`, `dimmers`, `switches`) whose options are `[{"<deviceId>": "<label>"}]` *(probed 2.5.2.129)*.
- **Disable or enable an installed app:** `POST /installedapp/disable` with JSON `{"id": <appId>, "disable": true|false}` → `{"result":true}`; `/hub2/appsList` then shows `disabled`. This is the Apps page's own call (`/ui2/js/vue-hub2.min.js`) *(probed 2.5.2.133–2.5.2.135; source: vue-hub2.min.js, 2.5.2.129)*. `result` repeats the `disable` value that was sent (`true` for a disable, `false` for an enable, `false` when `disable` is missing, `true` for `"true"`), also for an id that does not exist (still 200), for an id sent as text and when the app was already in that state; a missing `id` also answers 200 and changes nothing. A GET answers 404, and a form body or invalid JSON answers 500; an empty body answers `{"result":false}` *(probed 2.5.2.135, C-8 Pro)*.
- **A disabled app** does not run its button handler, receives no subscription events while disabled (they are not replayed on enable), and a `runIn` that came due while it was disabled never runs, not even after enabling. Its subscriptions made earlier resume on enable (an event after enabling reached the handler), and disabling and enabling run neither `updated()` nor `uninstalled()` *(probed 2.5.2.135, C-8 Pro, throwaway app)*. A Done on a disabled app saves its settings and marks the app installed but runs neither `installed()` nor `updated()`; the first Done after enabling runs `updated()` *(probed 2.5.2.135, C-8 Pro, throwaway app)*.
- **Create a child of a built-in parent app** (a new Thermostat Scheduler, Rule, ...): `GET /installedapp/createchild/{namespace}/{appName}/parent/{parentAppId}` (e.g. `hubitat/Thermostat%20Scheduler%202.0/parent/{parentAppId}`) → 302 to `/installedapp/configure/{newId}`. The new instance has no subscriptions until its page is saved with Done. The same endpoint creates a child of a user app; the parent page's `app(...)` input shows in `configure/json` as a body element `{element: "app", type: "app", multiple, name, appName, namespace, title, appId, nameHashCode}`. The new child is not installed and has no label (`null`), but it is listed under its parent in `/hub2/appsList` at once with `name: ""`; each level of that tree is ordered by label, then id. Its Done runs its `installed()`. `/installedapp/create/{childAppTypeId}` instead makes an orphan: a top-level instance whose `parent` is null *(probed 2.5.2.135)*.
- **Dynamically-added input rows must be seeded first** by POSTing the add-button via `/installedapp/btn` (fires `appButtonHandler`, whose `state` write persists). A dynamicPage only *declares* its grown inputs once `state` holds their ids, so until the row exists, a settings POST for it is silently dropped. (Sub-page inputs: see the sub-page bullet below.) *(probed firmware not recorded, C-8 Pro)* A `state` write made while the page renders persists too ([platform notes](hubitat-platform-notes.md), "App page rendering") *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway app)*.
- A **device multi-select** input (`capability.X`, `multiple: true`) needs `{name}.multiple=true` sent on the POST — without it the input stores `multiple:false`, so only the FIRST device id's subscription arms even though all ids look bound (`settings` show every device, but `eventSubscriptions` covers one). Multiple ids go comma-joined in one `settings[{name}]=id1,id2,id3` field, not repeated keys *(probed firmware not recorded, C-8 Pro)*.
- Each input sent carries `{name}.type`, `{name}.multiple` and `settings[{name}]` *(unmarked)*
- To clear a device multi-select, POST `settings[{name}]` empty, with `{name}.type`, `{name}.multiple=true` and `deviceList={name}`: the setting becomes null. Leaving the field out keeps the devices picked *(probed 2.5.2.139, C-7, own app instance)*.
- Bool inputs need no `checkbox[{name}]=on`: `settings[b1]=true` with `b1.type=bool` alone stored `true`, a later `false` stored false, and `checkbox[b1]=on` alone changed nothing *(probed 2.5.2.135, throwaway app)*
- Enum-multiple inputs: send a **JSON array string** — `["Events","Actions"]`, `[]` for empty. A comma-joined value (`x,y`) is stored as that literal text *(probed 2.5.2.135, throwaway app)*
- Label input needs both `label.type=text` and `label={app label value}` *(probed firmware not recorded)*
- Required POST fields (confirmed from HAR): `id`, `version`, `currentPage`, `formAction=update`, `url` (full configure URL), `pageBreadcrumbs=%5B%5D`, `referrer`, `_action_update=Done`, `_cancellable=false` — `_cancellable` is the one that matters: a Done without it answers a 500 error page, saves the label and leaves the app uninstalled *(probed 2.5.2.135)*
- `appTypeId` and `appTypeName` may be omitted on updates (were empty in HAR) *(probed firmware not recorded, HAR)*
- Label inputs use `app.label` value (NOT from `settings` object) *(probed 2.5.2.135)*
- A page with no `label` element still takes a `label` field in the `update/json` POST: the instance is labelled, and the `installed()` that first Done runs already reads the new `app.label` *(probed 2.5.2.135, throwaway app)*.
- Null settings values should be sent as `[]` (not empty string) **for fields without a `type`**. For typed fields, omit the field or send its default: a typed setting given `"[]"` stores the literal string, and Groovy arithmetic on it then hits string repetition and crashes (`Long.minus(String)`) *(probed firmware not recorded)*.
- Success response: `{"status":"success","location":"/installedapp/list?section=apps"}` *(probed 2.5.2.135)*
- A page declared with `install: false` does not stop a Done POST: a fresh instance whose only page had `install: false` was installed by the POST *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway app)*.
- The page posts its `returnPath` as a hidden form field (`returnPath`, with `donePage`). On Done the reply's `location` is that `returnPath` when it is a hub-local path starting with `/` (`/device/list`). `"list"`, an absolute URL (`https://example.com/x`), a protocol-relative URL (`//example.com/x`) and a path without the leading slash (`device/list`) give `/installedapp/list?section=apps`. `donePage` does not change the reply's `location` *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway app)*.
- Sub-page settings are POSTable through the same endpoint. Read the page with `GET /installedapp/configure/json/{id}/{page}`, then POST that page's inputs with `currentPage={page}`, `pageBreadcrumbs=["mainPage"]` and the page name at the end of `url` (`/installedapp/configure/{id}/{page}`). Save one page per POST; a save with `_action_update=Done` runs `updated()`, so re-read the next page before saving it *(probed 2.5.2.129)*, while a sub-page save without it stores the settings and runs neither `updated()` nor `initialize()` *(probed 2.5.2.135, throwaway app)*.
- **`href` params over HTTP.** To open an app page with params, the `update/json` POST carries `_action_href_<name>|<page>|<n>` and also `params_for_action_href_<name>|<page>|<n>` set to `encodeURIComponent(JSON.stringify(params))`. Without the second field the target page gets no params, and the response echoes `paramsForPage`. Query params on `configure/json/<id>/<page>?ieee=…` are not passed to the page *(source: /ui2/js/main.js, 2.5.2.139; probed 2.5.2.139)*.
- **An app error never reaches the HTTP reply.** When `installed()` or `updated()` throws during a Done save, `update/json` still answers `{"status":"success","location":"/installedapp/list?section=apps"}`; a throwing `appButtonHandler` still gets `{"status":"success"}` from `/installedapp/btn`; a driver command that throws still gets `{"success":true,"message":null}` from `/device/runmethod`, and a device whose `installed()` throws is still created (`/device/save` redirects to its page). The only trace is one `error` line on the log socket and in `/logs/past/json`: `java.lang.IllegalStateException: <message> on line N (method installed)`, so a client that must know watches the log socket for that line *(probed 2.5.2.135, throwaway probes)*.
- **A page that throws still answers 200.** When a page method (`page(name:)` + `dynamicPage`) throws, `configure/json` carries a `configPage` with no sections, `title`, `install` and `uninstall` null/false, `content` set to the page name, and `error` holding the exception's message alone (no class, no line); `removeButton` is false. When a static page body (`page(...) { ... }`) throws, the reply has no `configPage`, `removeButton` or `pageType` at all. The log line names the page method, or `(method run)` for a static page. An app whose `preferences {}` declares nothing gets `configPage: {sections: [], defaults: true}`, `pageType: "preferences"`, `doneButton` and `defaultFields` true, and no `app` block *(probed 2.5.2.135)*.
- `statusJson` `appSettings` show a device input's `value` as null, its ids being in `deviceIdsForDeviceList`, and an enum or mode list as JSON text (`["a","c"]`); `configure/json` `settings` shows the list as a List when the setting is multiple and as the JSON text when it is not. The row order is not stable between reads. A `decimal` setting saved as `2.5` reads as a Double in the app, a `number` as a Long *(probed 2.5.2.135)*.
- `statusJson` rows: a `subscribe(location, "mode", ...)` made without options shows `type: "LOCATION"`, `typeId: 1`, `typeName` the location name and `filter: "false"`; a `runIn` job shows `schedule: "Once"` and `nextRunTime` as `2026-10-13T10:55:12+0000` (UTC). Key order: `handler, subscriptionData, type, filter, typeName, typeId, name` and `handler, nextRunTime, schedule, status, prevRunTime` *(probed 2.5.2.135)*.

## File Manager files over HTTP

- `GET /hub/fileManager/json` → `{path, freeSpace, backupSelection, files[]}`; each file is `{id, name, size, date, type, backupIncluded}` *(probed 2.5.2.135)*.
- `GET /local/{fileName}` serves a File Manager file. The content type follows the extension: `.txt` is `text/plain` and opens in the browser, `.log` is `application/octet-stream` and downloads *(probed 2.5.2.129)*. `.json` is `application/json`, and a missing file is a 404 HTML page (`text/html;charset=utf-8`) *(probed 2.5.2.135)*.
- In the list, `path` is null at the top folder, `freeSpace` a number of bytes, `backupSelection` `{excludedFiles: 0}` on a hub that excludes nothing, and every file's `size` and `date` (epoch milliseconds) are strings *(probed 2.5.2.135)*.
- `POST /hub/fileManager/upload` (`/hub/fileManager/upload/{folder}` for a folder) takes multipart form data with the file in the field `uploadFile` and answers `{"success": true, "status": "Successfully uploaded {name}"}` *(probed 2.5.2.135; source: vue-hub2-file-manager.min.js, 2.5.2.135)*.
- `POST /hub/fileManager/delete` takes JSON `{name, type: "file", folder}` and answers `{"status": true}`, or `{"status": false}` when there was no such file *(probed 2.5.2.135; source: vue-hub2-file-manager.min.js, 2.5.2.135)*.

## Device discovery

- `GET /device/listJson?capability={capability}` — list devices with a specific capability. Takes the full `capability.switch` form (a bare `switch` returns nothing). A comma-separated list, the form multi-capability inputs use, returns the devices that have any of them *(probed 2.5.2.129)*.
  - e.g. `capability=capability.battery`, `capability=capability.notification`
  - Returns `[{"id":N,"name":"...","label":"...","displayName":"..."},...]`
  - Useful for populating device picker inputs programmatically
- `GET /device/list/all/data` — every device as one flat JSON list, each row with the keys of a parent device's `fullJson` `childDevices` rows (`id`, `name`, `label`, `displayName`, `deviceNetworkId`, `deviceTypeId`, `deviceTypeName`, `type` `sys`/`usr`, `parentDeviceId`, `status`, `createTime`, `lastActivityTime`, ...) *(probed 2.5.2.135)*.
- Multiple drivers can share a name; `data.source` on `/hub2/devicesList` disambiguates — **`System`** (built-in Hubitat driver, usually what you want), **`Linked`** (Hub Mesh receiver-side proxy whose `on()`/`off()` are no-ops that emit no events), **`User`** (user-installed custom driver). Filter `source=='System'` for a built-in when the hub already has a device using it. `GET /device/drivers` → `{"drivers":[{"id","name",...}]}` lists every driver, built-in ones included (e.g. Virtual RGBW Light, Virtual Fan Controller), and `GET /driver/list/data` returns the same as a list *(probed 2.5.2.129)*. (E.g. "Virtual Switch" often has both a System and a Linked variant sharing the name.)
- **Label fields differ across endpoints:** on `/hub2/appsList` the user label is in `data.name` (there is no `data.label` key); on `/hub2/devicesList` `data.name` is the display name (the label when there is one) and `data.secondaryName` the device name when a label hides it, else `""` (there is no `data.label`) *(probed 2.5.2.135)*; `installedapp/configure/json/{id}` exposes it as `app.label` *(probed 2.5.2.135)*.
- **Find a device by hardware model:** read `device.data.model` from `GET /device/fullJson/{id}` (e.g. a Zigbee model string) — do NOT filter by driver name, since a device can be paired to any generic driver whose name won't mention the model *(probed firmware not recorded)*. Pre-filter candidates via `/hub2/devicesList` `data.isZigbee` to bound the per-device `fullJson` calls (`/hub2/devicesList` itself does not carry `data.model`) *(probed 2.5.2.135)*.
- **Hub Mesh remote (consumed) device identity:** a consumed remote carries its source in **`remoteDeviceUrl`** (in both `/hub2/devicesList` `data.remoteDeviceUrl` and `/device/fullJson/{id}` `device.remoteDeviceUrl`), format `http://<sourceHubIP>:<port>/device/edit/<sourceDeviceId>` — parse for source hub IP + device id. The remote marker is `data.isLinked == true`; `remoteDeviceUrl == '#'` marks an **orphaned link** (source hub gone/unreachable). On `fullJson`, `device.meshEnabled` is false and `device.isLinked` is null on remotes — rely on `remoteDeviceUrl` (non-empty, non-`#`) instead *(probed firmware not recorded, C-8 Pro)*.
- **Field semantics — `isOrphan`:** `isOrphan` (in `/hub2/devicesList`) / `device.orphan` (in `fullJson`) is a **mesh/radio orphan** state — a lost radio parent/route — NOT "no apps subscribe." For unreferenced devices ("no apps subscribe") use `appsUsing[]` / `appsUsingCount` from `GET /device/fullJson/{id}` *(unmarked)*.
- **Hub Mesh discovery and transport (what admits a peer):** discovery is plain mDNS: each hub advertises `_hubitat._tcp` on port 80 with TXT keys `hubMeshProtocol` (observed `1.0`), `hubUID` (a UUID), `id` (the hub MAC), `platformVersion`, `hubVersion` (model) and `hubMeshEnabled`. The data transport is **TCP 8083**, open only on mesh-enabled hubs. Linking is **not** automatic from discovery: a peer only connects after its 64-char Hub Mesh token is entered on the other hub. A LAN host that merely advertises a well-formed `_hubitat._tcp` record draws no connection and leaves no entry in the target's `/hub2/hubMeshJson` `hubList`. The 8083 wire format is undocumented. The admin UI drives the link via `/device/{generate,set,show}HubMeshToken`, `/device/addToMesh/{id}`, `/device/createLinked/{hubId}/{deviceId}`, `/hub/advanced/{enable,disable}HubMesh`, `/device/hubMeshReconnect`, `/device/hubMeshFullRefreshNow` *(probed 2.5.2.134, C-8 Pro; source: vue-hub2-hub-mesh, 2.5.2.134)*.
- **Child devices in the admin endpoints** *(probed 2.5.2.135, throwaway parent app and driver)*: in `/hub2/devicesList`, a driver's children are nested under the parent device's node (`parent: true`, each child `child: true`), while an app's children are top-level nodes with `parent` and `child` both false. `GET /device/fullJson/{id}` of a child has `device.parentAppId` or `device.parentDeviceId` (a number, the other null), `device.isComponent` (Boolean) and `device.displayAsChild` (null when not set), and an app's child also a top-level `parentApp` (the parent's app record); the parent app is not in `appsUsing`. A parent device's `fullJson` has `hasChildren: true` and `childDevices: {"<parentId>": [rows]}`, each row with the device's identity fields (`id`, `name`, `label`, `deviceNetworkId`, `type` `usr`/`sys`, ...) and `isComponent` as the string `"true"`/`"false"`. An app's `statusJson` has `childDeviceCount` and `childDevices: [{id, name}]` (`name` is the display name). `/device/forceDelete/{id}/json` deletes a child like any device (`{"status":"success"}`, its `uninstalled()` runs) and on a parent device also deletes its children.

- **Video streams** (`capability "RTSPStream"` devices, see [platform notes](hubitat-platform-notes.md#capabilities)): the hub serves the stream as MJPEG at `/hub2/videoStream/{deviceId}.mjpg` and checks the source with `POST /hub2/videoStream/{deviceId}/validate` (JSON reply with `success`, `message`, `width`, `height`) *(unmarked)*.

### Per-device event history

- `GET /device/eventsJson/{id}` — the device's recent event list as a JSON array (works on secured hubs via an authenticated session). Each row: `name`, `value`, `unit`, `descriptionText`, `source` (DEVICE/APP/…), `type`, `date` (ISO-8601 with tz offset), `producedBy`, `triggered`, `isStateChange`, `physical`, `digital`, `deviceId` *(probed 2.5.0.158, hub security on; probed 2.5.2.135)*.
  - **`physical` vs `digital`** discriminates a hand at the wall switch/button from an automation/command. Matter devices set neither (both false → treat as unknown) *(probed 2.5.0.158)*.
  - **Row counts:** ~11–190 rows per device were seen on a busy hub *(probed 2.5.0.158)*. The cap is `maxEvents` rows **per attribute name**, applied by pruning some minutes after the write, not when the event is stored: a virtual device with `maxEvents` 11 returned all 36 rows (20 on one attribute, 16 on another) at once and about 10 min later, a second one held 40 rows of one attribute right after writing and 11 about 14 min later, and the same device with 20 + 16 new rows on two attributes held 11 + 11 hours later *(probed 2.5.2.135, virtual devices)*. On 12 devices of a hub with security on, every attribute returned exactly 11 events, so a chatty attribute did not crowd out a quiet one *(probed firmware not recorded, 12 devices, 2026-09)*. `unixTime` is present but null; parse `date` *(probed 2.5.0.158)*.
  - `/device/events/{id}` (no `Json`) is a Vue SPA shell — use `eventsJson`, not the HTML *(probed 2.5.0.158)*.

### Device state variables (driver `state`)

- `GET /device/fullJson/{id}` `device.homeKitCompatible` is true for a device whose user driver sets `homekitCompatible: true` in `definition()` *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver)*.
- `GET /device/fullJson/{id}` exposes a driver's Groovy `state.*` map as the **top-level `deviceState`** object — NOT under `device.state` (that key is empty/absent), and there is no `/device/state/{id}` endpoint *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh; probed 2.5.2.135)*. Keys are entirely driver-author-defined (no platform contract), so use `deviceState` for per-device display/backup only — never for cross-device aggregation or assuming a key exists across drivers *(inferred: the keys come from driver code)*.

## Device creation (virtual devices)

- `POST /device/save` with form-encoded fields: `name`, `label`, `deviceNetworkId`, `deviceTypeId` *(probed 2.5.2.135)*
- Returns HTTP 302 on success (redirect to the new device's edit page) *(probed 2.5.2.135)*
- Delete a virtual device: `GET /device/forceDelete/{id}/json` → `{"status":"success"}` *(probed 2.5.2.135)*
- Change a device's driver (or name, label, room): `POST /device/update`, form-encoded, the device page's Save. It replaces the whole record, so send every field: `id`, `version` (from `/device/fullJson/{id}` `device.version`), `name`, `label`, `deviceNetworkId`, `deviceTypeId`, `zigbeeId`, `maxEvents`, `maxStates`, `spammyThreshold`, `roomId`, `groupId`, `locationId`, `hubId`, `meshEnabled`, `retryEnabled`, `homeKitEnabled`, `dashboardIds`, `tags`, `defaultIcon`, `notes`, `controllerType`, `deviceTypeReadableType`, and `meshFullSync=on` when Hub Mesh full sync is on. `meshFullSync` is a checkbox: leaving it out turns full sync off. The page sends unset fields as `""`, which the hub stores as `0` for `roomId`/`groupId`. `notes` keeps line breaks. A stale `version` is not rejected, so the last save wins, including a device page left open with older values. A save built from this field list changed only the edited field *(probed 2.5.2.129)*. `apps/tests/test-architecture-claims.sh` uses it to switch drivers *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*. It is also the only way to write a device's notes: an app gets `getNotes()` but `setNotes()` is not supported and `notes` is read-only on the device *(probed 2.5.2.129)*.
- **Changing a device's driver empties its `state`.** A `/device/update` that moved a device from one user driver to another of the same name in another namespace left `deviceState` empty, so a driver that keeps pairing keys there must pair again; the preferences, room and dashboard selections were kept. Fields the save sent as empty came back as `''`, or `0` for `roomId`/`groupId`, where `fullJson` had shown null *(probed 2.5.2.135, C-8 Pro, Android TV Remote device)*.
- `POST /device/update` answers `200` with `{"status":"success"}` (JSON) and does not redirect *(probed 2.5.2.135, C-8 Pro, throwaway driver)*. The `zigbeeId`, `endpointId` and `controllerType` fields it carries are stored: with `controllerType=ZGB`, `/device/fullJson` shows `zigbee: true`, `zigbeeId`, `endpointId`, and `data` gains an `endpointId` entry; the driver then reads `device.zigbeeId` and `device.endpointId`, and the `zigbee` helpers print that endpoint instead of `null`. `device.getDataValue("endpointId")` stays null, because that `data` entry is a view of the field, and a code push to the device's driver clears the `endpointId` field again *(probed 2.5.2.135, C-8 Pro, throwaway driver)*. This is how a virtual device can be made to look like a Zigbee device for a driver that builds Zigbee command strings; nothing reaches a radio unless the driver sends them.
- The device page saves preferences with `POST /device/preference/save`, a JSON body `{"deviceId": <id>, "defaultCurrentState": "", "commandRetry": <bool>, "showOnHome": <bool>, "preferences": [{"name", "type", "value"}, …]}` listing every preference (bools as JSON booleans); `deviceId` with a partial or map-shaped `preferences` returns `success: true` and changes nothing *(probed 2.5.2.134, capture; probed 2.5.2.129, applied)*. On 2.5.2.135 a partial list did apply: it changed the one preference it listed, kept the others, ran `updated()`, and answered `{"success":true,"message":null}`, as the full list does; a map-shaped list was not retried *(probed 2.5.2.135, throwaway Virtual Switch)*; adding `settings[...]` fields to `POST /device/update` returns 500 *(probed 2.5.2.134, throwaway device)*.
- Delete a user driver type: `GET /driver/deleteDeviceType/{id}` (delete any devices using it first) *(probed 2.5.2.135, an unused user driver type)*

## Device swap and replace

- **Swap Apps Device** (Settings) is a built-in app. `GET /installedapp/direct/swapDevice` → 302 `/installedapp/create/{typeId}` → 302 `/installedapp/configure/{id}`, a pending instance. Its `mainPage` has enum inputs `oldDev` and `newDev` (submitOnChange; options as `[{"<id>":"<label>"}]`). `newDev` gets its options only after `oldDev` is saved, and they are the devices the hub accepts as compatible. A `doSwap` button appears once both are set. Clicking it (`POST /installedapp/btn`) only arms the swap: **the swap runs when the page next renders**, and every later render of that instance's page (a browser reload, a `GET /installedapp/configure/json/{id}`) swaps the two devices again, showing the same "has been replaced" message. Delete the instance right after the one render that swaps, with `GET /installedapp/delete/{id}`, which does not render it. The page's Cancel button, relabelled Done after a swap, also deletes the instance (`/installedapp/forcedelete/{id}/quiet`) and sends the browser to the Apps list. An app can open the instance itself: `httpGet` with `followRedirects: false` returns both 302s and their `Location` *(probed 2.5.2.129–2.5.2.135)*. An instance left open is still there after 30 minutes. The page works in an `<iframe>` on an app page (no frame-blocking headers), and the admin chrome inside it can be removed with `#divSideMenu, #divMainUIMenu, #divMainUIHeader, #divMainUIFooter` *(probed 2.5.2.129)*.
- A settings save on an armed instance swaps again too: the response of `POST /installedapp/update/json` is a page render. Each open of `/installedapp/direct/swapDevice` creates a new pending instance, although the app type is single-instance, and a pending instance does not appear in `/hub2/appsList` *(probed 2.5.2.135)*.
- **What the click checks:** the swap refuses a child device in either input; the page then carries `error: "<id> is a child device"`, has no sections, and swaps nothing. It does not re-check capabilities: a `newDev` saved outside the offered list is swapped all the same. The same device in both inputs shows the "has been replaced" message and changes nothing, and a click with no `newDev` fails with a page error *(probed 2.5.2.135, throwaway devices)*. An app that drives the page has to check the offered list itself.
- **What the swap does:** it exchanges the two device records. Name, label, DNI, driver, capabilities, current states, room and `createTime` move between the two ids. Apps that used the new device before the swap now reach the old hardware. A second swap of the same two devices restores both records exactly. App settings, subscriptions and app `state` are not touched, and `updated()` does not run, so every reference to the old id now reaches the new hardware. Event history stays with the id, so the old id's history continues with the new device's events. The old hardware ends up under the new device's id *(probed 2.5.2.129–2.5.2.135)*. Verified with two virtual switches and with a Virtual Contact Sensor swapped for a Virtual Omni Sensor *(probed 2.5.2.129)*. A check that the old id has lost its dependents therefore reports a successful swap as a failure. bravenel describes it as a DNI swap ("It swaps the DNIs of the two devices", [community thread 148552](https://community.hubitat.com/t/feedback-clarification-of-swap-versus-replace-device/148552/2)); the test shows more than the DNI moving *(staff: [bravenel](https://community.hubitat.com/t/feedback-clarification-of-swap-versus-replace-device/148552/2))*. Hubitat excludes child devices because a child and its parent call each other's methods, and nothing maps those links ([thread 125101](https://community.hubitat.com/t/connector-support-in-swap-apps-device/125101), [110895](https://community.hubitat.com/t/feature-request-swap-devices-that-works-for-child-devices/110895)) *(staff: [bravenel](https://community.hubitat.com/t/connector-support-in-swap-apps-device/125101/3))*.
- The record that moves also carries the driver's data values, driver `state`, preferences, notes, tags, the disabled flag, the parent link of an allowlisted child (it stays a child of its integration, under its new id), a Hub Mesh linked device's link, and the Hub Mesh sharing setting: a shared device's entry in the hub's shared list moves to the other id with the record. What the other hub's linked copy showed was not read. What stays with the id: the swapped device's own child devices, so a parent swap leaves its children on the id, their calls to `parent` reach the driver that now has that id, and `getChildDevice()` on the moved parent finds none; and the driver's scheduled jobs, which fire on the id under whichever driver it now has (a pending `runIn` failed with `MissingMethodException` on a different driver). No lifecycle method (`installed`, `updated`, `initialize`, `configure`) runs on either device, and the swap sends no events *(probed 2.5.2.135, throwaway drivers and devices, plus an AirPlay child, a Hub Mesh linked device and a shared Bluetooth child swapped and restored)*.
- **Eligibility:** `oldDev` listed only devices some app uses *(probed 2.5.2.129; false 2.5.2.135)*. On 2.5.2.135 it lists every device that is not a child, including disabled devices and devices no app uses *(probed 2.5.2.135)*. App-child devices are excluded except those of an allowlist of built-in integrations, added in 2.4.4.129: "whitelisted AirPlay, Wiz, HomeKit, Bluetooth and Tuya integrations to allow child device swaps" ([release notes](https://community.hubitat.com/t/release-2-4-4-available/161597)) *(staff: [gopher.ny](https://community.hubitat.com/t/release-2-4-4-available/161597))*. On one hub, children of AirPlay, Bluetooth and HomeKit Controller were listed; children of Lutron, Ecobee and every user app were not. Hub Mesh linked devices are listed *(probed 2.5.2.129–2.5.2.135)*. Children of a device (component or not, built-in driver or user driver) and Hub Variable connector devices are not listed either *(probed 2.5.2.135)*. The same release added a capability check on the target device *(staff: [gopher.ny](https://community.hubitat.com/t/release-2-4-4-available/161597))*.
- `newDev` lists the other eligible devices that share at least one capability with `oldDev`, not counting Actuator, Sensor, Refresh, Configuration, Initialize, Polling and Battery. A superset is not required: a Virtual Switch and a Virtual Dimmer are offered for each other. HealthCheck, SignalStrength and PowerSource count. The same driver is not enough on its own: two devices whose only capability is Configuration are not offered for each other *(probed 2.5.2.135, throwaway drivers with one capability each)*.
- `GET /device/getReplacementOptions/{id}` → `[{"id":N,"name":"...","deviceTypes":[...]}]`, the candidates for the device page's Replace. `GET /device/replace?oldId=&newId=` returned `{"success":false,"message":"Failed to replace device"}` for two virtual switches the options call offered; it likely works only for radio devices. Its semantics are unverified *(probed 2.5.2.129–2.5.2.135)*. Its list follows a different rule from Swap Apps Device: candidates share an entry in `deviceTypes` (such as `Switch`, `Light`, `Graph`, `ContactSensor`), and child devices are included *(probed 2.5.2.135)*.
- `configure/json` returns an enum-multiple setting as a List (`["a","c"]`) and `statusJson` returns it as a JSON string. Echoing the List with Groovy `toString()` stores the string `"[a, c]"` *(probed 2.5.2.129)*.

## Export, Import and Clone of app instances

The App Status page's Export/Import/Clone button opens a hidden built-in app, "Export/Import/Clone" (`classLocation: appCloner`). Like Swap Apps Device, it is an ordinary app page, driven with `update/json` and `/installedapp/btn` as in [App configuration](#app-configuration-addremove-devices-change-settings), so the whole flow works over HTTP. It copies one app instance; for the whole hub see [Hub database backups](#hub-database-backups) *(probed 2.5.2.129)*.

- **Open:** `GET /installedapp/sysAppApi/appCloner/app/{appId}` → 302 to `/apps/api/{clonerId}/app/{appId}?access_token=…`, whose GET selects `{appId}` and redirects to `/installedapp/configure/{clonerId}/main`. Each open creates a new cloner instance and deletes the previous one. The page is `main`, so `configure/json/{clonerId}` without a page name is a 404 *(probed 2.5.2.129)*.
- **Export:** press `exportRuleButton`, then read `configure/json/{clonerId}/main`: the `download-text` input `ruledownload` carries the export in `filecontent`. There is no download URL *(probed 2.5.2.129)*.
- **File name step:** when the app's label carries an HTML status badge (Rule Machine's red "Required Expression false", "Paused", "Stopped"), the page after `exportRuleButton` shows a text input `fileName` and no file. Saving `fileName` (save-on-change) returns the page with `ruledownload` in that POST's response; a later GET shows the plain page again. Seen on two rules, one with a Required Expression and one stopped without one *(probed 2.5.2.129)*.
- **Format:** JSON with `deviceReplacements` (`{oldId: {deviceName, deviceLabel, deviceTypeName, deviceTypeNamespace}}`), `appReplacements` (app type, label, parent, `childApps` by id and label) and `appData` (`{appId: {state, appSettings, subscriptions}}`). It holds one app: a parent's export names its child apps but carries none of their settings or state. Child devices and scheduled jobs are not exported. Multi-select enum values are double-escaped (`"[\\"Events\\",…]"`), so the file is not strict JSON; the importer still restores them correctly *(probed 2.5.2.129)*.
- **Import:** save the file text as `settings[ruleUpload]` (`ruleUpload.type=file-text`) on page `main` without Done, then POST the field `_action_href_name|importRule|55` to open `importRule`. It has `newName{oldAppId}` and one `dev{oldDeviceId}` input per exported device, prefilled with the same id. `importNow` appears after one save-on-change of that page (the browser's `changeSubmit` script). As with Swap Apps Device, the button only arms the import and **the next render runs it**. A later render does not import again (`state.imported`) *(probed 2.5.2.129)*.
- **Result:** a new instance with the same settings, `state` (plus `clonedName`) and subscriptions; a child app attaches under its original parent. A remapped `dev{id}` rewrites the setting and its subscription. The lifecycle runs twice, before and after `state` is restored, and the app acts at once on the restored runtime state: an HFC import whose state said it owned the fan turned the fan off within 2 s *(probed 2.5.2.129)*.
- **Restore** (`_action_href_name|restoreApps|55`, button `restoreNow`, runs on the next render) works only when the exported app id no longer exists. It keeps the label and offers no device remap. The app returns under a **new id**, so references to the old id stay broken *(probed 2.5.2.129)*.
- **Clone:** press `cloneRuleButton`, then open `importRule` and continue as for an import. One press in the `settings[cloneRuleButton]=clicked` form did nothing; a repeat with `cloneRuleButton=clicked` worked. The cause was not isolated *(probed 2.5.2.129)*.
- Not tested: import onto another hub, an import whose app type is missing, and single-instance apps *(inferred: what the 2.5.2.129 tests left out)*.

## Hub variables admin API

From 2.5.2.133 the Hub Variables page is a native page at `/hub/variables`, and `/installedapp/direct/hubVariables` redirects there *(false 2.5.2.129; probed 2.5.2.133)*. Earlier firmware serves it as a built-in app at `/installedapp/direct/hubVariables` → `/installedapp/configure/{id}` *(probed 2.5.2.129)*. The new page uses a JSON API:

- `GET /hub2/variables` → `{timeZone, variables[]}`; each variable has `name`, `type` (`integer`, `bigdecimal`, `boolean`, `string`, `datetime`), `value` (always a string), `linked`, `meshEnabled`, `sourceName`, `connectorId`, `connectorType`, `connectorOptions[]`, `usedBy[]`, `connectorUsedBy[]` *(probed 2.5.2.133)*. A local variable also has `sourceName` `Local`, `sourceIp` and `connectorLabel` null; `usedBy` rows are `{id, label}` of the apps that called `addInUseGlobalVar`; `connectorOptions` is `Variable`, `Illuminance`, `Humidity`, `Dimmer`, `Volume`, `ColorTemp` for an integer, `Variable`, `Temperature` for a bigdecimal, `Variable`, `Presence`, `Acceleration`, `Contact`, `Motion`, `Water`, `Switch`, `Lock` for a boolean, `Variable` for a string and `DateTime` for a datetime *(probed 2.5.2.135)*.
- Refusals and their messages *(probed 2.5.2.135)*: a name that exists, 400 "The name already exists or the value is invalid."; an unknown type, 400 "Select a supported variable type."; a value that does not fit, 400 "The value does not match the variable type."; an empty name, 400 "Use a name of 1-255 characters without leading/trailing spaces, control characters, or quotes, backslashes, ~, [, ], :, <, >." (a space or `!` inside a name is accepted); a variable that does not exist (update, rename, remove), 400 "This variable no longer exists. Refresh the table."; an `update` whose `expectedValue` is not the current value, or that has none, 409 "The value changed while you were editing. Reopen the editor and try again."; removing a variable in use, 400 "This variable or connector is in use. Refresh and review the affected apps before deleting it.".
- A DateTime `create` with `mode` `unset`, `date` or `time` stores `9999-99-99T99:99:99.999-9999`, `2027-01-02T99:99:99.999-9999` or `9999-99-99T15:07:00.000-0400` (created in October, in America/Toronto); `datetime` stores the date and time in the location's zone *(probed 2.5.2.135)*.

All of them check the value against the type *(probed 2.5.2.133)*.
- `remove` and `removeConnector` refuse a variable or connector in use (`usedBy`/`connectorUsedBy`). The built-in Easy Mobile Dashboards pick up new connector devices on their own, so a new connector is in use at once; delete the connector device (`/device/forceDelete/{id}/json`) before removing the variable *(probed 2.5.2.133)*.

## Run a device command (no Maker API)

- `POST /device/runmethod` — invoke any command on a device via the admin-UI channel, without a Maker API token. JSON body: `{"id": <deviceId>, "method": "<commandName>", "args": [{"type": "<paramType>", "value": <v>}, ...]}` (use `"args": []` for no-arg commands). Response: `{"success":true,"message":null}`. Unlike a Maker API command or an app's `device.cmd()`, which each leave a `command-<name>` row (`type: "command"`, `descriptionText: "Command called: name(args)"`) in `/device/eventsJson`, a runmethod call leaves none. Maker API hands a NUMBER parameter's argument to a built-in virtual driver as a BigDecimal with its scale (`"20.0"` arrives as 20.0) and a non-numeric one as the String *(probed 2.5.2.135, built-in virtual drivers)*. To a driver written in Groovy it hands the text of an argument to a parameter declared `NUMBER` as an Integer when it is a whole number in Integer range (`50`, `-5`, `+5`, `007`, ` 5`), else as a Double (`20.0` arrives as 20.0 and `20.50` as 20.5, `1e2` as 100.0, `12345678901` as 1.2345678901E10, `NaN`, `5d`), and as the String when neither parses (`abc`, `0x10`, `1_000`); parameters declared `Number`, `number`, `DECIMAL`, `Decimal`, `STRING` or `ENUM` get the String *(probed 2.5.2.135, C-8 Pro, throwaway driver)*. Arguments for a command declared without parameters answer 500 at once; any other count reaches the driver, which fails with a `MissingMethodException` in its log while the reply is 200, and a missing value calls a one-parameter command with null *(probed 2.5.2.135, C-8 Pro, throwaway driver)*.
- The POST runs the command before it answers: a driver command that paused 2 s answered in 2018 to 2035 ms (3 runs; Maker API the same, 2031 to 2094 ms) *(probed 2.5.2.135, C-8 Pro, throwaway driver)*. The command's events are applied by the device's event queue afterwards, so a read right after the reply can still show the old state *(probed 2.5.2.135, see hubitat-platform-notes.md, "An event is not readable the moment it is sent")*. An earlier note here said the POST returned before the command ran *(false 2.5.2.135)*. Poll `GET /device/fullJson/{id}` (`device.currentStates` is a map keyed by attribute name, each entry with a `value`) until the expected state appears *(probed 2.5.2.135)*.
- `method` need not be a declared command: `{"method": "parse", "args": [{"type": "STRING", "value": "<description>"}]}` runs the driver's `parse(String)` with that description, answers `{"success":true,"message":null}`, and the events and state changes show in `/device/fullJson` and `/device/eventsJson` afterwards *(probed 2.5.2.135, C-8 Pro, throwaway driver)*. The value `parse` returns is ignored *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver)*.
- `/device/runmethod` does not enforce a parameter's `required` flag (`Mode*`) or an `ENUM` parameter's `constraints`: a command called with no argument received null, and an `ENUM` parameter received `"bogus"`. Maker API and app callers were not tested *(probed 2.5.2.135–2.5.3.102, C-8 Pro, throwaway driver)*. The device page's Run button doesn't check it either: with an `ENUM` parameter declared `required: true` (kept as `"required": true` in `/device/fullJson` `commands[].parameters`) and its dropdown left at "Click to set...", the page said "Command submitted" and the command received null *(probed 2.5.3.104, C-8 Pro, throwaway driver)*. A `method` of `dump` answers success and runs nothing of the driver's, because Groovy's built-in `Object.dump()` takes the call; a command named `dumpRec` ran *(probed 2.5.3.102, C-8 Pro, throwaway driver)*.
- A device's invokable commands are listed in `GET /device/fullJson/{id}` in the top-level `commands[]` (each has `name`, `parameters`) *(probed 2.5.2.135)*.
- This is the **web-UI invocation channel**; its script-instance/binding lifecycle could differ from app- or Maker-API-driven calls. For production-representative behavior — and any test that cares about cross-invocation state — prefer the Maker API route `GET /apps/api/{appId}/devices/{deviceId}/{command}?access_token={token}`. (The two channels matched for command dispatch and binding persistence on firmware 2.5.0.143 — see [`hubitat-platform-notes.md`](hubitat-platform-notes.md).) *(probed 2.5.0.143)*

## App access tokens

- **Preferred: `GET /installedapp/statusJson/{id}` → `appState[]`, the entry named `accessToken`.** A structured field, no HTML parsing. This is not Maker-API-specific — it works for any app instance, because `createAccessToken()` stores the token in `state.accessToken`. On a Maker API instance and a custom app, the token read this way authenticates the app's endpoints *(probed 2.5.2.113 and 2.5.2.135)*.
- The entry is **absent** for an app that never called `createAccessToken()` (no OAuth endpoints), so treat a missing `accessToken` as "this app has no endpoints", not as a read failure *(probed 2.5.2.135)*.
- Fallback: the token is also embedded in HTML links inside `configPage.sections[].body[]` paragraphs — look for `description` fields containing `access_token=`. Example: `<a href='http://{hub_ip}/apps/api/{id}/devices?access_token={TOKEN}'>`. Use this only if `appState` is unavailable; it breaks whenever the app's config page markup changes *(probed 2.5.2.135)*.
- The token is **not** in `settings` *(probed 2.5.2.135)*.

## App OAuth endpoint authentication (`Bearer` header)

Every app OAuth endpoint (`/apps/api/{appId}/{path}` — Maker API and any custom Groovy app with a `mappings` block) accepts the token as an **`Authorization: Bearer {TOKEN}` header** instead of the `?access_token={TOKEN}` query parameter *(probed 2.5.1.183, 2.5.2.113 and 2.5.2.135)*. Prefer the header: a query-string token lands in hub and proxy access logs, DNS/filtering logs, browser history, and outbound `Referer` headers, and on the cloud relay it crosses the public internet in the URL *(inferred: where a URL is logged and sent)*.

This is enforced by the platform's OAuth filter, not by app code — a rejected request never reaches the mapped handler and returns `401` with an XML body, `<oauth><error_description>null</error_description><error>invalid_token</error></oauth>`, rather than the JSON `AppException` shape an app-level error produces *(probed 2.5.1.183, 2.5.2.113 and 2.5.2.135)*.

Measured against both a Maker API instance and a custom app's own endpoint *(probed 2.5.2.113, C-8 Pro, hub security off; probed 2.5.1.183, C-7, hub security on)*:

| Request | Result |
|---|---|
| `?access_token={TOKEN}` | 200 |
| `Authorization: Bearer {TOKEN}`, no query param | 200 |
| `Authorization: Bearer {WRONG}` | 401 |
| no auth | 401 |

Scope of the behavior:

- Applies to **POST as well as GET** — a POST carrying only the header to a GET-only path returns `405 Method Not Allowed` (auth passed, routing failed), while the same POST with no auth returns `401` *(probed 2.5.2.113 and 2.5.1.183)*.
- Applies to the **cloud relay** (`https://cloud.hubitat.com/api/{hubUID}/apps/{appId}/{path}`) identically. This is where the header matters most *(probed 2.5.2.113 and 2.5.1.183)*.
- Independent of hub security — app OAuth endpoints never consult the hub login session *(probed 2.5.2.113 and 2.5.1.183)*.
- The local OAuth API (`/apps/api/<id>/...`) sends **no CORS headers** and does not support preflight: a cross-origin `GET` returns `200 OK` with no `Access-Control-Allow-Origin`, and an `OPTIONS` preflight returns `405 Method Not Allowed` *(regression 2.5.2.129–2.5.3.102, apps/tests/test-architecture-claims.sh)*. This is browser-enforced, so a page served by one hub cannot *read* another hub's API response, while `curl` and server-side calls are unaffected. The architectural consequence is in [`ARCHITECTURE.md`](../ARCHITECTURE.md) ("Cross-origin (CORS) and multi-hub browser clients") *(spec: [Fetch standard, CORS protocol](https://fetch.spec.whatwg.org/#http-cors-protocol))*.

Three traps:

- **The scheme is case-sensitive before 2.5.2.120.** On earlier firmware only exactly `Bearer` authenticates; `bearer` and `BEARER` both return 401 *(probed 2.5.2.113)*. This is off-spec (HTTP authentication schemes are case-insensitive tokens), so an HTTP client or gateway that normalizes the scheme's case will break the request *(spec: [RFC 9110 §11.1](https://www.rfc-editor.org/rfc/rfc9110#section-11.1))*. From 2.5.2.120 the match is case-insensitive, locally and through the cloud relay *(false 2.5.2.113, local; probed 2.5.2.135–2.5.3.107, local; probed firmware not recorded and 2.5.3.107, local and cloud relay)*. Send exactly `Bearer` while any target hub runs older firmware.
- **No other form works.** A bare `Authorization: {TOKEN}` with no scheme, and `X-Auth-Token: {TOKEN}`, both return 401 *(probed 2.5.2.113 and 2.5.1.183; probed 2.5.2.135–2.5.3.107)*.
- **The query parameter wins when present.** Wrong query param + correct header → 401; correct query param + wrong header → 200. The header is consulted only when `access_token` is absent from the URL, so a header cannot override a stale token left in a URL *(probed 2.5.2.113 and 2.5.1.183; probed 2.5.2.135)*.

Re-measured on 2.5.2.135 against a custom app (throwaway probe): the rules above hold, and the filter takes the `access_token` *parameter*, so a form-encoded POST body field works like the query (the query's value wins when both are present), while a JSON body field does not count. An empty `?access_token=` falls through to the header. The 401's `error_description` is the `access_token` parameter as sent (empty when empty) and `null` when there was none, including for a wrong Bearer token. An app id that does not exist answers `404` `{"error":true,"type":"AppException","message":"Not Found"}` before any token check *(probed 2.5.2.135, throwaway app)*. Full routing and render rules: [`hubitat-platform-notes.md`](hubitat-platform-notes.md) ("App endpoints and child apps").

Undocumented by Hubitat — nothing promises this across firmware versions. Code that relies on it should keep the query-param form as a fallback *(absent 2.5.2.135: the docs2 Maker API page mentions no `Authorization` header or Bearer token)*.

### Cloud relay response size limit

The relay carries responses over AWS IoT Core MQTT, whose publish payload limit is 128 KB and not adjustable *(spec: [AWS IoT Core quotas](https://docs.aws.amazon.com/general/latest/gr/iot-core.html), "MQTT payload size"; staff: [gopher.ny](https://community.hubitat.com/t/119869/15))*. Measured with a throwaway app returning a `text/plain` body: bodies up to 127,831 bytes returned 200 and from 127,845 bytes `504` with body `No response from hub` after about 10 s. About 3.2 KB of the 131,072-byte payload goes to the relay's own envelope. The relay does not compress, and an `Accept-Encoding: gzip` request header made no difference *(probed 2.5.2.134, throwaway app)*. Cloud clients that read large lists (Maker API `/devices/*`) must page or slim the response.

### Cloud relay connection lost

- **The hub reports a lost relay connection in `/hub2/hubData`.** `alerts.alertItems[]` holds `{key: "CLOUD_UNAVAILABLE", message: "Cloud connection is unavailable.", dismissible: false, detailed: false, version: null}`, the same text is in `alerts.headerMessages[]` and `alerts.alertMessages.CLOUD_UNAVAILABLE`, and the item is gone once the connection is back *(probed 2.5.3.102, C-8 Pro)*.
- **The relay answers `504` with body `No response from hub` after about 10 s**, the same reply as an oversized response, so a 504 alone does not say which. A request to an app id that does not exist (`/api/{hubUID}/apps/999999/…`) tells them apart without a token: a connected hub answers `404` `{"error":true,"type":"AppException","message":"Not Found"}` in under a second *(probed 2.5.3.102, C-8 Pro, disconnected; probed 2.5.2.135–2.5.2.139, C-8 Pro and C-7, connected)*.
- **Only inbound requests fail.** While the relay was down, `GET /hub/cloud/checkForUpdate` still answered. The connection dropped about 5 h after boot with no hub event and nothing in `/logs/past/json`, stayed down until a reboot, and worked again as soon as the hub was back up, so watch for it by polling `hubData` or the relay; no event announces it *(probed 2.5.3.102, C-8 Pro, one occurrence)*.

## Maker API specifics

- Device notes are read-only: `GET /devices/{id}` carries a `notes` key (added in 2.5.0), and nothing writes them. The documented device writers are `setLabel`, `setDriver` and `deleteDevice`. `/devices/{id}/setNotes?notes=…` is treated as a device command and returns 404 *(probed 2.5.2.129)*.

- **Modes:** `GET /apps/api/{id}/modes` → `[{"active":true,"id":1,"name":"Day"}, ...]` (`Content-Type: application/json`); `GET /apps/api/{id}/modes/{modeId}` switches to that mode and answers the list as it is afterwards; an unknown id or a non-numeric one changes nothing and still answers 200 with the list *(probed 2.5.2.135)*.

### Status codes

Status codes follow REST for authentication and lookup, while a write the hub declines comes back as 200 *(probed 2.5.2.133)*:

- 401 with an XML `invalid_token` body: missing or wrong `access_token` *(probed 2.5.2.133)*.
- 404 with plain text: an unknown path (JSON `{"error":true,"message":"Not Found"}`); a device that doesn't exist or isn't picked ("Device not found or not authorized"); a command the device doesn't have ("…not authorized to send that command"); a hub variable that doesn't exist or isn't picked ("Hub variable not found or not authorized"). The API doesn't say whether the object is missing or only not picked *(probed 2.5.2.133)*.
- 500 with JSON `{"error":true,"type":…,"message":"An unexpected error occurred."}`: the command threw, for example `on` called with an argument *(probed 2.5.2.133)*.
- 200 with nothing applied: a hub variable value of the wrong type (`{"result":"not authorized"}`), a mode id that doesn't exist (returns the mode list unchanged), an HSM command while HSM access is off (`{"hsm":null}`) *(probed 2.5.2.133)*.

A client must therefore compare the body of a 200 with what it asked for: for a variable write, check that `value` came back *(inferred: the 200 cases above)*.

### Device commands with arguments

- `GET /apps/api/{appId}/devices/{deviceId}/{command}/{args}?access_token={TOKEN}`. Several arguments go comma-joined in one path segment (`/holdProfile/Sleep,next`); separate segments (`/holdProfile/Sleep/next`) answer 404 *(probed 2.5.2.129)*.

### Device events via Maker API

- `GET /apps/api/{appId}/devices/{deviceId}/events?access_token={TOKEN}` *(probed 2.5.2.135)*
- Returns array: `[{"device_id","label","name","value","date","unit","isStateChange","source"},...]` *(probed 2.5.2.135)*
- Most recent events first; useful for verifying app behavior in tests *(probed 2.5.2.135)*
