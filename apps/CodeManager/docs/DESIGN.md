# Code Manager — design

Companion documents: [`FEASIBILITY.md`](FEASIBILITY.md) (measured limits, decomposition, platform verification) and [`HPM-PARITY.md`](HPM-PARITY.md) (what must be reimplemented, with HPM source citations). Repo-wide conventions in [`../../../ARCHITECTURE.md`](../../../ARCHITECTURE.md) and the dashboard-SPA conventions in [`../../../CONTRIBUTING.md`](../../../CONTRIBUTING.md) apply; this document only adds what is specific to this app.

## 1. What it is

Code Manager is a Hubitat app that owns the inventory of user code on its hub (apps, drivers, libraries, bundles, File Manager assets installed by packages) and the dependencies between those items, checks an item's upstream freshness when the user asks, and applies updates only after the user has seen the diff and a snapshot has been taken. Two rules bound everything it does: every fact it shows is either current or labelled with what it is based on (3.1), and its own load on the hub stays inside a fixed budget (5.1). It installs and maintains Hubitat Package Manager (HPM) packages from the unchanged HPM ecosystem, and it treats every other item on the hub as a package too. The UI is a File Manager SPA served over the app's OAuth endpoint, in the HubDiagnostics pattern.

Layout in this repository: `apps/CodeManager/CodeManager.groovy`, `apps/CodeManager/code_manager_ui.html`, `apps/CodeManager/README.md`, `apps/CodeManager/docs/` (these documents), `apps/CodeManager/tests/`. The folder carries a `.wip` marker until the first release. Manifests ship from the `hubitrep` mirror like the other apps.

## 2. Data model

### 2.1 The package is the unit

Everything is a package. A package has an origin, a manifest, and components; a component is one hub object (app type, driver type, library, bundle, or File Manager file) bound to one upstream location. Every hub object belongs to exactly one package and never to two — the uniform model exists so that one update path serves HPM packages, bundles, and hand-installed files alike, not because every file is worth its own row. Most hand-installed code forms a package of one, and the SPA lists those apart from real multi-component packages (10) so the model's uniformity does not become the reader's problem.

```
Package
  key          String   identity (see 2.3)
  origin       enum     hpm | url | bundle | local
  name         String   packageName, or the component name for synthesized packages
  manifest     String   name of the package's manifest document in File Manager (2.2)
  version      String?  installed package version as declared (hpm) or null
  beta         Boolean
  repo         String?  repository.json URL this package was found in (hpm)
  components[] Component
  managedBy    enum     cm | hpm | none   (transition state, see 8)

Component
  kind         enum     app | driver | library | bundle | file
  mid          String?  manifest item id (HPM uuid), null when synthesized
  name, namespace
  location     String?  upstream URL (manifest location / importUrl / bundle sourceUrl); null for local
  hubId        String?  app/driver/library/bundle id on the hub; file name for files; null = not installed
  required     Boolean
  iver         String?  installed version: manifest item version (hpm) or parsed from source (heuristic, 4.2)
  ihash        String?  sha-256 of the normalized installed source at last write or adoption
  lock         Integer? optimistic-lock version from ajax/code at last read
  lastMod      String?  hub lastModified at last inventory pass
```

### 2.2 Manifest documents

Every package has a manifest document in File Manager, `cm_pkg_<digest>.json` where `<digest>` is the first 16 hex characters of the SHA-256 of the package key, in the `packageManifest.json` schema extended with a `_cm` block (`{key, gen, origin, writtenAt}`); on every read the document's `key` must equal the key that produced the file name and `gen` must equal the registry's generation for that package, otherwise the document is treated as foreign (a file copied from another hub, or a stale write) and listed for the user rather than used. For origin `hpm` it is the downloaded manifest as published (nothing trimmed: `releaseNotes`, `licenseFile`, `dateReleased`, `minimumHEVersion` are kept, unlike HPM's `minimizeStoredManifests`). For every other origin it is written once at adoption with the degenerate content below and is thereafter the user's to edit: grouping several `importUrl` files into one package, adding a `version`, `releaseNotes`, `minimumHEVersion`, or marking components optional is done by editing the file (download, edit, upload in File Manager, or through the SPA's manifest editor), and the next inventory pass re-validates it. The engine has one read path for all origins: manifest document → components → locations. The manifest declares what a package *is*; the registry in `state` records only how it is *bound* to this hub (hub ids, installed hash, lock version, freshness pointers).

Because these documents are ordinary File Manager files, they outlive an uninstall or reinstall of Code Manager, are visible and downloadable in the hub UI, and can be copied to another hub, where they are *foreign* until the user adopts them through onboarding (8.1): a document whose `_cm.key`/`gen` has no matching registry entry is listed, never used silently. A local package whose manifest has been pushed to GitHub becomes an HPM package by re-keying (12).

Degenerate content at adoption:

- **`importUrl` item** → `{packageName: name, apps|drivers: [{name, namespace, location: importUrl, required: true}]}`; version is whatever 4.2 parses, content hash is the version of record.
- **Library** → same shape with a `libraries[]` array (an extension the HPM schema does not have; it exists only in synthesized manifests, never in anything Code Manager publishes or reads from authors); `location` parsed from the `library(...)` header; `iver` from the hub's `version` field, which is the one kind of code whose version the hub reports itself.
- **Bundle** → `{packageName: bundle name, bundles: [{name, namespace, location: sourceUrl}]}` plus its member app/driver/library ids from `/bundle/list/json`. Members of a bundle are components of the bundle package, not packages of their own; a member that also carries its own `importUrl` is shown with that URL but is updated through the bundle (the hub's private-bundle rule makes member sources read-only anyway).
- **Orphan** (no `importUrl`, no bundle, not in any HPM manifest) → `{packageName: name, apps|drivers: [{name, namespace, required: true}]}`, origin `local`, no upstream; freshness is `unmanaged` by definition, and the item still gets usage counts, snapshots, and local-modification detection.

When an HPM manifest later claims an item (by match-up or by installing the package), the local package is folded into the HPM package, its document is replaced by the published manifest, and its `ihash` and snapshots carry over.

### 2.3 Identity

Package key: the `packageManifest.json` URL for origin `hpm` (identical to HPM's `state.manifests` key, so migration is a one-to-one copy); `url:` + importUrl for origin `url`; `bundle:` + hub bundle id for origin `bundle`; `local:` + kind + `/` + namespace + `/` + name for origin `local`. Component identity on the hub is the hub id; across hubs and for match-up it is `kind` + `namespace` + `name`, exactly HPM's rule, with `alternateNames` honored and `location == importUrl` tried first.

### 2.4 Where each thing lives

| data | store | why |
|---|---|---|
| manifest documents, one per package (2.2) | File Manager `cm_pkg_<digest>.json` | the declared package; user-editable; outlives the app; portable between hubs |
| package registry (2.1: binding only, no sources, no component lists beyond ids) | `state.pkgs` | must survive reboot and push; ~80 KB at 0.1 scope, smaller from 0.2 (binding plus per-item facts); moves to a File Manager document with an in-memory cache if it grows past that |
| settings, transition flags, job state | `state` / settings | |
| operation journal (6.6) | `atomicState.op` | written from async callbacks and read on restart; must never be lost |
| per-item facts (`importUrl`, declared version, `ihash`, each with the `lastModified` it was read at) | registry, filled by the fact reader (5.2) | valid exactly while the item's `lastModified` is unchanged (3.1) |
| drift-check results per component (`rhash`, `rver`, `etag`, `checkedAt`, `httpStatus`, `error`, and the installed `lastModified` they were computed against) | `@Field static final ConcurrentHashMap` (callbacks mutate entries concurrently; `volatile` would protect only the reference) + File Manager `cm_drift.json` written at the end of each check | result of a user-requested check, regenerable; too large and too churny for `state` |
| catalog index (repositories → packages → components, with category/tags) | File Manager `cm_catalog.json` | built in the SPA, persisted through the app, read by the hub for match-up and by the SPA for browse/search |
| pre-write snapshots | File Manager `cm_snap_<kind><hubId>_<epoch>.groovy` (3 per component), first line `// cm-snapshot kind=… id=… key=… hash=…`; the header is validated against the target component and the body's hash before any rollback. File Manager assets (`kind: file`, which may be binary) are snapshotted as raw bytes to `cm_snap_file_<digest16(name)>_<epoch>.bin` with the header in a sidecar `….json`, read and written with `downloadHubFile`/`uploadHubFile` byte arrays and never through a String | rollback source; listed in the SPA per component |
| registry export | File Manager `cm_registry_export.json` on demand | migration, exit, support |
| HPM mirror (read-only copy of HPM's `state.manifests` and settings at last import) | `@Field static` + `cm_hpm_import.json` | transition UI and diffing against HPM |

Invalidation: manifest documents change only by install/import/adoption or a user edit (detected by the file's `date` in `/hub/fileManager/json`, one call for all files, so only changed documents are re-read); the registry changes only on apply/install/uninstall/adopt/import; drift results are void as soon as the installed `lastModified` changes and otherwise carry their age (3.1); the catalog expires after 24 h or on demand; snapshots are pruned per component on each write; nothing in `state` is a cache of something the hub can give back in one call.

## 3. Inventory and classification

### 3.1 What a shown fact is based on

Every value the SPA shows has one of three bases, and the SPA states which:

- **Live**: derived from the bulk reads of this request (3.2), with the payload's `asOf`. The inventory, package grouping by HPM and bundle, and every dependency are live, except libraries and their consumer lists, which are read at a time (3.2) and shown with their own `asOf`.
- **Read at a version**: a per-item fact (`importUrl`, declared version, `ihash`) stored with the `lastModified` it was read at. It is shown only while the item's current `lastModified`, which every bulk read returns, still equals that value; otherwise the item reads "not read since its last change". An item never read reads "not read yet". A cached fact is therefore never presented as current when the code has changed.
- **Checked at a time**: a drift result (5.3). It is void when the installed `lastModified` moves, and otherwise shows its age, because the upstream side can change at any time without the hub knowing.

No status claims a comparison that did not happen: `current` requires a drift result valid for the installed code. This rests on the hub changing an item's `lastModified` on every successful save and never on a rejected one, which holds for `ajax/update` and `saveOrUpdateJson` on apps, drivers and libraries (the editor's Save uses the latter), including a save of identical source, and for bundle re-import, which moves every member's `lastModified` (the fork's internal-API notes). Two cases need care. `lastModified` is printed to the second, so a fact read within 2 s of its item's `lastModified` is stored as provisional and re-read once later, since a second save in the same second would leave the value unchanged. A library save does not change its consumers' `lastModified`, but consumer hashes are taken over the unflattened source (15), so a consumer's own facts stay valid and the library carries its own.

### 3.2 Inventory from bulk reads

The inventory and the dependency graph are rebuilt from bulk reads alone: `/hub2/userAppTypes` and `/hub2/userDeviceTypes` (types, namespace, `lastModified`, instances and devices using each), `/hub2/userLibraries` (libraries and their consumer types, no source), `/bundle/list/json` (bundle members and update order, `sourceUrl`), `/hub2/appsList` and `/hub2/devicesList` (parent and child instances and devices in use), HPM's state (8.1), and the File Manager listing. Nothing in this view is cached in `state`. The bulk reads are shared by concurrent requests and made at most once per 30 s (5.1). Libraries and their consumer lists are read at a time, not with each view: refreshed in the background when older than 10 min while the SPA is open (page load starts it) and on demand ("Refresh libraries"), and shown with their `asOf`. A library save moves only the library's own `lastModified`, which only the library list carries, so type-list changes cannot trigger the refresh. The list costs 10–20 s on a hub with 26 libraries; its measured cost is stated in the README.

Classification per component, in this order: `hpm` (hub id appears in an HPM-origin package), `bundle` (hub id appears in a bundle's member ids), `url` (has an `importUrl`), `local` (none). `url` versus `local` needs the per-item `importUrl`, so until the fact reader (5.2) has read an item it is classified `unread`, shown under its own heading, never guessed as `local`. An HPM package that installs a bundle owns that bundle and its members: the bundle component binds to the installed bundle by its `sourceUrl` (the manifest's bundle `name` is not the hub's bundle name), and the members are folded into the HPM package rather than forming a second package of the same name. Bundle components bind by location and File Manager files by name, both re-checked on every read, so a component reads as absent only when it genuinely is.

A component a package declares but the hub does not have is `missing` when the manifest marks it required and `not-installed` when it does not. HPM manifests declare every component a repository ships and mark most of them optional, so `not-installed` is the ordinary state for the ones the user never chose. Absent components are shown with their package, are not counted as installed code, and are never removable.

### 3.3 Dependencies and safe-to-remove

Usage index, from the same bulk reads: app type → instances (`usedBy`), driver type → devices (`usedBy`), library → consumer types (`usedByAppTypes`/`usedByDeviceTypes`, names resolved to ids against the type lists), read at a time with the library list (3.2) and shown with its `asOf`, bundle → members, parent instance or device → children. The device-level drill-down (device → apps, `appsUsing[]` from `fullJson`) is fetched on demand for one device.

A component is listed as removable when it is installed, has zero usage, and is not a member of a bundle with any member in use. That list is live and needs no source. What it cannot see is code that would create the type later (`addChildDevice`/`addChildApp` naming it), so the list says "no current use", and the check that a parent could create it runs when the user asks to remove one item: one source read per installed app or driver that calls `addChildDevice` or `addChildApp`, found from the per-item facts where they are valid and read under the budget otherwise. The uninstall path re-checks `usedBy` live and `deleteJsonSafe` refuses in-use types regardless.

### 3.4 Freshness statuses

Freshness exists only where a drift check (5.3) has run: `current`, `update-available`, `changed-upstream` (hash differs but no ordered version comparison is possible), `modified-locally` (installed hash differs from the adoption hash), `broken-source` (7), `private` (source not readable), `unmanaged` (origin `local`, no upstream), and `not-checked` (no valid drift result). A package's status is the roll-up: `broken-source`, then `incomplete` (a required component is absent), then `update-available`, `changed-upstream`, `current`; a package with nothing checked reads `not-checked`. For an HPM package the roll-up ignores the members of a bundle it installed, because HPM updates on the manifest `version`.

## 4. Version detection without version strings

### 4.1 Two signals, stated trust

**Content hash** is the signal of record for every origin. `ihash` is the sha-256 of the installed source after normalization; `rhash` is the same function over the upstream body. Normalization: strip a UTF-8 BOM, convert CRLF to LF, strip trailing whitespace on each line, collapse to exactly one trailing newline. `ihash != rhash` means "changed upstream relative to what is installed" and is always trusted; it does not say which side is newer. `MessageDigest` is available in the sandbox (in use by this repository's Blink integration and by several community drivers).

**Declared version** is a heuristic everywhere except HPM manifests and libraries. Extraction runs an ordered regex list over the first 400 lines of the source (long license headers push the constant down): `@Field\s+(?:static\s+)?(?:final\s+)?(?:String\s+|def\s+)?\w*(?:[vV]ersion|VERSION)\w*\s*=\s*['"]([^'"]+)['"]` (covers `CODE_VERSION`, `VERSION`, `DRIVER_VERSION`, `APP_VERSION`, `driverVersion`, with or without `static`, `final`, and a type); the same without `@Field` for `static final String VERSION = …`; `(def|static String|String)\s+(version|appVersion|driverVersion)\s*\(\)\s*\{\s*(return\s+)?['"]([^'"]+)`; `version\s*:\s*['"]([^'"]+)` inside a `library(` or `definition(` block; and a header-comment `[Vv]ersion[:\s]+v?(\d+(\.\d+)+)`. The first hit wins and the idiom that matched is recorded (`iverSrc`) so the SPA can show how confident the value is. The community idiom survey behind this list is in the host repo's design notes; values seen in the wild include `5.83.4`, `v1.10 (29th August 2023)`, `2.3.9l`, `1.09 (2023-04-16)`, `2023-05-25`, `v0.2.260409`, and no constant at all.

Comparison: strip a leading `v`, cut at the first space or parenthesis, split on `.`, compare numerically segment by segment with missing segments as 0; a segment that is not an integer after stripping a trailing letter run makes the comparison **unavailable**, not 0 (this is the difference from the existing `compareVersions` in HubDiagnostics/MultiHubInventory, which zeroes such segments, and from HPM's routine, which has an ordering defect). Date-shaped values (`YYYY-MM-DD`, `YYYYMMDD`) compare as dates.

### 4.2 Truth table

| `ihash` vs `rhash` | ordered compare | status | apply offered |
|---|---|---|---|
| equal | any | `current` | no |
| differ | remote newer | `update-available` | yes |
| differ | unavailable (either side unparsable or no constant) | `changed-upstream` | yes, labeled as "upstream differs; no version to compare" |
| differ | remote older or equal | `changed-upstream` with a warning (upstream regressed or local has unreleased edits) | yes, warning shown |
| installed hash ≠ `ihash` | — | `modified-locally` (checked first; overrides the rows above) | yes, with a three-way note: snapshot of the local edit is taken before any write |
| HPM origin | manifest `version` compare (the authoritative field) | as HPM, plus the hash row for each component so a re-published file under an unchanged manifest version is still visible | yes |

For HPM packages the manifest version stays the decision input for "update available", exactly as authors expect; the per-component hash adds visibility of unversioned re-publishes without changing what the author has to do.

## 5. Refresh architecture

### 5.1 Hub budget

Code Manager's reads go to the same web server that serves the hub's admin UI, and a per-item source read can take tens of seconds on a large or unusual item. Its own load is therefore bounded by fixed rules, documented in the README with their measured cost:

- **No per-item read inside an endpoint handler**, except for the one item the user just acted on (a single drift check, a remove check). Anything wider is a background job (9).
- **Memory**: a per-item read loads the whole source into the shared JVM heap, and JSON parsing roughly doubles it. Reads run one at a time, hold nothing after hashing, and sources above a fixed size are read only when the user asks (`downloadFull` is flattened, and hashes are taken over the unflattened source, 15). A run of full-source reads on a hub with several multi-hundred-KB and one 2.7 MB source coincided with a heap exhaustion and hub restart.
- **One hub read in flight** for background work, with a fixed gap between reads, and none while a write is outstanding (6.6).
- **Bulk reads are shared** and made at most once per 30 s, whoever asks.
- **Back-off per item**: a read that times out or errors twice in a row is retried after 1 h, then after 24 h, and the item shows "could not read" with the error. It never costs a full timeout on every pass.
- **Measured before each release**: the release's cost on the development hub (`/logs/json` runtime per app, bulk-read and per-item timings) is recorded in the README; a release whose cost was not measured does not ship.

Upstream fetches go to GitHub, not the hub, and run 6 in flight (two of the eight async slots stay free for endpoint handlers); they are still counted against the hub's async budget.

### 5.2 Fact reader

A background job reads per-item facts (`importUrl`, declared version, `ihash`) for items whose facts are missing or not valid for their current `lastModified` (3.1), newest-changed first, under the budget (5.1). The source is hashed and discarded. On a first install it works through every item once; afterwards it reads only items that changed. The SPA shows its progress ("facts read for 140 of 212 items") and every unread item says so (3.1). It starts on install, on `systemStart` after 5 min, after any write by Code Manager, and when a bulk read shows an item's `lastModified` moved; it never runs inside a request.

### 5.3 Drift checks, on request

A drift check compares an item's installed hash with its upstream body. The user starts it for one item, one package, or everything; there is no scheduled check, no badge for component updates and no notification until those are designed (14); the label badge reports only Code Manager's own version. One item runs synchronously in the endpoint handler (the caller needs the result); a package or everything runs as a job with progress. The job first brings the facts of the items in scope up to date (5.2), then fetches upstream with `If-None-Match` on the stored `etag` (a `304` costs no body and only stamps `checkedAt`), then normalizes, hashes, version-parses and compares (4). HPM packages compare the manifest `version`/`betaVersion` first and fetch component bodies only when the manifest changed. A bundle's freshness is its manifest entry (hpm) or `not-checked` with a "re-import to refresh" action, since the hub gives no hash for an installed bundle.

### 5.4 What the SPA does itself

Catalog build (all subscribed `repository.json`, then each `packageManifest.json`) runs in the browser, which can do a few hundred fetches in parallel with no hub involvement, and the result is posted to `POST /api/catalog` for persistence. The diff view fetches the upstream body directly when the host sends CORS headers and falls back to `POST /api/fetch` otherwise (6.3). Calls into the hub's own `/api/*` go through the SPA's 3-wide semaphore (10); direct GitHub fetches do not. Nothing the SPA fetches is trusted at apply time; the hub re-fetches.

## 6. Safety model for the apply path

### 6.1 Rules

No write happens without a user action on a specific *plan* (6.2) in the same SPA session, with one exception: packages the user has explicitly opted in to unattended apply (6.5). Every write route — single-component apply, rollback, package install, modify, repair, uninstall, bundle import — starts from a plan token, and the engine executes only the steps the plan lists, against the bindings the plan recorded. No other scheduled job writes code. One component is written at a time. Every write is preceded by a snapshot of the installed source to File Manager and followed by a read-back verification. A failed compile changes nothing on the hub (measured: the previous source and lock version stay in place and the hub returns the compiler message), so the only rollback cases are multi-component packages and post-write regressions the user reports.

### 6.2 Sequence: plan, then execute

1. **Plan** (`POST /api/plan` with an operation — `apply` of one component, `install`/`modify`/`repair`/`uninstall` of a package, `rollback` to a snapshot, `bundle-import` — and its target; returns `{jobId}`, and the finished job's result carries the plan): planning is a job like every other long operation (10), because a package plan fetches one body per component and a single slow host would push a synchronous route past the cloud relay's ~10 s limit. The job builds an immutable draft server-side — for each step the plan will take, the hub fetches the upstream body (HTTPS only; 2 MB cap; 30 s timeout), normalizes and hashes it, rejects it if any quoted literal exceeds 65,535 UTF-16 units or the body does not parse as a `definition(`/`metadata {`/`library(` source, runs the version parse, and and the completed job returns `{planId, steps: [{component, action: create|update|resave|delete|restore|file|bundle, hubId?, lock?, ihash?, rhash?, rver?, size, usedBy?, expect: {exists, lock?, ihash?, usedBy?, bundleMember?}, warnings[]}]}`. `expect` is the step's precondition, stated explicitly rather than implied by which fields happen to be present: `create` expects `exists: false` for `kind`+`namespace`+`name` (re-checked against the bulk type lists at execution, so an object the user imported by hand after planning is not duplicated and the step fails with `precondition-drift` instead); `update` and `resave` expect `exists: true` with the recorded `lock` and `ihash`; `delete` expects `exists: true`, the recorded `ihash`, `usedBy: 0` re-read live from `usedBy`/`usedByAppTypes`/`usedByDeviceTypes`, and `bundleMember: false` re-read from `/bundle/list/json` (an instance, device, or bundle attached after planning makes the step fail, and `deleteJsonSafe` remains a second guard); `restore` expects `exists: true` with the current `lock`; `file` expects the File Manager entry's presence or absence as planned; `bundle` expects the membership recorded at planning. — every step bound to the component's identity, its installed lock version and hash where the object exists, and the hash of the body that will be written where one is fetched (for `restore`, the snapshot's header hash; for `delete`, the installed hash and the live usage count; for `bundle`, the zip URL and the current membership, with the non-reversible flag of 6.3). The `planId` is issued only when the draft is complete — a partially fetched plan is never approvable — and is a random token held on the hub (`@Field static ConcurrentHashMap`, so it does not survive a restart, which is the intended expiry) with the whole step list, a 10-minute expiry that starts at completion, single use. Planning holds no write lease and fetches under the hub budget and the upstream in-flight limit (5.1), so a plan never blocks a running operation and never exceeds the in-flight cap; the SPA polls the job and renders the step list when it completes. It is not an authentication boundary — a caller holding the OAuth token can call any route — it is what turns the rule "no write without a specific plan" from a convention into a check the engine performs: a start without a live plan is refused, a plan older than 10 minutes is refused, and at execution each step's `expect` block is re-evaluated against the live hub (existence, `lock`, `ihash`, usage, bundle membership) and the body is re-fetched and re-hashed against `rhash`; any drift stops the operation at that step with `precondition-drift` or `changed-since-plan`, before the step's snapshot or write. A single-component apply is a one-step plan; the SPA renders the diff for every `update` step from the installed source (`GET /api/item/{kind}/{id}/source`) and the upstream body. The SPA renders the diff (installed source via `GET /api/item/{kind}/{id}/source`, upstream via direct fetch or the returned body).
2. **Execute** (`POST /api/apply/start` — or the package and rollback `…/start` routes — with the `planId`; returns `{jobId}`, progress via `GET /api/jobs/{id}` as in 10): the hub acquires the write lease (6.6), consumes the plan (`no-plan`, `plan-expired`, `plan-mismatch` otherwise), and then, per step, re-fetches, re-hashes, and aborts with `changed-since-plan` if the hash differs from the step's `rhash`; re-reads `ajax/code` and aborts with `lock-changed` if the lock version moved (someone saved in the editor meanwhile); writes the snapshot `cm_snap_<kind><id>_<epoch>.groovy`; posts to `/app|driver/saveOrUpdateJson` with `id`, `lock`, `source` (re-parses `definition()`; `ajax/update` would not); classifies the write into exactly one of three outcomes: `compile-error` (the hub answered `success:false`: return the compiler message verbatim and stop; nothing changed), `ok` (answered success), or `unknown` (any exception, timeout, or missing or unparseable response: never treated as failed, because a request timeout is not evidence the save did not land, and a large source can finish compiling after the client has given up); the step is journaled `unresolved` before the POST is sent. An `unknown` outcome is resolved by read-back, never by retry (see *Unresolved writes* below); on `ok`, or once an unresolved step resolves to `verified`, re-reads `ajax/code`, verifies the hash equals `rhash`, updates `ihash`, `iver`, `lock`, `lastMod`, and `checkedAt`; re-enables OAuth when the manifest says so and verifies `oauthClientId` is present; prunes snapshots beyond the retention count.

**Unresolved writes.** The engine polls the bulk type list for the step's `lastModified` and the type's lock version, and `ajax/code` for the hash, at a fixed interval until a resolution deadline, refreshing the write lease on every poll. Hash equals `rhash`: the step is `verified` and the operation continues with the next step's usual re-checks. Hash equals the snapshot and `lastModified` and lock version are unchanged at the deadline: `not-written` (a failure; 6.3 applies). Anything else (a hash that matches neither, or a changed `lastModified` with an unreadable body): `drift`, which stops the operation. The same body is never re-posted automatically, because a second POST queued behind the first compile is a second compile and can overwrite an edit made in between. The deadline is sized from the component's recorded or size-estimated compile time and bounded by a fixed ceiling documented in the README; it is not the HTTP client timeout, and the client timeout is not assumed to equal the value requested (the hub may cap a call's wait lower; to be measured before 0.2 writes, 14).
3. **Rollback** (`POST /api/rollback/start` with a plan whose single step is `restore` of a snapshot file name, never a list index): same write path with the snapshot body after its header is validated (2.4); the current source is snapshotted first, so rollback is itself reversible.

Libraries use `POST /library/saveOrUpdateJson` with `{id, source, version}`, the same contract as apps and drivers (the Libraries Code editor's save path, response `{success, message, id, version}` in ~1 s); delete is `GET /library/edit/deleteJson/{id}`, which the admin UI blocks while `usedByAppTypeCount + usedByDeviceTypeCount > 0`. A library save does not touch its consumers' records (their `lastModified` and lock `version` are unchanged afterwards) and the flattened source the hub serves for a consumer (`downloadFull`) reflects the new library text immediately, so the hub composes includes from the live library at read time. Whether a consumer's compiled class is refreshed without a re-save is not established; until it is, every library change carries explicit `resave` steps for its installed consumers (6.3) — each consumer's unchanged source re-posted through `saveOrUpdateJson`, one compile per consumer, journaled and verified like any other step — which is also what makes a compile error in a consumer visible at apply time rather than at the consumer's next load. Files use `uploadHubFile` after snapshotting the existing file with `downloadHubFile` (if present). Bundles use `/bundle2/uploadZipFromUrl`; the member sources are snapshotted first (readable for non-private bundles), since a bundle import overwrites them.

### 6.3 Package transactions and the fetch endpoint

A package operation is a multi-step plan in dependency order: bundles first (the hub imports a bundle's own libraries, apps and drivers atomically), then libraries — ordered among themselves by their `#include` lines when a library includes another — then drivers and apps, then File Manager files. A consumer of a library that changes in the same plan is compiled after the library: the plan lists an explicit `resave` step for every installed consumer of each changed library (found from `usedByAppTypes`/`usedByDeviceTypes` and the consumer's `#include` lines), bound to the consumer's lock and hash, placed after the library step and before any `update` of that consumer (an `update` subsumes the `resave`). HPM's apps-before-drivers order has no dependency meaning and is not kept. The plan is produced and approved exactly like a single-component apply: the plan step list *is* the preflight, every body is fetched and hashed before the user sees the plan (HPM's download-first phase, kept), and execution re-fetches and re-checks each step. On a failure at component *n* (`compile-error` or `not-written`), components 1..n-1 are restored from the snapshots taken seconds earlier, the outcome per component is returned, and the registry records the package as partially applied with the failing component's message. The user decides whether to retry or leave it. Three rules bound the restores. (1) A step that is `unresolved` is not a failure: no restore and no later step starts, and no other write of any kind is issued, until it resolves, because a save issued while the hub is still compiling the previous one can stall or time out and, if it lands, can overwrite a write that succeeded. If it does not resolve by the deadline the operation stops as interrupted with the step `unresolved`, with no restores, and the recovery view (6.6) takes over. `drift` stops the same way. (2) Before each restore, the live hash is compared with the hash the journal records for that step (`rhash` if `verified`, the snapshot hash if `not-written`); a mismatch skips the restore and reports the component as `drift` rather than overwriting an unknown state. (3) Only steps this operation verified are restored; the failing step is never restored by snapshot unless it later resolves `verified`. Among steps with no dependency between them (no library-before-consumer relation), the plan orders them by ascending source size, so the slowest compile comes last and a stalled write leaves the fewest components behind it unwritten. The plan shows each step's recorded write-to-verified time from the registry (blank until measured) next to its `size`, and warns on a step whose recorded or estimated time approaches the resolution deadline. Every step is journaled (6.6), so a hub restart or code push in the middle of a transaction leaves a record of exactly which components were written and verified.

Bundles are the exception to the rollback guarantee and are labeled as such. A bundle import overwrites its member types in one hub-side operation; for a **non-private** bundle the members' sources are snapshotted first and can be restored one by one, and the import is verified by re-reading `/bundle/list/json` membership and the members' hashes; for a **private** bundle the members' sources are unreadable (the hub refuses them to the editor and to `ajax/code`), so there is nothing to snapshot and nothing to verify against. Private-bundle updates are therefore presented as **not reversible**, require their own confirmation naming that fact, and are never eligible for unattended apply (6.5); non-private bundles are excluded from unattended apply as well until a bundle-level hash exists on the hub.

`POST /api/fetch` exists only for hosts without CORS and accepts a component key or catalog entry id, never a URL; the hub resolves the URL from the registry or catalog. Install-from-URL first records the URL as a pending package (`POST /api/package/add`) and then plans through the same key-based path. All upstream fetches are HTTPS; `http://` locations (one repository in the master list) are shown but not fetched unless the user enables a per-repository exception.

### 6.4 Things the engine refuses

Writing while a sweep is mid-dispatch to the same component; writing a component whose hub id no longer exists (the HPM dangling-`heID` case: offered as "reinstall" instead); writing Code Manager's own type from a plan older than 10 minutes (self-update is allowed and finalized by the `CODE_VERSION != state.version` check on the next invocation, with `atomicState.pendingSelf` carrying the expected version across the swap); deleting a type with `usedBy` non-empty (the hub refuses too); any write when `state.hpm.mode == 'observe'` to a component HPM manages (8).

### 6.5 Unattended apply, opt-in per package

Opt-in is a per-package flag in the registry (`auto: true`), set from the SPA with a confirmation that lists the package's components. It is never inherited: a newly installed or newly adopted package starts opted out, there is no global "all packages" mode, and Code Manager's own type is never eligible. HPM's `appsToAutoUpdate` list seeds the flags at import when the user confirms it during onboarding; HPM's `Always` mode imports as no flags, with a note saying so.

Unattended apply needs scheduled upstream checks, which are deferred (5.3, 14); it ships with them, not before. The unattended pass is the one path that executes without a user-approved plan; it still builds a plan internally (so every step carries the same bindings and the same re-checks) and takes the write lease like any other operation. It runs at the end of each scheduled check, after its results are persisted. Eligible packages are those opted in whose status is `update-available` by an ordered comparison (manifest `version` for HPM origin, parsed version otherwise) — not `changed-upstream` without an ordered version, not `modified-locally`, not `broken-source`, and not while a plan or an operation for the package is in flight. Each eligible package runs the package transaction of 6.3 unchanged: download everything first, snapshot, write one component at a time, verify by read-back, restore earlier components from their snapshots on failure. Packages are processed serially, at most three per run (fixed value), the rest deferred to the next run, which bounds compile load on the hub. Every outcome is recorded in an unattended-apply log shown in the SPA with per-component results and one-click rollback, and is sent to the notification devices when configured. A failed unattended apply clears the package's opt-in until the user re-enables it. Packages containing a bundle are not eligible (6.3). Compile cost is also an eligibility rule: a package with any component whose recorded write-to-verified time exceeds a fixed threshold, or, where no time has been recorded, whose size exceeds a fixed bound, is not eligible, because an unattended run cannot be watched through an `unknown` outcome and a long compile holds the write lease and loads the hub; such a package is updated from a user-approved plan. An unattended operation that ends with any step `unresolved` or `drift` is reported like a failure and clears the opt-in.

### 6.6 Write lease, operation journal, and recovery

There is exactly one writer at a time, and that is enforced mechanically rather than by the "one component at a time" wording. Two layers, because neither alone covers every case:

- **In-process exclusion**: a `@Field static final Semaphore WRITE = new Semaphore(1)` (the sandbox allows `Semaphore`). Every write route and the unattended pass call `tryAcquire()` and return `write-busy` immediately when it fails; nothing queues, the SPA shows who holds it (operation id, package, started-at from the journal) and offers retry, and the unattended pass simply defers the package to the next run. `singleThreaded: true` is deliberately not used: it would serialize the job-status and inventory endpoints behind a 30-second compile and the page would appear hung.
- **Durable lease**: the semaphore is reset by a code push and a restart while a job thread from the previous class may still be running. So after the semaphore, the route checks `atomicState.op`: if it exists with an unexpired `lease`, the write is refused with `write-busy` even though the semaphore was free. The operation then writes `atomicState.op` with `lease = now + 10 min`, refreshes the lease after every step and on every poll of an unresolved step (the write timeout does not bound a step: a save can outlive its request, so a step is bounded by the resolution deadline and the lease is refreshed at an interval well inside its 10 minutes while the step is unresolved, so a live operation never lets its lease lapse), and clears `op` only after commit. A lease found expired at any entry point means an interrupted operation and triggers the recovery below. A live lease with no in-process job is ambiguous only after a code push (the previous class's thread may still be running), and in that case it is left alone until it expires or clears itself; after a hub restart no such thread can exist, so the `systemStart` handler marks any `atomicState.op` interrupted immediately, regardless of its lease, and the recovery view is available on the first page load rather than up to ten minutes later.

Acquisition order is always semaphore → lease check → journal write → work → journal clear → semaphore release (in `finally`), so two routes, two clients, or a route and the scheduler cannot both pass the check, and a journal is never overwritten by a second operation.

Every write path — apply, rollback, install, modify, repair, uninstall, adopt, re-key, import — runs as one *operation* recorded in `atomicState.op` before its first side effect: `{id, kind, pkgKey, startedAt, lease, steps: [{component, action, snapshot?, status: pending|unresolved|written|verified|not-written|drift|failed|restored, error?}]}`. `atomicState` is used because the steps are advanced from async callbacks and from the job thread, where plain `state` writes can be lost. The order within each step is fixed: write the snapshot, mark `pending`, mark `unresolved` immediately before the POST, send the write, mark `written` only when the hub answered success (an unknown outcome stays `unresolved` until read-back resolves it), read back and hash, mark `verified`; manifest documents and registry bindings are committed last, after every step is `verified`, and the operation is cleared only after that commit. The registry's per-package `gen` is incremented at commit, and the value is written into the manifest document's `_cm.gen`, so a document from an uncommitted or superseded write is detectable (2.2).

On `initialize()` (hub restart, `updated()`) and on any write-route entry, a non-empty `atomicState.op` whose lease has expired is an interrupted operation. Nothing is re-attempted automatically: steps marked `verified` are real, steps marked `written` are re-verified by hash, steps marked `unresolved` are resolved by the same read-back as a live operation (hash equals the intended body: `verified`; equals the snapshot: `not-written`; neither: `drift`) and never re-posted, steps marked `pending` are checked (the hub object's hash equals either the snapshot or the intended body), and the result is surfaced in the SPA as an interrupted operation with a per-component state and a one-click rollback from the recorded snapshots; each rollback restore re-checks the live hash against the journaled state first (6.3), so a write that landed late is never undone blindly. The registry is updated to whatever was verified, so the inventory never claims a component is at a version it is not. This journal is also what makes the two-store model of 2.4 safe: a manifest document is never written before the components it describes are verified, and a document whose `_cm.gen` does not match the registry is never used to drive a write.

The fact reader and drift checks keep no journal — their output is regenerable — but a job interrupted by a restart is detected the same way HubDiagnostics detects an orphaned audit scan (stale job state with no live job) and marked `stale` rather than `done`; live job state lives in `ConcurrentHashMap`/`ConcurrentLinkedQueue`/`AtomicInteger` only, and a scalar job snapshot in `state` serves the status endpoint, with progress read from the atomics while the job is live.

## 7. Broken-source detection

Hub-scoped and mechanical: does the code on this hub still resolve upstream? Per component, each drift check records `httpStatus`; `404`, `410`, a DNS failure, or a TLS handshake failure on three consecutive checks marks `broken-source`, and a single such result is shown as such with its date; `5xx`, timeouts, and `429` are `unreachable` and do not count toward the three. Per package: a `packageManifest.json` that no longer resolves is `manifest-gone`; a package whose `repository.json` no longer lists it is `delisted`; a repository removed from the master list is `repo-delisted`, and its packages stay installed and updatable from their own manifest URL as long as that resolves (HPM's own behavior on delisting is to silently drop the repository from `installedRepositories`). No field anywhere expresses a quality judgment about the package; the only statuses are about reachability and listing.

## 8. Migration and exit

### 8.1 Onboarding: import HPM's state rather than rebuild it from a scan

A scan of the hub yields, per item, its name, namespace, hub id, `importUrl`, source, and usage. It cannot yield what a package manager is made of: which manifest an item belongs to (one manifest on the test hub covers 23 drivers; another covers an app, a driver, and two File Manager files), the manifest item ids that per-item versioning and `alternateNames` hang on, which optional components the user chose, beta opt-ins, subscribed and custom repositories, which File Manager files a package installed (a file has no namespace and no `importUrl`), the package ↔ bundle link, and the declared installed version for the majority of code that carries no version constant (a narrow regex set matched 36 of 159 sources on the test hub). `importUrl` is not a reliable key back to the manifest either: HPM writes the downloaded source verbatim, and the `importUrl` inside it is whatever the author put in `definition()`, which need not equal the manifest `location` (on the test hub, of the HPM-managed apps and drivers that carry an `importUrl`, 14 equal their manifest `location` and 10 do not). Rebuilding package membership from a scan means running HPM's own fallback match-up — fetch every package manifest of every repository — followed by a user decision for every name collision across forks, and it still loses per-item ids, optional selections, files, and versions. Reading `state.manifests` is one request, lossless, deterministic, and it surfaces HPM's own drift (a dangling `heID`) instead of hiding it.

Onboarding therefore offers three starting points, and every one of them ends with the scan:

1. **Import from HPM** (default when a `dcm.hpm` type is installed) — 8.2. The scan then adds everything HPM does not know: `importUrl` items, libraries, bundles, orphans, and HPM-managed items whose hub id has gone.
2. **Start from the hub** (no HPM, or the user declines the import) — scan, then match each unmanaged item against the catalog: `importUrl == location` first, then `name`+`namespace` and `alternateNames`. Unambiguous matches are proposed as packages to adopt; collisions are listed for the user to pick one or skip. Each adopted package is marked either *assume current* (the installed hash becomes the baseline and the manifest version is recorded) or *mark for update* (HPM's `pkgUpToDate = false`, version `0.0`); *assume current* is the default because the first drift check reveals any real difference by hash regardless. Everything unmatched becomes origin `url` or `local`.
3. **Import an export** — `cm_registry_export.json` from a previous install or another hub, or foreign manifest documents found in File Manager (2.2); hub ids are re-resolved by `kind`+`namespace`+`name`, since they differ per hub, components that do not resolve are listed for reinstall or removal from the registry, and each adopted document is rewritten with this hub's registry generation.

After any starting point, one reconciliation view lists what needs a decision and nothing else: components a registry claims that do not exist on the hub (reinstall or forget), unmanaged items that match a catalog package (adopt), HPM's `appsToAutoUpdate` packages (confirm as unattended opt-ins, 6.5), and private-bundle members (read-only, no decision). The HPM import can be re-run while HPM is installed; the match-up of option 2 can be re-run for code installed later.

### 8.2 Import

`POST /api/hpm/import` locates HPM by `namespace == "dcm.hpm"` in `/hub2/userAppTypes` and its instance id from `usedBy`, reads `GET /installedapp/statusJson/{id}`, and converts `appState.manifests` one-to-one into origin-`hpm` packages with the same keys; `heID` becomes `hubId` after checking the id still exists (a dangling id becomes a component with `hubId: null` and a `missing` flag, shown in the transition panel); `ihash` is computed from the current source on the hub; `installedRepositories`, `customRepositories`, and `pkgBetaOn` become Code Manager's repository subscriptions and beta opt-ins. The import is idempotent and re-runs whenever the inventory is read while HPM is installed (it is one bulk read, 3.2), so Code Manager tracks what HPM does during the transition. Nothing is written to HPM.

### 8.3 The transition is a phase with three states

`state.hpm.mode` ∈ `absent | observe | manage`, shown as a persistent panel in the SPA.

- **`absent`** — no `dcm.hpm` type on the hub, or the user dismissed the panel after uninstalling HPM. Code Manager is the only writer.
- **`observe`** (the default whenever HPM is detected) — HPM is the writer for every package it manages. Code Manager shows those packages with a "managed by HPM" badge, runs drift checks on them for visibility when asked, and refuses apply/install/uninstall on their components (6.4). Code Manager is the writer for everything else (`url`, `bundle`, `local`). Exit in this state is trivial: uninstall Code Manager; HPM is unaffected.
- **`manage`** — the user flips a switch in the panel. Precondition, checked live from `GET /installedapp/statusJson/{hpmId}` → `installedApp.disabled`: the HPM instance is **disabled** (the hub's per-app disable toggle, which stops its schedules and its pages) or absent. While HPM is enabled the switch is off, with the instruction to disable HPM from the Apps list first; Code Manager never changes another app's settings or state. The precondition is re-checked immediately before every write to an HPM-origin package, and an HPM that has been re-enabled in the meantime makes the write refuse with `hpm-enabled`. Two apps writing the same package is an unsupported state, not a degraded one, and the design has no mode in which it can occur. Disabling rather than uninstalling keeps HPM's state intact for the fall-back: re-enable HPM, uninstall Code Manager, and HPM resumes with its own registry; packages Code Manager updated meanwhile show in HPM as "updates available" (HPM's stored versions lag) and applying them re-pushes the same source, which is harmless; packages Code Manager installed are adopted by HPM's Match Up. The panel recommends uninstalling HPM once the user is comfortable. Exit from this state: uninstall Code Manager, open HPM, run Match Up; packages Code Manager installed after the switch are adopted by HPM's name+namespace match, and installed code is ordinary hub code throughout, so nothing is lost. Code Manager also writes `cm_registry_export.json` on every registry change so a support case or a later reinstall has the full mapping.

The phase ends when the user deletes the HPM app instance and type; Code Manager notices on the next inventory pass, switches to `absent`, and keeps the HPM-origin packages as its own. There is no state in which two apps can write the same package: `observe` has one writer per package by construction, and `manage` requires HPM disabled and re-checks it before every write.

## 10. SPA conventions inherited from HubDiagnostics

HubDiagnostics' SPA is this repository's reference implementation (CONTRIBUTING.md "Building a dashboard SPA"); its `CODE_REVIEW.md` and `ARCHITECTURE.md` record what went wrong on the way there. Code Manager starts from the current HubDiagnostics code, not from a simplified copy — MultiHubInventory 0.1.0 was the simplified copy, and it shipped unusable.

**Division of labour.** The hub is the constrained side. Groovy collects and normalizes (stable field names, epoch-ms dates, `{ok, data, error}` wrappers, fail-soft reads); the SPA derives and presents (sorting, filtering, top-N, diffs, grouping, severity). If the SPA already has the inputs, the derivation lives in the SPA, because rule changes then cost no push and no reinit. One stated exception: the freshness status of 4.2 is computed on the hub, because the label badge, the notifications, and the unattended pass (6.5) need it with no browser open; the SPA still receives the raw inputs (`ihash`, `rhash`, `iver`, `rver`, `iverSrc`) so it can explain or re-derive the verdict.

**Skeleton.** One static HTML file, no build step, no framework; `:root` tokens `--ok/--warn/--crit/--bg/--card/--border/--text/--muted`; sticky header with the app name, hub name and firmware, **Docs ↗** to the README, **⚙ Settings** to `/installedapp/configure/{id}` derived from `api_base` and hidden when the placeholder is literal (WORKBENCH), and a Refresh button; tab router `R = {tab: renderFn}` that persists the tab in `localStorage` and re-renders only empty or errored panels (clear the panel first to force a re-render). `serveUI` substitutes `${access_token}`, `${api_base}`, `${app_version}`; any other occurrence of those literals in the SPA's own JS must be assembled at runtime (`'$' + '{access_token}'`) or it is rewritten at serve time; a literal `</script>` inside JS must be written `<\/script>`. `WORKBENCH = true` plus `MOCK_DATA` keyed by endpoint makes the page run hub-free; the mock data ships in production (accepted, ~4 % of the file). No offline report mode: the exportable artifact is the registry JSON, not the page.

**`api()` wrapper.** `fetch(B + '/api/' + ep, {headers: AUTH()})`, the token in an `Authorization: Bearer` header rather than the query string so it stays out of hub and proxy access logs; the platform matches the scheme case-sensitively, so it must read exactly `Bearer`. A browser navigation cannot carry a header, so the config page's bootstrap link to `/ui.html` keeps the `?access_token=` form. `!r.ok` → throw, per-tab `loading(P)` / `err(P, e, retryFn)` with a Retry button. Flat in-page cache with a 2-minute TTL as the outer gate; every mutating `post()` is followed by `drop(key)` for the affected endpoints, and `refreshPage()` drops the current tab's keys from an explicit map; nothing is invalidated by time pressure. Two things HubDiagnostics still lacks are built in from day one: an in-flight `Promise` registry in `api()` so double-clicks and timer ticks never duplicate a request, and a concurrency semaphore of **3** for `/api/*` calls (each OAuth endpoint fans out to several hub calls against a ~20-slot hub HTTP pool; an unbounded `Promise.all` exhausted it in HubDiagnostics 5.32.0 with partial, fail-soft-masked failures). Direct browser fetches to GitHub (5.3) are outside that semaphore; they never touch the hub.

**Primitives, copied from the current HubDiagnostics source.** `tbl(cid, cols, rows, opts)` as the only table engine (tbody-only re-render on sort, 150 ms debounced filter, filter and sort over the rendered cell text, `_<field>Color` per cell, `<details>` collapse); never a second string-built sortable table. `h()` escaping on every value that is not a literal in the SPA's own source — hub payloads *and* everything that originates upstream: manifest fields, package and repository names, descriptions, release notes, author and link fields, upstream error bodies, and source text. Upstream content is the most hostile input this page renders, and the page carries the OAuth token, so one raw `innerHTML` of a manifest field is a request-forging vector. Release notes and descriptions render as text (HPM shows them in a `<textarea>`, so authors do not expect markup); links from manifests are rendered only when they parse as `https://` URLs and never as raw anchors from the document; the diff and source views are built from text nodes, never from HTML strings; CSV exports prefix cells starting with `= + - @` with a quote. Mode 3 tests include hostile fixtures (a manifest and a source containing `<script>`, `onerror=`, `javascript:` URLs, CSV formulas) asserting the rendered output is inert. No arrow parameter named `h`. `mc()`/`ni()` metric and name-value items; `.badge .b-ok/.b-warn/.b-crit/.b-muted` plus the source badges; `.alert.a-*` rows; `.btn` variants. Names are always links: `dlink()` for devices, `alink()` for app instances, `dlistlink()` for device counts, and for this app a `clink(kind, id, name)` to `/app/editor/{id}`, `/driver/editor/{id}`, `/library/editor/{id}`, `/bundle/editor/{id}`. Dates arrive as epoch ms and are formatted with `toLocaleString()`; "last checked" and "last changed" are shown as absolute days with the `--ok/--warn/--crit` tiers, never as bare timestamps. Table headers and card titles link to README anchors that explain the rule (thresholds, TTLs, retention) instead of exposing a setting for it. Inline status text and `flash()` for outcomes; `confirm()` only before a destructive action (uninstall, rollback, unattended opt-in); no `alert()`. Delegated event listeners, not inline `onclick` strings with array indexes; every delete or view addresses a stable id (hub id, package key, snapshot file name), never a list position.

**Long-running work.** Anything that compiles code or sweeps upstream is a job: `POST …/start` returns `{jobId}`, `GET /api/jobs/{id}` returns `{status: 'running'|'done'|'error', processed, total, startedAt, error, result?}`; the terminal status is `'done'`. The SPA keeps a `pollTimers[jobId]` registry so a re-render cannot stack pollers, polls every 2 s, keeps the last good row on a transient fetch error, caps the wait client-side (5 min) so a stranded job reads as timed out rather than hanging, and disables the triggering button with a busy label until the terminal status. Server-side progress is read from the `AtomicInteger`s while live, a watchdog fails stranded jobs, and the finalize gate re-reads the atomics. This is why apply (6.2), package transactions (6.3), the unattended pass, the fact reader and multi-item drift checks are all start/status routes in 9 rather than one long OAuth call: a compile of a large driver runs tens of seconds, and the cloud relay returns 504 after about 10 s.

**Payload bounds.** No gzip exists on this path. `GET /api/inventory` carries no sources, no diffs and no manifests inline (~300 B per component); sources and manifest documents are fetched per item on demand; snapshot lists are capped per component; anything that could cross the cloud relay has a slim projection. Consumers degrade on field presence, never on a version number.

**Lockstep and self-sync.** `CODE_VERSION` in both files, bumped together even for a UI-only change (otherwise the page shows a false "App Update Required"); `syncUI()` downloads the HTML from the mirror only when `state.lastInstalledVersion != CODE_VERSION` or 24 h have passed, and `processSyncUIResponse` refuses any body that does not contain the app's exact `const CODE_VERSION = "…"` string; daily cron plus `POST /api/ui/sync` and `POST /api/reinit`; the config page and the SPA's Settings tab show app version, UI version, in-sync state, and the GitHub "vX available" line from `/api/version/check`; the label badge is stripped by text with optional tags (saving the config page strips label HTML). `serveUI` never checks GitHub per request. After a publish the hubs' UIs sync themselves; nobody uploads the HTML per hub.

**Testing from the first commit.** Mode 2: `tests/test-code-manager-api.sh` (bash argument parsing, Python assertions, closed-loop contract, instance self-discovery by `appTypeName`, exit 0/1/2). Mode 3: every SPA derivation (classification, truth table, version parse and compare, safe-to-remove, manifest validator, semaphore, in-flight dedup) written as a dependency-free named `function` and tested by brace-extraction from the shipped HTML, so tests bind to the code that ships. A Node test that reads both files and fails on `CODE_VERSION` drift. Hostile-fixture tests for every renderer that touches upstream content (10, escaping). Parse gates before any push: `groovy scripts/groovy-parse-check.groovy` and `node --check` on the extracted JS. No mocked hub responses in integration tests.

**Groovy side, inherited as-is.** `hubMapRequest()`/`hubRequest()` with one transient retry and `[ok, data, error]`; `cachedFetch(key, ttl, closure)` as the single server cache, cleared wholesale in `updated()`, closures returning `null` on failure; `timed(name)` per aggregator feeding `/api/stats`; `jsonResponse()`; a request-scoped shared map so one endpoint never fetches the same hub resource twice; `GET/POST /api/settings` with a key whitelist and `initialize()` re-run only when a scheduling key changed; three logging booleans with `logsOff`; `@CompileStatic` on pure computation; no regex parsing of hub HTML anywhere — every hub read in this design is a JSON endpoint. Cron `*/N` day syntax is never used; recurring work is a fixed jittered daily schedule or self-rescheduling `runIn`.

## 11. Driver alternatives by fingerprint

An index built off-hub and fetched by the SPA only. Source of truth: every driver location reachable from the catalog (all `packageManifest.json` `drivers[]` of all repositories in the master list plus subscribed custom repositories), fetched by tooling in the host repository (`tools/fingerprint-index/`), parsed for `fingerprint(...)` lines, and published as one JSON file on GitHub under the mirror. Schema contract:

```
{ "schemaVersion": 1, "generatedAt": epochMs, "catalogCommit": "…",
  "drivers": [ { "id": "<manifest driver uuid>", "name", "namespace", "package": "<manifest url>", "location": "<raw url>",
                 "fingerprints": [ { "protocol": "zigbee"|"zwave"|"matter",
                                     "manufacturer"?, "model"?, "profileId"?, "inClusters"?, "outClusters"?,
                                     "mfr"?, "prod"?, "deviceId"?, "deviceJoinName"? } ] } ] }
```

Lookup in the SPA: the hub side provides `GET /api/devices/fingerprints` (aggregator over `/hub2/devicesList` + the `manufacturer`/`model`/`inClusters`/`mfr`/`prod`/`deviceId` data values from `fullJson`, fetched under the hub budget (5.1) once per device and cached with a 7-day TTL — `/hub2/devicesList` does not carry the `data` map, so the per-device call is unavoidable, but the values change only on a driver switch or a re-join); the SPA joins against the index by exact `manufacturer`+`model` (Zigbee), `mfr`+`prod`+`deviceId` (Z-Wave), and shows for each device the drivers that claim it, with the currently assigned one marked. Built-in drivers cannot be indexed this way: Hubitat publishes no driver source and no endpoint lists built-in types; the built-in column is limited to "currently assigned built-in driver" until a source for built-in fingerprints exists. The switch-driver action needs the admin endpoint the device page uses to change Type; it is not yet captured in this repository and the feature ships read-only until it is.

## 12. Author mode

The manifest documents make Code Manager useful to the person publishing a package, not only the person installing one. The HPM publishing flow is: the author hosts `packageManifest.json` and `repository.json` on their own GitHub; the master list records the `repository.json` URL once, the first time, through a human request to a maintainer; every later package is added by editing the author's own `repository.json`. Code Manager covers everything before that one human step:

- **Validation against the parser's rules**, the same validator the install path runs on fetched manifests: `category` is one of the six enum values and belongs in `repository.json`, not the package manifest; `tags` from settings.json; `required` is a literal boolean (only `required == false` makes a component optional; a string or a missing key makes it neither); `id` values are UUIDs that never change once published; `location` is a raw URL; `betaLocation` and `betaVersion` come together; `minimumHEVersion` is present; `oauth` is set on apps that declare `mappings`.
- **Cross-check against the code** the manifest describes, which Code Manager has: each component's `name` and `namespace` equal the Groovy `definition()`; the component's `importUrl` equals its manifest `location`; every `files[]` entry exists in File Manager with a plausible `transferType`.
- **The lockstep check as a pre-publish lint**: a component whose hash changed since the manifest `version` was last bumped, while `version` is unchanged, is the mistake that leaves every existing install blind to the release; it is the `changed-upstream` row of 4.2 applied to the author's own packages.
- **Test-install from the document**: the identical engine HPM users will hit — download-first, component order, optional selection, OAuth enabling, file transfer, bundle import — run from the local manifest against a development branch URL, with no `repository.json` and no master-list entry. Components must be reachable by URL for this; code that exists only on the hub can be described and validated but not installed from the document.
- **Publish artifacts**: download the manifest for the repository; generate the `repository.json` entry (`name`, `location`, `category`, `description`, `tags`, the fields that live there and not in the manifest); after publishing, re-key the package from the local key to the manifest URL and confirm the hosted file hashes equal the local document.

Author mode adds no schema: a document that passes is a valid HPM manifest as-is, and the one local-only extension (`libraries[]`) is flagged by the validator as something HPM will ignore. There is no API to the maintainers; Code Manager's part ends at producing correct artifacts.

## 13. Settings

`txtEnable`/`debugEnable`/`traceEnable` (repo standard, with `logsOff`). `labelBadge` (app label shows only Code Manager's own-version update). Notification devices come back only with scheduled checks (14). Nothing else is a setting: the hub-budget values (5.1), snapshot retention (3 per component), the unattended cap (3 packages per run), the in-flight limits, and the fetch caps are fixed values documented in the README, and the cards and table headers that depend on them link to the README anchor that states the rule. Repository subscriptions, per-package beta opt-in, per-package unattended opt-in, and per-repository `http://` exceptions are registry data edited from the SPA, not hub settings. No credentials of any kind.

## 15. Decisions taken here and their basis

- Unattended apply exists only as an explicit per-package opt-in through the same transaction as an interactive apply; no global `Always`/`Include`/`Exclude` modes, and a new package is never auto-applied until selected.
- `saveOrUpdateJson` over `ajax/update` for code writes, because upstream updates may change `definition()` flags (repo note: `ajax/update` does not re-parse it).
- Hashes are computed over `ajax/code` (unflattened) bodies, not `downloadFull`, so local and upstream have the same shape for `#include` consumers.
- The hub never fetches a caller-supplied URL; the SPA registers the URL first and the hub resolves it from the registry.
- Six in-flight upstream requests, not eight, to leave endpoint handlers headroom.
- Bundle freshness is manifest-driven or unknown; the hub exposes no hash for an installed bundle and the zip is not worth fetching on a schedule. The members of a bundle carry their own upstream locations and are checked individually.
- Every write route starts from a live, single-use, 10-minute plan whose steps are bound to component identity, installed lock and hash, and fetched body hash (6.2); one writer at a time is enforced by a `Semaphore(1)` plus a refreshed durable lease in `atomicState.op`, with `write-busy` rejection and no queue (6.6); every write path runs under an `atomicState` operation journal with deterministic recovery and no automatic re-attempt (6.6); bundles are outside the rollback guarantee and outside unattended apply, private bundles are labeled non-reversible (6.3); `manage` mode requires HPM disabled and re-checks before each write (8.3); manifest documents and snapshots are named by digest and validated against their embedded identity before use (2.2, 2.4).
- The SPA inherits HubDiagnostics' current conventions wholesale (10) and adds the two things its review left open — in-flight dedup and a 3-wide semaphore in `api()` — rather than rediscovering them; every compiling operation is a start/status job because of compile time and the cloud relay's ~10 s limit; settings are limited to logging and notifications, everything else is a documented fixed value or registry data.
- Manifests are documents in File Manager for every origin, not a view synthesized from `state`: one read path for the engine, user-editable grouping and metadata for local packages, survival across uninstall, portability between hubs, and an on-ramp from local package to published HPM package without a second schema. The registry in `state` holds binding only.
- HPM's `heID` and manifest URL keys are preserved verbatim so the import is lossless and the exit via HPM Match Up is predictable; onboarding imports HPM's registry rather than re-deriving it from a scan (8.1).
- A write has three outcomes, `ok`, `compile-error` and `unknown`; an exception or missing response on a save is `unknown`, resolved by read-back against the bulk list and `ajax/code` hash and never by retry, and nothing else is written while a step is unresolved (6.2, 6.3, 6.6). Basis: a save of a very large source was observed to land minutes after its client request timed out, and a client that treated the timeout as failure rolled back into a hub still compiling and left a multi-component package half-updated. Compile cost (recorded write-to-verified time, then size) gates unattended apply (6.5).
- The inventory and its dependencies come from bulk reads only, and every shown fact is live, read at a stated `lastModified`, or checked at a stated time (3.1); per-item reads are lazy and run in the background under a fixed hub budget (5.1, 5.2); drift is checked when the user asks (5.3). Basis: reading every source in one pass took about 11 minutes on a 212-item hub, ran inside a request, tied up the hub's code endpoints, and repeated whenever one item failed to read; an inventory that reports stale freshness as current wastes the user's time more than one that says what it has not read.
